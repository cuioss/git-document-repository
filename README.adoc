== What is it?

Base libraries for _Git as the Persistence of Versioned Documents_: a server-side Git repository as the persistence
of an application in which users maintain versioned documents (OWASP SAMM assessments, threat models, incident
response reports, ISMS). Git is the persistence only, not a user-facing tool; the libraries build on JGit and work
in memory, without working trees.

The documentation starts at link:doc/README.adoc[doc/README.adoc]: concepts, architecture decisions and
specification.
The repository is a multi-module Maven reactor whose modules are released together but consumed separately.

[cols="1,3"]
|===
|Module |Content

|`git-core`
|Hardened repositories, remote policy, identity, results, transport, reading, cache repository, in-core writing,
compare-and-swap, in-core merge, notes; linked working trees, commit from a working tree, working-tree status.

|`git-testing`
|Generators and fixtures: local and in-memory repositories, a local remote.

|`git-store`
|Repository registry, typed configuration, codec interface, outcome list and result, service interfaces with provider
selection; write path (drafts, explicit save with lease and per-attempt step, conflicts and change detection, draft
expiry), release with tag, in-memory index with contributors, fetch and snapshots, post-commit listeners. Depends on
`git-core` only.

|`git-forms`
|Schema-driven documents: outcome list and result, log messages, kinds of documents as configuration, schema
validation, data layout, YAML codec in schema order. Depends on `git-store` only.
|===

`git-core` holds the repository part taken over from its first client: hardening, remote policy, identity, results,
repository operations and the cache repository, plus in-core writing, compare-and-swap reference updates, in-core
merge, reading (snapshot, path history, changed paths) and notes. Its package `de.cuioss.git.document.core.worktrees`
holds the worktree part taken over from the same client: adding, listing and removing linked working trees and the
commit from a working tree, plus a new working-tree status. `git-testing` holds its credential generator and its repository fixtures (see
link:doc/concepts/module-structure.adoc[Module Structure] and link:doc/clients/pm-mcp-core.adoc[Client: `pm-mcp-core`]).
`git-store` holds the foundation of the document store: the registry of its repositories, the typed configuration
checked at start, the codec interface, its own outcome list and result, and the service interfaces for signing keys,
anchor proofs and the person directory with the selection of their providers. On that foundation it holds the write
path (drafts, the explicit save with its lease, conflicts and change detection, draft expiry), the release of a
document with its version tag, the in-memory index with consumer contributors, fetch and snapshots, and the
per-branch post-commit listeners; the commit signature, the identity trailers and the anchoring follow. `git-forms`
holds the layer of schema-driven documents on top of the store: its own outcome list, result and log messages, the
kinds of documents loaded from configuration alone, validation against the JSON Schema of a kind (Draft 2020-12), the
file layout of a document and the YAML codec that writes its data in schema order; generated output, workflow and
links follow. The other aspect modules (`git-timestamp`, `git-directory`) follow as the document store needs them.

The build guards the layering and the consumer closure of `git-core`: a module that declares a dependency on another module outside the module graph fails
the build, and so does a compile or runtime artifact outside the closure a consumer of `git-core` alone receives.
`git-core` ships the GraalVM native-image metadata for the JGit classes it reaches; `git-store` relies on it, and
`git-forms` ships the resource metadata of its JSON Schema validator (see
link:doc/specification/general.adoc[General Requirements], GDR-GEN-1 and GDR-NFR-4).

== Credentials

All secrets (GPG, Sonatype, Sonar, Release App) are managed at the https://github.com/cuioss/cuioss-organization[cuioss organization level]. The caller workflows pass them explicitly to the reusable workflows; pass only the secrets a reusable workflow declares, an undeclared one makes every run end in `startup_failure`. No repo-level secrets need to be configured.

== Releasing

Merging a change of `release.current-version` in `.github/project.yml` *is* a release: the central
guard in `reusable-maven-release.yml` publishes to Maven Central whenever that value differs from the
merge commit's first parent and no tag for it exists. Maven Central releases cannot be withdrawn.
Every other `project.yml` edit reaches the release workflow too and is refused by the guard.

* `current-version: 0.1.0` is declared together with `0.1.0-SNAPSHOT` in the poms. Do not touch it in an ordinary PR.
  The first release is a deliberate `workflow_dispatch` from `main`, and only once the modules contain code.
* Every later release goes through the runbook `.claude/skills/release/SKILL.md`: a dedicated
  `chore/release_<version>` PR that changes nothing but the version, merged only after the pre-cut
  checks.
* Do not rewrite the `cuioss/cui-java-module-template` literal in `.github/workflows/release.yml`; it only excludes the template repository itself.
* `maven-build.enable-snapshot-deploy` is `true`: every push to `main` deploys the `0.1.0-SNAPSHOT` modules to the Sonatype snapshot repository. This is not a release.
