= Trailhand: MCP Server
:toc: left
:toclevels: 2
:toc-title: Table of Contents
:source-highlighter: highlight.js

xref:../README.adoc[Trailhand documentation] » Specification

The MCP endpoint for AI agents as an OAuth 2.1 protected resource
(link:https://www.ietf.org/archive/id/draft-ietf-oauth-v2-1-13.html[draft-ietf-oauth-v2-1-13], the Internet-Draft the
MCP authorization specification of revision 2026-07-28 is based on). Reasoning:
xref:../concepts/mcp-server.adoc[MCP Server]. Normative sources: MCP specification revision 2026-07-28,
link:https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization[Authorization] and
link:https://modelcontextprotocol.io/specification/2026-07-28/basic/transports[Transports] (Streamable HTTP);
link:https://www.rfc-editor.org/rfc/rfc9728[RFC 9728], link:https://www.rfc-editor.org/rfc/rfc8707[RFC 8707],
link:https://www.rfc-editor.org/rfc/rfc6750[RFC 6750]. Authorization is optional in MCP; Trailhand uses
authorization and follows the MCP authorization specification for HTTP transports.

[#TRH-MCP-1]
== TRH-MCP-1: Transport

* The MCP server must offer Streamable HTTP at `/mcp` in the shape of MCP revision 2026-07-28 and no STDIO transport.
* A request with an invalid `Origin` header must be answered with `403`.

[cols="1,3"]
|===
|Item |Value

|Endpoint
|`POST /mcp`, Streamable HTTP, revision 2026-07-28 (no protocol-level sessions; an `Mcp-Session-Id` header is ignored
and never minted or echoed, a `Last-Event-ID` header is ignored)

|`GET`, `DELETE`
|`405 Method Not Allowed` on `/mcp` (the answer the revision gives to clients of earlier revisions)

|`Origin`
|Validated against `mcp.allowed-origins`; absent is accepted, present and not listed is `403`

|Content types
|Request `application/json`; response `application/json` or `text/event-stream`
|===

[#TRH-MCP-2]
== TRH-MCP-2: Protected Resource Metadata

* The server must serve RFC 9728 metadata at `/.well-known/oauth-protected-resource/mcp` (the URL RFC 9728 derives
  from the resource identifier `<origin>/mcp`), and the same document at `/.well-known/oauth-protected-resource`, with
  `resource`, `authorization_servers` (at least one) and `scopes_supported`; `offline_access` must not be listed.
* A request without a token must be answered with `401` and `WWW-Authenticate: Bearer` carrying `resource_metadata`
  and `scope`.

The path-suffixed URL is formed by inserting the well-known path between the host and the path `/mcp` of the resource
identifier; MCP clients try the root path when it is not found.

[source,json]
----
{
  "resource": "https://trailhand.example.org/mcp",
  "authorization_servers": ["https://idp.example.org/realms/main"],
  "scopes_supported": ["trailhand:read", "trailhand:write", "trailhand:request-release"],
  "bearer_methods_supported": ["header"]
}
----

`resource` is `mcp.canonical-uri`; `authorization_servers` is `mcp.authorization-servers`.

Unauthenticated request (the header is sent as one line; it is wrapped here for readability):

[source,http]
----
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer resource_metadata="https://trailhand.example.org/.well-known/oauth-protected-resource/mcp",
                  scope="trailhand:read"
----

[#TRH-MCP-3]
== TRH-MCP-3: Token Validation

* Every request must be authenticated by a bearer token in the `Authorization` header; a token in the query string
  must be refused.
* The server must validate signature, expiry, issuer and audience; the token's `aud` must contain the server's
  configured canonical URI.
* An invalid, expired or foreign-audience token must be answered with `401`.

Engine: `token-sheriff-validation-quarkus`, one issuer configuration per entry of `mcp.authorization-servers`.

[cols="1,2"]
|===
|Check |Rule (each failure is `401`)

|Location
|`Authorization: Bearer <token>`; `access_token` in the query string is refused

|Signature
|Against the issuer's JWKS; asymmetric algorithms only

|`exp`, `nbf`, `iat`
|Current time within bounds (clock skew per Token Sheriff configuration)

|`iss`
|One of `mcp.authorization-servers`

|`aud`
|Contains `mcp.canonical-uri` (`expected-audience`)
|===

[#TRH-MCP-4]
== TRH-MCP-4: Scopes and Rights

* Each tool must require one scope of `trailhand:read`, `trailhand:write`, `trailhand:request-release`.
* A call lacking the scope must be answered with `403`, `error="insufficient_scope"`, the required `scope` and
  `resource_metadata`.
* The effective permission must be the intersection of the token's scopes and the user's rights
  (xref:authentication.adoc#TRH-AUTH-2[TRH-AUTH-2]).

[cols="1,2"]
|===
|Scope |Tools

|`trailhand:read`
|`list_documents`, `read_document`, `search`, `diff`, `list_due`, `read_catalog`, `read_recipe`

|`trailhand:write`
|`write_draft`, `discard_draft`, `save`

|`trailhand:request-release`
|`request_release`
|===

Missing scope (one header line, wrapped here for readability):

[source,http]
----
HTTP/1.1 403 Forbidden
WWW-Authenticate: Bearer error="insufficient_scope", scope="trailhand:write",
                  resource_metadata="https://trailhand.example.org/.well-known/oauth-protected-resource/mcp"
----

After the scope check the user's rights on the target repository are checked; a missing right is a tool error
`FORBIDDEN`, not an HTTP error, and names no document the user may not read.

[#TRH-MCP-5]
== TRH-MCP-5: No Passthrough, No Credentials to the Agent

* The server must never forward a received token to another service.
* No Git or KMS credential may appear in a tool result, an error or a log record; a test must scan responses and logs
  of the integration suite for the configured credential values.

Git is reached with the technical user's credential, the KMS with the application's own; tool results and errors are
built from typed result objects that carry no credential field.

[#TRH-MCP-6]
== TRH-MCP-6: Human-Bound Releases

* An agent must not complete a release.
* The tool `request_release` must create a pending release that appears in the requesting user's *Due* lens.

[cols="1,2,2"]
|===
|Tool |Input |Result

|`list_documents`
|`repository`, `category`, optional `filter`
|Ids, titles, states

|`read_document`
|`repository`, `id`, optional `revision` (tag or commit)
|YAML data and fragments

|`search`
|`query`
|Matches from the index the user may read

|`diff`
|`repository`, `id`, `from`, `to`
|Structured diff

|`list_due`
|—
|Deadlines, reviews and pending releases of the user

|`read_catalog`
|`catalog`
|Entries of a catalog

|`read_recipe`
|`category`, optional `id`
|Without `id` the recipes of the category; with `id` the recipe's steps (`title`, `guidance`, `fills`)

|`write_draft`
|`repository`, `id`, `data` (validated against the category schema)
|`DRAFT_SAVED`

|`discard_draft`
|`repository`, `id`
|`DISCARDED`

|`save`
|`repository`, `id`, `base_blob_ids`
|`SAVED`

|`request_release`
|`repository`, `id`, `comment`
|`RELEASE_REQUESTED` with the request id; the request waits in the user's *Due* lens. The request is saved in Git, so
`REJECTED` and `GIT_UNAVAILABLE` are possible as well
(xref:architecture-and-modules.adoc#operation-outcomes[Operation Outcomes])
|===

The Result column shows a successful call. The complete outcome set of each tool, the same as that of its web-app
equivalent, is listed once in
xref:architecture-and-modules.adoc#operation-outcomes[Architecture and Modules, Operation Outcomes].

Tool input sizes are limited to the category schema's `maxLength` and `maxItems`; a document of more than 1 MiB is
refused.

[#TRH-MCP-7]
== TRH-MCP-7: Audit

* Every tool call must produce one log record with pseudonym, client id, tool, repository and outcome; token material,
  session ids and document content must not be logged.

One `INFO` record per tool call: `TRAILHAND-<n>: MCP tool {tool} by {pseudonym} via {client} on {repository}:
{outcome}`, where `{client}` is the token's `client_id`, else `azp`, else `-`.
