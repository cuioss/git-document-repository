[#CIFR-NFR-1]
== CIFR-NFR-1: Index Size and Start Time

* With 1,000 SAMM assessments of 90 answers each, the in-memory index must stay below 100 MB of heap, and the native
  application must become ready within 60 seconds after the repositories are present locally.

[#CIFR-NFR-2]
== CIFR-NFR-2: Save Latency

* The application's share of a save (the save duration minus the measured fetch and push time) must stay within
  500 ms at the 95th percentile.

Fixture for both: a generated `samm-assessments` repository with 1,000 assessments of 90 answers
(`cui-test-generator`). Index size: heap histogram after start, attributed to the index classes. Start: time from
process start to readiness `UP` with local repositories present. Save latency: 1,000 sequential saves against the
Gitea of the integration stack; the save service records the time spent in fetch and push per save (timer
`cisos_friend_save_git_seconds`).

The checks of CIFR-NFR-1 and CIFR-NFR-2 run in the `benchmarks` lane. It reports each measured value against its
target and does not fail the build.

[#CIFR-NFR-3]
== CIFR-NFR-3: Concurrent Workshop

* Fifteen users saving the fifteen different practices of one assessment concurrently, ten saves each, must lose no
  save.

Fifteen virtual users, each saving ten times to its own practice of one assessment, in parallel; afterwards all 150
changes must be present on the working branch and every save result must be `SAVED` after the library's retries.

[#CIFR-NFR-4]
== CIFR-NFR-4: Inbound Input Security

* Every path segment, query parameter and header read by the REST API and the MCP endpoint must pass a
  `de.cuioss.http.security` validation pipeline before use; the adversarial attack-database tests must pass.

Tests:

* Inbound validation: every REST resource and the MCP endpoint run the generator-driven attack databases of
  `cui-http-testing` (path traversal, header injection, query manipulation); every attack must be rejected before
  reaching a service.
* MCP token tests: foreign audience, expired, wrong issuer, query-string token, missing scope; each with the specified
  status and `WWW-Authenticate`.
* Credential leak scan: see xref:mcp-server.adoc#CIFR-MCP-5[MCP Server, CIFR-MCP-5].
* Web: CSRF header missing, wrong `Origin`, CSP present on every HTML response
  (xref:web-app.adoc#CIFR-WEB-8[Web App, CIFR-WEB-8]).

[#CIFR-NFR-5]
== CIFR-NFR-5: Native Image Verification

* The integration suite must run a fetch, a save, a release and a push against a local Git server with the native
  image before any other integration test.
* A boot of the native image with an invalid configuration must fail
  (xref:configuration.adoc#CIFR-CONF-1[Configuration, CIFR-CONF-1]).

The first test class, `NativeGitRoundTripIT`, runs fetch, save, release and push against Gitea and verifies tag and
signature. It runs in its own failsafe execution `native-round-trip`, declared before the execution of the remaining
suites, with both its `integration-test` and its `verify` goal bound to the `integration-test` phase. Maven runs
several executions bound to one phase in the order they are declared in the POM, a parent's declarations before the
child's
(link:https://maven.apache.org/guides/mini/guide-configuring-plugins.html#Using_the_.3Cexecutions.3E_Tag[Maven:
Configuring Plugins, Using the `<executions>` Tag]), so a failure of this class fails the build before the remaining
suites start. A second boot, with an invalid configuration, checks that the boot fails.
