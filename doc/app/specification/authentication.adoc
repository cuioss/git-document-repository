[#CIFR-AUTH-1]
== CIFR-AUTH-1: Web Login

* The web login must use the authorization code flow with PKCE `S256` as a confidential client through Token Sheriff.
* No access, refresh or ID token may be sent to the browser.
* During login the browser must hold only a short-lived login-transaction cookie, afterwards only the session cookie,
  both `HttpOnly` and `Secure`; the session must end after a configurable idle time (default 30 minutes) and absolute
  lifetime (default 8 hours).
* The `return` address of the login must be accepted only as a same-origin relative path that matches a canonical
  address (link:web-app.adoc#CIFR-WEB-3[CIFR-WEB-3]); any other value must be replaced by `/`.
* Logout must be RP-initiated and revoke the held tokens.

[cols="1,3"]
|===
|Item |Value

|Engine
|`token-sheriff-client-quarkus`, confidential client

|Flow
|Authorization code, PKCE `S256`, session-bound `state` and `nonce`, issuer check; PAR when the provider supports it

|Endpoints
|`GET /api/v1/auth/login?return=<address>`, `GET /api/v1/auth/callback`, `POST /api/v1/auth/logout`

|`return`
|Starts with a single `/` (not `//`, no `\`, no scheme, no authority) and matches one of the canonical addresses of
link:web-app.adoc#CIFR-WEB-3[Web App, Navigation]; kept in the server-side login transaction, not in the browser

|Transaction cookie
|`__Host-cisos-friend-login`; `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, `Max-Age=600`; carries only an opaque
reference to the server-side login transaction (`state`, `nonce`, PKCE verifier); deleted by the callback. `Lax`,
because the browser does not send a `SameSite=Strict` cookie on the cross-site redirect back from the identity
provider

|Session cookie
|`__Host-cisos-friend-session`; `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`; set by the callback

|Callback response
|A small same-origin page that navigates to the checked `return`, not a `302`: a `302` continues the navigation that
the identity provider's page started, and `Strict` cookies are not sent with top-level navigations triggered from a
cross-site document context
(link:https://www.ietf.org/archive/id/draft-ietf-httpbis-rfc6265bis-22.html#section-5.6.7.1[draft-ietf-httpbis-rfc6265bis-22, §5.6.7.1];
a request is same-site only if its URL is same-site with its client's "site for cookies", §5.2;
link:https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie[MDN]: `Strict` cookies are sent
only for requests originating from the same site). The navigation started by the same-origin page is same-site and
carries the session cookie.

|Idle timeout, lifetime
|`web.session.idle-timeout` (default `PT30M`), `web.session.max-lifetime` (default `PT8H`)

|Logout
|RP-initiated at the provider's `end_session_endpoint`; held tokens revoked first

|`401` from `/api/v1`
|Response body names the login address; the web app follows it with the current canonical address as `return`
|===

[#CIFR-AUTH-2]
== CIFR-AUTH-2: Rights

* Rights must be derived from identity-provider groups through a configured mapping to repositories and the actions
  *read*, *edit*, *approve* and *administer catalogs*.
* Every request must be checked; a request without a mapped right must be refused (deny by default).
* No right may be derived from a directory role.

Input: the `groups` claim (or the claim configured as group source) of the session or bearer token. Mapping:
`cisos-friend.yaml` → `rights`.

[cols="1,3"]
|===
|Action |Permits

|`read`
|Reading documents, index views and diffs of the repository

|`edit`
|Drafts, saves and transitions that are no release

|`approve`
|Releases, with step-up (<<CIFR-AUTH-4>>)

|`administer-catalogs`
|Changes of the catalogs; erasure of persons; deletion of expired repositories
|===

A request is permitted only if one of the user's groups maps the action on the target repository. No other source
(directory role, token scope alone) grants a right.

[#CIFR-AUTH-3]
== CIFR-AUTH-3: Signed Commits and Identity Trailers

* Every commit must be signed by the application; there must be no unsigned commit and no other kind of signature.
* Every commit must carry the user's pseudonym, never the `sub`, and the issuer, the authentication time and the
  authentication context in the library's trailers.

[cols="1,2"]
|===
|Trailer |Source

|`Actor`
|The pseudonym from the person directory, looked up by (`iss`, `sub`)

|`Actor-Issuer`
|`iss`

|`Auth-Time`
|`auth_time`

|`Auth-Context`
|`acr` and `amr`, in the library's format
|===

[#CIFR-AUTH-4]
== CIFR-AUTH-4: Step-Up

* Every release must require step-up; no save and no other transition may require it.
* Before a release the application must check `acr` or `amr`, and `auth_time`, against the configured `step-up`
  values, and re-drive authorization with `acr_values` and `max_age` (RFC 9470) when they are not met.
* The release must be written only after the renewed values were verified; without them nothing is written.

Configuration: `cisos-friend.yaml` → `step-up` (`acr`, `amr`, `max-age`, default `PT5M`), one setting for all
categories (link:configuration.adoc#_cisos_friend_yaml[Configuration]).

. The release request checks the session's `acr` or `amr` and its `auth_time`.
. Not met: the service result is `STEP_UP_REQUIRED`; nothing is written.
. The REST API returns it with a step-up address, and the web app redirects there. The client re-drives authorization
  with `acr_values` and `max_age` and verifies the returned `acr` and `auth_time`.
. The release is written with the renewed values in the trailers.

The MCP server returns the tool error `STEP_UP_REQUIRED`; an agent never completes a release
(link:mcp-server.adoc#CIFR-MCP-6[MCP Server, CIFR-MCP-6]).

[#CIFR-AUTH-5]
== CIFR-AUTH-5: Git Credential

* The application must reach every Git server only as the technical user configured per repository.
* The application must merge every release itself and push it as the technical user; `main` must be protected so that
  only the technical user may push to it.

Per repository: `credential-ref`, the credential of the technical user (a deploy key or a bot account token); there is
no other kind of Git credential. `main` is protected on the Git server so that only the technical user may push and
nobody may force-push; a refused push returns `REJECTED` and the draft stays.
