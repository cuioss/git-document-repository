== Web Login
_See Requirement link:../Requirements.adoc#CIFR-AUTH-1[CIFR-AUTH-1: Web Login]_

Status: PLANNED

[cols="1,3"]
|===
|Item |Value

|Engine
|`token-sheriff-client-quarkus`, confidential client

|Flow
|Authorization code, PKCE `S256`, session-bound `state` and `nonce`, issuer check; PAR when the provider supports it

|Endpoints
|`GET /api/v1/auth/login?return=<address>`, `GET /api/v1/auth/callback`, `POST /api/v1/auth/logout`

|`return`
|Accepted only as a same-origin relative path: it starts with a single `/` (not `//`, no `\`, no scheme, no
authority) and matches one of the canonical addresses of link:web-app.adoc#_navigation[Web App, Navigation]; any
other value is replaced by `/`. The checked value is kept in the server-side login transaction, not in the browser

|Transaction cookie
|`__Host-cisos-friend-login`; `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, `Max-Age=600`; carries only an opaque
reference to the server-side login transaction (`state`, `nonce`, PKCE verifier); deleted by the callback

|Session cookie
|`__Host-cisos-friend-session`; `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`; set by the callback

|Callback response
|A small same-origin page that navigates to the checked `return`, not a `302`: a `302` continues the navigation that
the identity provider's page started, and `Strict` cookies are not sent with top-level navigations triggered from a
cross-site document context
(link:https://www.ietf.org/archive/id/draft-ietf-httpbis-rfc6265bis-22.html#section-5.6.7.1[draft-ietf-httpbis-rfc6265bis-22, §5.6.7.1];
a request is same-site only if its URL is same-site with its client's "site for cookies", §5.2;
link:https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie[MDN]: `Strict` cookies are sent
only for requests originating from the same site). The navigation started by the same-origin page is same-site and
carries the session cookie.

|Idle timeout
|`web.session.idle-timeout`, default `PT30M`

|Absolute lifetime
|`web.session.max-lifetime`, default `PT8H`

|Logout
|RP-initiated at the provider's `end_session_endpoint`; held tokens revoked first

|`401` from `/api/v1`
|Response body names the login address; the web app follows it with the current canonical address as `return`
|===

== Rights
_See Requirement link:../Requirements.adoc#CIFR-AUTH-2[CIFR-AUTH-2: Rights]_

Status: PLANNED

Input: the `groups` claim (or the claim configured as group source) of the session or bearer token. Mapping:
`cisos-friend.yaml` → `rights`.

[cols="1,3"]
|===
|Action |Permits

|`read`
|Reading documents, index views and diffs of the repository

|`edit`
|Drafts and saves

|`approve`
|Approval transitions (releases and approvals), with step-up where the workflow requires it

|`administer-catalogs`
|Changes of the role, team and service catalogs; deletion of expired repositories
|===

A request is permitted only if one of the user's groups maps the action on the target repository. No other source
(directory role, token scope alone) grants a right.

== Trailer Values
_See Requirement link:../Requirements.adoc#CIFR-AUTH-3[CIFR-AUTH-3: Identity in the Commit]_

Status: PLANNED

The application supplies these values to the library's trailer schema:

[cols="1,2"]
|===
|Value |Source

|Pseudonym
|Person directory lookup of the pair (`iss`, `sub`); created on first login

|Issuer
|`iss`

|Authentication time
|`auth_time`

|Authentication context
|`acr`, else `amr` joined by `+`

|Session HMAC
|HMAC-SHA-256 with the key of `signing.session-hmac-key-ref` over the session id: the `sid` of the login (web app);
for an MCP bearer token its `sid`, else its `jti`, else the SHA-256 of the token

|Agent client (MCP only)
|`client_id`, else `azp`
|===

== Step-Up Defaults
_See Requirement link:../Requirements.adoc#CIFR-AUTH-4[CIFR-AUTH-4: Signed Commits and Step-Up per Transition]_

Status: PLANNED

Every commit is signed by the application with the identity trailers. Defaults of `step-up` per transition in
`categories/<category>/workflow.yaml`; overrides in `cisos-friend.yaml` → `categories`.

[cols="2,1"]
|===
|Transition |Step-up

|`save` (all categories), `directory-entry`
|no

|`samm.release`, `threat-model.release`, `incident.release`; `isms.policy.approve`, `isms.scope.approve`,
`isms.soa.approve`, `isms.audit-report.approve`, `isms.management-review.approve`
|yes
|===

A transition that requires step-up and lacks the evidence returns the service result `STEP_UP_REQUIRED`; nothing is
written. The interfaces map it as follows:

[cols="1,3"]
|===
|Interface |Mapping

|REST (`/api/v1`)
|`STEP_UP_REQUIRED` with the step-up address (Step-Up)

|MCP
|Tool error `STEP_UP_REQUIRED`; an agent never completes a transition that requires step-up
(link:mcp-server.adoc#_tools[MCP Server, Tools])
|===

== Step-Up
_See Requirement link:../Requirements.adoc#CIFR-AUTH-5[CIFR-AUTH-5: Step-Up]_

Status: PLANNED

Configuration per category in `cisos-friend.yaml` → `categories.<category>.step-up`: `acr` (required `acr` value)
and `max-age` (default `PT5M`) (link:configuration.adoc#_categories[Configuration, Categories]).

. The approval request checks the session's `acr` and `auth_time`.
. Not met: the service result is `STEP_UP_REQUIRED`, which the REST API returns with a step-up address
  (<<_step_up_defaults>>); the web app redirects there.
. The client re-drives authorization with `acr_values` and `max_age` (RFC 9470) and verifies the returned `acr` and
  `auth_time`.
. The approval is written with the renewed values in the trailers.

== Git Credential
_See Requirement link:../Requirements.adoc#CIFR-AUTH-6[CIFR-AUTH-6: Git Credential]_

Status: PLANNED

Per repository: `credential-ref`, the credential of the technical user (a deploy key or a bot account token); there is
no other kind of Git credential. The application pushes every commit, releases included, with it. `main` is protected
on the Git server so that only the technical user may push and nobody may force-push; a refused push returns
`REJECTED` and the draft stays.

== First Login
_See Requirement link:../Requirements.adoc#CIFR-DIR-1[CIFR-DIR-1: First Login]_

Status: PLANNED

. With the default person directory (`git`): after login the server asks the library for the person of (`iss`, `sub`).
  The outcome entry-required (no pseudonym yet, which the library then creates, or a pseudonym without a saved entry
  from an interrupted first login) makes it answer every `/api/v1` request outside the allow-list below with
  `FIRST_LOGIN_REQUIRED`, until the entry is saved.
. `GET /api/v1/directory/me` returns the prefill: `name` from the token, `team` candidates from the groups.
. The form shows the text referenced by `web.information-text-ref`.
. `PUT /api/v1/directory/me` validates team and role against the catalogs and saves the entry.

Allow-list during the first login, exactly the requests the form and the shell need:

* `GET` and `PUT /api/v1/directory/me`;
* `GET /api/v1/catalogs/team` and `GET /api/v1/catalogs/role` (the pickers of the form);
* `GET /api/v1/session` (the anti-CSRF token) and `GET /api/v1/messages` (the texts);
* `POST /api/v1/auth/logout` and the login endpoints `/api/v1/auth/login` and `/api/v1/auth/callback`.

The MCP endpoint answers a tool call of such a user with the tool error `FIRST_LOGIN_REQUIRED`.

== Directory Flows
_See Requirements:_

* _link:../Requirements.adoc#CIFR-DIR-2[CIFR-DIR-2: Keeping the Entry Current]_
* _link:../Requirements.adoc#CIFR-DIR-3[CIFR-DIR-3: Catalog Maintenance]_

Status: PLANNED

* Own entry: `PUT /api/v1/directory/me` at any time.
* Confirmation: when the entry's last confirmation is older than `web.directory.confirm-interval` (default `P12M`), the
  next login shows the form with "Is this still right?"; confirming writes the confirmation date.
* Catalogs: `PUT /api/v1/catalogs/{catalog}/{id}` requires `administer-catalogs`; `DELETE` is not offered; retiring sets
  `retired: true`.
