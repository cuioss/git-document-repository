== Ports and Probes
_See Requirement link:../Requirements.adoc#CIFR-OPS-3[CIFR-OPS-3: Ports and Readiness]_

Status: PLANNED

[cols="1,1,2"]
|===
|Port |Protocol |Serves

|`8443`
|HTTPS
|Web app, `/api/v1`, `/mcp`, `/.well-known/oauth-protected-resource/mcp` and `/.well-known/oauth-protected-resource`

|`8080`
|HTTP
|Redirect to `8443` only

|`9000`
|HTTP (management)
|`/q/health/live`, `/q/health/ready`, `/q/metrics`
|===

Readiness checks, all required for `UP`:

[cols="1,2"]
|===
|Check |`UP` when

|`repositories`
|Every configured repository is either fetched in this process or present as a valid local repository from an earlier
fetch (start from the cache, see
link:architecture-and-modules.adoc#_degraded_operation[Architecture and Modules, Degraded Operation]); a remote
repository without a local copy keeps readiness `DOWN`. A local-mode repository (`remote: none`) counts once its local
repository opens and its index is built. A later fetch failure does not drop readiness

|`persons`
|The person directory was loaded (for `local`: every entry file under `directory.persons.path` read)

|`index`
|The index was built for every repository
|===

Volume: `/app/data` holds the local repositories and the entries of the `local` person directory
(`/app/data/persons`). It is mounted from a persistent volume; the image declares no
volume.

== Secrets
_See Requirement link:../Requirements.adoc#CIFR-OPS-4[CIFR-OPS-4: Configuration]_

Status: PLANNED

[cols="1,2"]
|===
|Secret |Mount or reference

|TLS key and certificate
|`/run/secrets/tls/{tls.key,tls.crt}` (`quarkus.http.ssl.certificate.key-files`, `quarkus.http.ssl.certificate.files`)

|OIDC client credential
|`oidc.client-credential-ref`: the client secret or the `private_key_jwt` key

|Git push credential
|`credential-ref` per repository

|Commit-signing key
|`signing.key-ref` (KMS key id recommended)

|Anchor key of the own timestamp
|`anchor.signed-key-ref` (a KMS key of its own, ideally under the security team's key policy)

|Session-HMAC key
|`signing.session-hmac-key-ref`

|Webhook secrets
|`webhook-secret-ref` per repository
|===

Every reference uses one of the forms `file:`, `kms:` or `vault:`
(link:configuration.adoc#_cisos_friend_yaml[Configuration, cisos-friend.yaml]).

== Compose Sample
_See Requirement link:../Requirements.adoc#CIFR-OPS-6[CIFR-OPS-6: Compose Sample]_

Status: PLANNED

Location: `deployment/compose-sample/`. Never builds an image; the image is `${CISOS_FRIEND_IMAGE}`.

[cols="1,3"]
|===
|Service |Role

|`cisos-friend`
|The application, named volume `cisos-friend-data`, configuration from `docker/cisos-friend-config/`

|`keycloak`
|Realm `cisos-friend` with users of each group, a confidential client for the web login and a client for an MCP
agent

|`gitea`
|Git server with the repositories of the default cut and push webhooks to the application

|`tsa-stub`
|RFC 3161 timestamp authority for the integration tests of the provider `rfc3161`; the sample itself anchors with the
own timestamp `signed`
|===

Scripts in `scripts/`: `start-sample.sh`, `stop-sample.sh`, `check-sample.sh` (logs in as a test user, writes a SAMM
draft, saves it explicitly, releases it with step-up, and verifies the release tag in Gitea).
