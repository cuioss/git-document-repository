== Repository Cut
_See Requirement link:../Requirements.adoc#CIFR-DP-1[CIFR-DP-1: Repository Cut]_

Status: PLANNED

Default `repositories` in the shipped `cisos-friend.yaml`:

[cols="1,1,1,2"]
|===
|Alias |Confidentiality |Retention |Categories

|`isms-core` |`public-internal` |`unlimited` |ISMS documents
|`isms-register` |`restricted` |`unlimited` |ISMS registers
|`isms-incidents-<year>` |`strongly-restricted` |`incident-reports` (default `P5Y`) |Incident reports
|`samm-assessments` |`public-internal` |`unlimited` |SAMM
|`threat-models` |`restricted` |`unlimited` |Threat models (variant B)
|`directory` |`public-internal` |`unlimited` |Catalogs, person entries under pseudonyms, record of erasures
|===

The retention classes and their periods are defined in `retention-classes`
(link:configuration.adoc#_retention_classes[Configuration, Retention Classes]); the period of `incident-reports` defaults
to `P5Y`, and an organisation sets its own period with its data protection officer. Each category names its class;
boot validation refuses a repository whose categories carry two retention classes
(link:configuration.adoc#_boot_validation[Boot Validation]).
`isms-incidents-<year>` is created on the first report of a year.

== References
_See Requirement link:../Requirements.adoc#CIFR-DP-2[CIFR-DP-2: Cross-Repository References]_

Status: PLANNED

Reference forms, as defined by the library: `<alias>:<kind>/<id>` for a document, where `<alias>` is the repository
alias of `repositories` (`isms-register:risk/R-042`, `samm-assessments:assessment/<id>`), and `<catalog>:<id>` for a
directory catalog entry (`service:payment-api`, `role:ciso`). The application may append `#<fragment>` to name a part
of the target document (a practice, a threat); the existence check applies to the document. On save every reference
field (schema `x-reference: true`) is resolved against the index; an unresolved reference is a field error
`REFERENCE_NOT_FOUND`. A reference into a repository the user may not read is reported as not found.

== Erasure
_See Requirements:_

* _link:../Requirements.adoc#CIFR-DP-3[CIFR-DP-3: Erasure]_
* _link:../Requirements.adoc#CIFR-DIR-4[CIFR-DIR-4: Former Members]_

Status: PLANNED

* Request: `POST /api/v1/directory/erasures` (right `administer-catalogs`) with the pseudonym and, where a statutory
  retention duty applies, `restrict-until` (a date). The application calls the library's erasure of the active person
  directory (link:../../Requirements.adoc#GDR-DIR-8[GDR-DIR-8]).
* `git`: without `restrict-until` one commit deletes the entry and records pseudonym and date in `erasures.yaml` of the
  persons' repository; with it, the entry is hidden and erased on that date by the library's daily task. The history
  keeps the earlier versions; the next checkpoint anchors the erasure commit while anchoring is active.
* A provider for the organisation's own source returns managed-by-source; the application answers `409` with the
  problem type `managed-by-source` and names no person.
* Display: an erased or restricted pseudonym is shown as "former member".

== Retention
_See Requirement link:../Requirements.adoc#CIFR-DP-4[CIFR-DP-4: Retention]_

Status: PLANNED

Daily job: for each repository whose retention class has a period, compute `end = created + period` (for
`isms-incidents-<year>`: 31 December of `<year>` + period). Expired repositories are listed in the *Due* lens of users
with `administer-catalogs`. Deletion is a confirmed action that removes the local repository on the volume (the cache
of a remote repository included) and, through the Git host API of the repository's `host-type`, the remote
repository; it is logged in `directory` and anchored by the next checkpoint while anchoring is active. Backup
copies of the Git server and of the volume are outside the application: the operator's duties
(link:../concepts/deployment.adoc[Deployment]) require their expiry to match the retention period.

Restriction of processing: before the end of the period, a document can be marked `processing-restricted: true`
(GDPR Art. 18). This field is distinct from the confidentiality class `restricted` of a repository. It replaces
erasure while a statutory retention obligation applies (GDPR Art. 17(3)(b), § 35(3) BDSG). A document marked this way
is readable only with `approve`.

== Personal Details
_See Requirement link:../Requirements.adoc#CIFR-DP-5[CIFR-DP-5: No Personal Details in Documents]_

Status: PLANNED

A schema field with `"x-person": true` holds a pseudonym (`p-…`); the form offers a pick from the person directory and
stores the pseudonym, and validation refuses a value that is no known pseudonym. There is no encrypted field type.
Fields with `"x-free-text": true` show the hint text `form.hint.no-personal-notes` from the catalogue: personal details
and interview notes belong in the ticket system.

== Read-Access Events
_See Requirement link:../Requirements.adoc#CIFR-DP-6[CIFR-DP-6: Read-Access Events]_

Status: PLANNED

Every `read_document`, `GET /api/v1/documents/…` and diff on a repository of class `restricted` or
`strongly-restricted` emits one `INFO` record `CISOS_FRIEND-<n>: {pseudonym} read {repository}/{id}`, routed to the SIEM
through the log shipping of the platform. Index views emit one record per view, not per document.

== Person Directory
_See Requirement link:../Requirements.adoc#CIFR-DP-7[CIFR-DP-7: Person Directory]_

Status: PLANNED

`directory.persons.provider` selects the library's person directory
(link:../../Requirements.adoc#GDR-STORE-15[GDR-STORE-15]):

[cols="1,2"]
|===
|Value |Behaviour

|`git` (default)
|Entries `persons/<pseudonym>.yaml` in the repository named by `directory.persons.repository` (default `directory`),
saved on `main` at signature level 1; first-login form and own-entry changes as in
link:authentication.adoc#_first_login[Authentication, First Login].

|the id of a provider for the organisation's own source
|Names and memberships from that source; no first-login form; erasure in that source
|===
