== Status

Accepted

== Decision

People need a browser interface for forms, dashboards, review and approval. The organisation already has a web app
with a worked-out visual language and UI structure: `pm-web-app` of `pm-mcp-clients`.

*The decision:* the web UI is a Svelte single-page application.

* Svelte 5 with runes and SvelteKit with `adapter-static`; no server-side rendering.
* The design tokens, the shell, the page templates, the component vocabulary, the address model, the `ApiClient` with
  one event stream, the i18n catalogue and the test setup are taken from `pm-web-app`.
* `frontend-maven-plugin` builds it into a resource JAR. The Quarkus application serves it on its own origin.
* Authentication differs: a server-side session through Token Sheriff, not device pairing.

The details are in link:../concepts/web-app.adoc[Web App].

== Alternatives rejected

=== Server-rendered pages (Qute)

Quarkus can render HTML with Qute. *Rejected because* a form-heavy, live-updating workshop interface needs client
state. It would also share nothing with `pm-web-app`.

=== A separate frontend server

A Node server could host the app. *Rejected because* it adds a second process, a second origin and CORS. Same-origin
serving keeps the session cookie `SameSite=Strict`.

=== A component library (Material, Tailwind UI)

*Rejected because* `pm-web-app` deliberately uses a closed own vocabulary with a token contract and contrast checks.
Mixing in a library would break both.

== Consequences

=== Properties of the design

* One origin, one cookie, no CORS.
* Visual and interaction rules come from one design source.

=== Accepted costs

* Parts of `pm-web-app` are copied until a shared component package exists.
* A strict Content Security Policy needs a hash for the SvelteKit bootstrap script.

=== When this is revisited

* When a shared UI package for both applications is published.
