== Status

Accepted

== Decision

The application needs authenticated users, their claims for the signed trailers, step-up for releases, and access
rights. Token Sheriff provides the OAuth and OpenID Connect flows as a set of libraries that run inside the
application; the identity provider is the external system.

*The decision:* authentication is delegated to Token Sheriff.

* The application is a confidential client through `token-sheriff-client-quarkus`. It holds the tokens server-side.
* During the login the browser holds a short-lived `HttpOnly`, `Secure`, `SameSite=Lax` login-transaction cookie
  that binds `state` and `nonce` across the identity provider's callback. Afterwards it holds only an `HttpOnly`,
  `Secure`, `SameSite=Strict` session cookie.
* Step-up for releases uses RFC 9470 through the client.
* Agents present bearer tokens that `token-sheriff-validation-quarkus` validates.
* Rights come from identity-provider groups, mapped per repository. Directory roles grant nothing.

The details are in xref:../concepts/authentication-and-identity.adoc[Authentication and Identity].

== Alternatives rejected

=== Tokens in the browser

A public client in the SPA would hold access and refresh tokens. *Rejected because* any script injection could take
them. RFC 10017, OAuth 2.0 for Browser-Based Applications (BCP 212),
strongly recommends the backend-for-frontend architecture for business applications, sensitive applications and
applications that handle personal data (section 6.1.4.3).

=== API Sheriff as BFF in front of the application

API Sheriff offers BFF variants. *Not chosen for the first iteration because* the application needs the claims and
step-up results in its own process to write signed trailers. A second hop would have to forward them. It stays an
option for organisations that run API Sheriff anyway.

=== Device pairing as in pm-web-app

*Rejected because* pairing identifies a device, not a person. The trailers need an authenticated person.

== Consequences

=== Properties of the design

* No token reaches the browser.
* One authentication component serves the web app and the MCP server.

=== Accepted costs

* Sessions are lost on restart. Users log in again.
* The application runs as one instance; a second instance would need a shared session store.

=== When this is revisited

* When the claims and step-up results can travel reliably from an API Sheriff BFF.
