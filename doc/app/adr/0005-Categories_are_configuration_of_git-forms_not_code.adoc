== Status

Accepted

== Decision

The four categories share one shape: schema, YAML data with AsciiDoc free text, generated output, review and approval,
deadlines and links. The library's
link:../../concepts/schema-driven-documents.adoc[schema-driven documents] provide that shape as one generic layer.

*The decision:* a category is configuration of the library's schema-driven documents.

* Per category: a JSON Schema, a template for the AsciiDoc output, a workflow with states, deadlines and signature
  levels, and the repository it lives in.
* The definitions live in the `categories` module as resources.
* The web app generates its forms from the schemas. The MCP server derives its tool inputs from them.
* No category has a hand-written view. Category-specific Java code exists only behind named extension points of the
  application, for behaviour a schema cannot express (see _Accepted costs_).

The shape is described in link:../../concepts/schema-driven-documents.adoc[Schema-Driven Documents].

== Alternatives rejected

=== One module per category with its own code

*Rejected because* the four categories differ in content, not in mechanism. Four implementations of review, deadlines
and step-up would drift apart.

=== Free-form documents without schema

*Rejected because* mandatory fields, deadlines and evaluations across documents need structure. That is what the
categories gain over Confluence.

== Consequences

=== Properties of the design

* A new category (exception approvals, supplier assessments, access reviews) costs a schema, a template and a workflow.
* Every category gets the same review, approval and evidence.

=== Accepted costs

* Behaviour a schema cannot express (outdated threat models, SAMM score calculation) needs a named extension point in
  the application. Each such point is a deliberate exception.

=== When this is revisited

* When a third category needs an extension point of its own.
