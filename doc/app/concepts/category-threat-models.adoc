A threat model is written once, in a workshop, with good intentions, and then the architecture moves on without it.
Nobody notices until the next audit asks for it. Threat models are the second category of CISOs-Friend, and its
contribution is not the diagram but the life cycle: recipes that guide the filling in, by people or by an AI agent
through the link:mcp-server.adoc[MCP server], and detection of the moment a model no longer describes its
application.

No existing system known to this concept maintains threat models across many applications, evaluates them and
detects that they are outdated, without additional operation. That gap is the place of this category.

== Where a Threat Model Lives

A threat model describes one application and has to change with its architecture. That raises the question of
place. Both answers are supported by configuration over the same repository layer.

* *A: in the application's repository* (`threat-model/` beside the code), recommended as the source of truth. It is
  versioned with the code; a release has its threat model. Outdated models become
  detectable: the architecture changed since the last commit of the threat model (new interfaces, dependencies,
  infrastructure files), so a review is due. This works through Git diffs, and only when model and code share the
  repository. The application reads many repositories, which the library's repository layer does anyway. It writes as
  the technical user, with commits it signs, into a branch of the service's repository and opens a pull or merge
  request, because the `main` of the applications belongs to their teams; the service team merges it
  (link:authentication-and-identity.adoc[Authentication and Identity]).
* *B: a central repository `threat-models`*, like SAMM. Simpler where teams allow no writes into their repositories or
  the applications are not in Git; outdated models are then detected only through references to the applications'
  repositories.

== What the Application Contributes

Not a diagram editor; Threat Dragon has one. The value lies in the life cycle:

. *Recipes* guide the filling in; the result is a structured report in an open format.
. *Format*: OTM or the JSON of Threat Dragon instead of an own schema. With Threat Dragon JSON teams can go on editing
  the diagram in Threat Dragon and the application reads the same file; with OTM that needs a Threat Dragon release
  that imports OTM (see the open questions).
. *Maintenance*: detection of outdated models, due dates, review and approval trailers.
. *Evaluation across applications*: open threats per application, untreated risks, age of the models.
. *Links*: threat modelling is a stream of the SAMM practice _Threat Assessment_ (business function _Design_), so
  maintained threat models are direct evidence for that practice in a SAMM assessment; accepted or untreated
  threats become entries of the ISMS risk register (`isms-register:risk/…`), countermeasures become issues.

=== Detecting an Outdated Model

The detection compares two points in the history of each repository of the service: the head that was current at
the last review, which the model records per repository, and the current head. A model is due for review when,
between the two, a configured set of paths changed: interface definitions (OpenAPI, protobuf), dependency manifests,
infrastructure files (Dockerfile, Helm, Terraform), or when the service's entry in the service catalog changed its
protection needs. The due date then follows the review interval derived from those protection needs. Recording the
reviewed head per repository matters in variant B: there the model's own commits live in the `threat-models`
repository, not in the service's history, and could serve as no base for a diff there.

== What to Observe

* *Confidentiality*: threat models describe attack paths. In the application's repository everyone with read access to
  the code sees them; internally that is mostly intended, for public repositories it is excluded, and variant B with a
  restricted repository applies.
* *Personal data*: hardly any, apart from owners; roles instead of names, as elsewhere.
* *Service*: every threat model refers to its entry in the service catalog (`service:…`), which names its
  repositories (link:../../concepts/directory-and-catalogs.adoc[Directory and Catalogs]).
* *Diagrams* are stored as data (OTM or JSON); images are generated, so diffs stay readable.

== Open Questions

. Decide the threat model format (OTM or Threat Dragon JSON). OTM is read by IriusRisk and SD Elements, but the
  released Threat Dragon (v2.6.2) exports OTM without importing it, so editing an OTM file in Threat Dragon needs a
  release with the OTM import of `main` (see <<_existing_tools>>).
. Prototype the detection of outdated threat models from Git diffs of the application's repository, including the
  default path set per technology.
. Which recipes ship with the application, and whether a recipe is itself a schema-driven document.
