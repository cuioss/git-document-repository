ISO 27001 clause 7.5 asks for the control of documented information: versioning, review and approval, availability,
protection against change, traceable changes. Read with a developer's eyes, that is a description of a Git server with
protected branches. The ISMS category takes the hint, carefully: it is an extension of CISOs-Friend for development
organisations, not a replacement for a complete ISMS product.

== The ISMS on Git

[cols="1,1"]
|===
|Clause 7.5 |Git

|Versioning, change history |commits, diff
|Review and approval |pull or merge request with review, protected `main`
|Protection against unauthorised change |repository rights, protected branches and tags
|Availability and retention |the Git server and its backup
|===

The ISMS artefacts sort into three groups:

. *Documents, very well suited*: policies, scope, risk methodology, statement of applicability, internal audit and
  management review reports. Rarely changed, approval-centred, diffable.
. *Registers, well suited*, with the pattern of link:category-samm.adoc[SAMM] (one file per entry, in-memory index,
  compare-and-swap): risks, controls, suppliers, nonconformities, and the assets that are no applications. The
  in-memory index rests on the design assumption that a mid-sized ISMS holds at most a few thousand register
  entries; the prototype measures index build time and memory at that size.
. *Operational data, referenced instead of stored*: tasks and deadlines (issue tracker of the Git server or Jira), the
  live handling of incidents (ticket system; the report on an incident is a schema-driven document, see
  link:category-incident-reports.adoc[Incident Response Reports]), training records per employee (learning platform or
  HR system). Persons, roles, teams and the applications as assets come from the
  link:../../concepts/directory-and-catalogs.adoc[directory and its catalogs].

=== Mechanisms the ISMS Uses

All of these are library mechanisms; the ISMS category uses them and adds no mechanism of its own.

* *Portable approvals*: approvals of a pull request live in the Git server's database. On merge the application
  writes them as commit trailers, so the evidence survives a change of Git server
  (link:../../concepts/identity-and-signing.adoc[Identity and Signing]).
* *Running numbers* (R-042) under concurrent creation: a ULID identifies a new entry until its first save, which
  assigns the readable number that then names the entry file
  (link:../../concepts/schema-driven-documents.adoc[Schema-Driven Documents]).
* *Reporting dates*: "statement of applicability and risk register as of the audit on 1 March" is a tag or the commit
  of that date; the index is built from it.
* *Deadlines and reminders* are computed from the index; notifications are runtime state of the application, not
  persistence.

=== The Bridge to SAMM

A released SAMM assessment becomes evidence for the secure-development controls (Annex A 8.25 ff.) by a reference to
its tag; target maturity levels become measures in the issue tracker; gaps between score and target may become risks
in the register. Both domains run on one engine.

=== Limits

* Real-time incident handling with escalation is no case for Git; connect a ticket system.
* Queries across many repositories need an instance that may read all of them, or queries run with the user's rights
  and show only what the user may see.
* Git replaces no document management system an auditor knows as such; the process description of the control of
  documented information has to be written once.

== Comparison with verinice

verinice (SerNet) is an established ISMS product. The classic product is a desktop client (Eclipse RCP) with the server
verinice.PRO and a database, strong in BSI IT-Grundschutz, ISO 27001 and data protection. verinice.veo is the new web
application: microservices on PostgreSQL, Keycloak and RabbitMQ, orchestrated by Kubernetes, offered as SaaS or on
premise.

[cols="1,2,2"]
|===
|Criterion |CISOs-Friend (Git) |verinice / verinice.veo

|Domain content
|Built by the project. The Grundschutz compendium is free; the texts of ISO 27001 are copyrighted and may not be
shipped, only own wording and numbers
|Catalogues, methodology and modelling logic included, matured over years

|Reports (statement of applicability, Grundschutz check, risk report)
|Built by the project
|Available in the product

|Operation
|Application and existing Git server; backup, rights and reviews exist
|veo: Kubernetes, PostgreSQL, Keycloak, RabbitMQ, or SaaS with the data at the vendor

|Versioning, diff, reporting dates
|Native and complete
|veo keeps every change of an object as a version: the History sidebar shows and restores earlier versions
(https://github.com/SerNet/verinice-veo-web-documentation/blob/main/docs/en/manual/objects.md[veo manual, Objects]),
and the veo-history service returns all revisions of a resource and the one current at a point in time
(https://github.com/SerNet/verinice-veo-history[verinice-veo-history]); the History section of the manual names no
comparison between versions

|Approval, four eyes
|Pull request review, protected branches, commit trailers, graded signatures up to passkeys
|Workflow functions of the application (scope to verify)

|Tamper evidence
|Hash chain, signed commits and RFC 3161 timestamps, verifiable externally
|Depends on the database and the administrators' rights

|Rights
|Coarse per repository, cut by confidentiality; enforced by the application, or by the Git server when pushing in the
user's name
|Fine-grained per object and role in the application

|Audience
|Development organisations working with pull requests; editing also directly in the repository (YAML and CI checks)
|Security officers and business units without Git

|Data sovereignty
|Plain YAML or AsciiDoc, readable without any software
|Database, export through exchange formats or REST API

|Integration
|Everything is files: CI pipelines, scripts, SAMM, issue tracker
|REST API (veo), import and export

|Acceptance by auditors
|Has to be explained (process description of the control of documented information)
|Known, especially for Grundschutz certification

|Time to use
|SAMM: weeks to months; a complete ISMS at verinice level: rather years
|Product available; introduction effort not assessed
|===

=== Positioning

From this comparison follows the positioning: CISOs-Friend complements verinice and does not compete with it as a
complete ISMS. Core and extension are listed in
link:cisos-friend-overview.adoc#_positioning[Overview, Positioning]; the decision is
link:../adr/0006-CISOs-Friend_complements_verinice_and_does_not_replace_it.adoc[ADR-0006].
