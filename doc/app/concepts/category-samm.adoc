An OWASP SAMM assessment usually ends its life as a spreadsheet named `samm-final-v3-reviewed.xlsx`, and the
comparison with last year's assessment is done by eye. That loses the one thing an assessment is for: the trend.
SAMM is the core category of CISOs-Friend because its model and its assessments map directly onto files in Git.

== What an Assessment Is

An OWASP SAMM assessment is a self-contained document at a date: answers per question of the model, comments,
evidence, and the scores computed from them. Its value is the comparison over time. It is edited as a draft, then
released and frozen as audit evidence. It refers to the SAMM model version it was taken with; since version 2 the
model itself is published as YAML files with semantic versioning. The data volume is small, and the only personal
data are the assessors, kept as pseudonyms and resolved through the directory.

Git therefore fits:

* the model is already YAML in Git;
* an assessment as YAML diffs well;
* release maps to a merge and a tag;
* history, rights, reviews and backups come from the existing infrastructure.

Drafts, the working branch per assessment, saving and release are mechanisms of the library's
link:../../concepts/storage-engine.adoc[storage engine]; this page names only what SAMM adds.

== Repository Layout

----
samm.yaml                              # pinned SAMM model version(s)
scopes/<scope-id>/scope.yaml           # refers to a team:, a service: or the organisation (directory)
scopes/<scope-id>/assessments/<assessment-id>/
    assessment.yaml                    # header: date, model version, status, assessors
    answers/<practice-id>.yaml         # one file per practice: parallel editing without conflicts
    evidence.yaml                      # evidence as links, not as files
scopes/<scope-id>/targets.yaml         # target maturity, roadmap
----

* *One file per practice* keeps concurrent edits of different practices conflict-free.
* *Deterministic serialisation* (fixed key order, stable formatting) makes diffs show real changes only; the
  serialisation is the library's (link:../../concepts/schema-driven-documents.adoc[Schema-Driven Documents]).
* *Evidence as links* (wiki, ticket, pipeline) avoids large files and Git LFS.
* *The scope* refers to a team, a service or the organisation through the stable ids of the
  link:../../concepts/directory-and-catalogs.adoc[directory and catalogs].

The repository is `samm-assessments`, readable by development and security
(link:data-protection-and-repository-layout.adoc[Data Protection and Repository Layout]).

== Workshop Mode: Save Often

SAMM is mostly filled in jointly in workshops. The application therefore uses the storage engine's _save often_
pattern: every explicit save lands on the assessment's working branch at once, as a small commit; the draft holds only
what is not yet saved. The UI remembers the blob id it loaded, like an ETag, and detects a concurrent change of the
same practice file. Two assessors on different practices never conflict. Two on the same practice get a conflict for
that practice file; the form shows the differing questions with both values, and they decide.

The alternative pattern, _private until submitted_, is available for single assessors who want to work longer before
others see the changes. The pattern is a property of the category's workflow, not of the user.

== Release, Comparison and Targets

* *Release* merges the assessment branch into `main` and creates the library's release tag `<collection>/<id>/v<n>`,
  here `assessments/<id>/v1`: an assessment is released once, so `n` is always 1. Protected branches and tags of the
  Git server make it immutable. Optionally, release opens a pull or merge request whose review is the four-eyes
  approval. The signature level is configured per transition of the category's workflow (level 2 for the release
  by default, see link:authentication-and-identity.adoc#_signature_levels_per_transition[Signature Levels]).
* *Scores* are computed as the OWASP SAMM toolbox computes them, so they stay comparable with toolbox results and the
  SAMM benchmark. The model has one question per activity, 90 in all (15 practices, 2 streams each, 3 maturity
  levels), and each answer carries the value of the model's answer set: 0, 0.25, 0.5 or 1
  (https://github.com/owaspsamm/core/tree/develop/model/answer_sets[SAMM core, answer sets]). A stream score is the
  sum of its three answers, a practice score the average of its two stream scores (0 to 3), a business function score
  the average of its three practices, and the overall score the average of the five business functions
  (https://owaspsamm.org/blog/samm-relative-scoring/[SAMM blog, 2025-01-21]). The toolbox spreadsheet of model
  v2.2.0 computes the same: per practice and maturity level the average of the two streams' answers, summed over
  the three levels; business function and overall scores as averages; an unanswered question counts 0; no rounding
  in the formulas (https://github.com/owaspsamm/core/releases/tag/v2.2.0[`SAMM_spreadsheet.xlsx` of release
  v2.2.0], sheets _Interview_ and _Scorecard_). The SAMM core team advises against changing the calculation for
  activities declared not applicable, because the results would no longer compare with the benchmark
  (https://owaspsamm.org/blog/the-not-applicable-question/[SAMM blog, 2023-02-28]); the application accepts only the
  answers of the model's answer sets, which contain no not-applicable answer.
* *Comparison* reads two released tags from the in-memory index and shows the score difference per practice and
  stream. Dashboards, trends and heat maps over hundreds of assessments come from the same index.
* *Targets* in `targets.yaml` name the target maturity per practice. A gap between the released score and the target
  becomes a measure: an issue in the issue tracker, and optionally a risk in the ISMS register
  (link:category-isms.adoc#_the_bridge_to_samm[ISMS, the bridge to SAMM]).
* *Model versions*: an assessment keeps the model version it was taken with. A comparison across model versions maps
  practices by id and marks questions that changed.

== Links to the Other Categories

* A maintained threat model is direct evidence for the SAMM practice _Threat Assessment_ (business function
  _Design_); the assessment links to the threat models of the services in its scope
  (link:category-threat-models.adoc[Threat Models]).
* A released assessment is evidence for the secure-development controls of ISO 27001 (Annex A 8.25 ff.) by a reference
  to its tag.
* An ISMS product, verinice for example, refers to a released assessment by its release tag; the application delivers
  nothing into it (link:../adr/0006-CISOs-Friend_complements_verinice_and_does_not_replace_it.adoc[ADR-0006]).
