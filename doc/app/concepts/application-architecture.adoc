An application that stores its data in the organisation's Git server owns no database: it has no schema migration, no
database backup and no connection pool to tune, and the Git server's backup covers every saved state. Only the drafts
are covered by the backup of the volume, which therefore needs one of its own. The consequence is that everything the
application knows at run time is either derived from Git or lost on restart. The architecture of CISOs-Friend keeps
the first property and limits the second. Its build, runtime and test structure follow API Sheriff, so a contributor
who knows one knows the other.

== Shape

One Quarkus application, compiled to a native image on Java 25, serves three surfaces from one process:

* the *REST API* `/api/v1` and one Server-Sent Events stream for the web app;
* the *MCP endpoint* for AI agents;
* the *static web app*, served same-origin from a resource JAR.

Behind the surfaces sits one layer of *application services*: categories, rights, step-up, deadlines, the first
login, the dashboards. Neither surface carries a rule of its own; the web app and the MCP server call the same services
with the same checks. Below the services sit the libraries of `git-document-repository`
(xref:../../concepts/module-structure.adoc[Module Structure]): the document modules on top of `git-core`, which reaches
the Git server through JGit over HTTPS. Commit signing and anchoring live in `git-store`, the person directory in
`git-directory`; the application only supplies their configuration and keys. Besides the Git server, the identity
provider, the KMS and, where one is configured, an RFC 3161 timestamp authority, the application calls no other
system: tickets and issues are referenced by the ids users or agents enter.

----
 browser ──► static web app (resource JAR, same origin)
 browser ──► /api/v1 + SSE ──┐
                             ├─► application services
 AI agent ─► /mcp ───────────┘    │
                                  │ calls, configuration
                                  └─► ┌─ git-document-repository ───────────┐
                                      │ git-forms, git-directory            │
                                      │ git-store (signing, anchoring)      │ ──► KMS or Vault
                                      │ git-core ──► JGit                   │ ──► Git server (HTTPS)
                                      └─────────────────────────────────────┘
----

The layering is planned to be enforced by ArchUnit rules in the test suite: no surface package reaches a library
directly, and no service package knows JGit.

== Maven Modules

The reactor mirrors API Sheriff (parent `de.cuioss:cui-quarkus-parent`, the Quarkus BOM and the Token Sheriff BOM
imported in the root `dependencyManagement`, `maven.compiler-plugin.release` = `25`).

[cols="1,3"]
|===
|Module |Content

|`cisos-friend`
|The Quarkus application: surfaces, services, configuration, boot validation. Carries the `native` profile.

|`categories`
|The category definitions as resources: per category a JSON Schema, an AsciiDoc template and a workflow; besides
them the catalog declarations and the threat-model recipes. Tested on its own against the library's form engine; no
Java code. The one behaviour a schema cannot express, the SAMM score, sits
behind the extension point `ScoreCalculator` in `cisos-friend`.

|`web-app`
|The Svelte single-page application, built by `frontend-maven-plugin` into a resource JAR
(xref:web-app.adoc[Web App]).

|`web-e2e`
|Playwright end-to-end tests and the axe-core accessibility audit against the built application.

|`integration-tests`
|Builds the native image and the distroless container, starts a compose stack, runs the failsafe `*IT` suites.

|`deployment`
|The compose sample (xref:deployment.adoc[Deployment]).
|===

A `benchmarks` module (k6, non-gating) follows once there is a performance question worth measuring.

== Configuration

Following API Sheriff, `application.properties` carries only Quarkus and runtime settings (ports, management
interface, logging). The policy of the application lives in its own YAML, `cisos-friend.yaml`, validated against a
bundled JSON Schema:

* the repositories with alias, remote, confidentiality, retention period and credential reference;
* one fetch interval for all repositories (`fetch.interval`);
* the mapping from identity-provider groups to rights per repository;
* the enabled categories, whose behaviour comes from their definitions alone; there is no second layer of overrides;
* the one step-up setting for every release;
* the person directory provider and the signing and anchor keys.

Deployment-bound values (URLs, secret paths) are placeholders `${NAME:-default}` resolved from the environment.
Secrets are never values in the YAML, only references to mounted files or to the KMS. At boot an ordered list of
validation rules checks the configuration and refuses to start on an error; the binary also validates a configuration
offline (`--validate-config <dir>`).

== Run-Time State

Everything the application holds in memory is either derived from Git or deliberately volatile:

[cols="1,2,2"]
|===
|State |Source |After a restart

|In-memory index (dashboards, deadlines, search)
|`main` and the open working branches of every repository
|Rebuilt at start

|Person directory (`git`)
|The person entries in the persons' repository (by default `directory`)
|Rebuilt at start

|Drafts
|`refs/drafts/<pseudonym>/…` in the local repository
|Survive only on a persistent volume

|Sessions of the web app
|Server-side, holding the user's tokens
|Lost; the user logs in again

|Reminders and notifications
|Computed from the index
|Recomputed
|===

The index is refreshed after every save and by a periodic fetch. Even
hundreds of SAMM assessments with about ninety answers each are a few megabytes; the index needs no database.

== One Instance

The application runs as *one instance* with a persistent volume for the repository directory. Drafts, sessions and the
in-memory index live in that one process; a second instance would need them shared, and nothing in the expected load
asks for it. The compare-and-swap of the library still keeps concurrent saves of many users safe.

== Native Image

The native image follows API Sheriff: Mandrel builder on the JDK 25 line, distroless runtime image, a health probe
built into the binary. JGit in a native image is the open risk of this architecture: its reflection, resource and
service-loader use has to be registered, and the transport is restricted to HTTPS, which avoids the SSH stack. The
first integration test builds the native image and runs a fetch, a save and a push against a local Git server before
anything else depends on it.

== Testing

* *Unit*: JUnit 5, `cui-test-generator` for all test data, EasyMock for test doubles, `cui-test-value-objects` for the
  contracts of value types, `cui-test-juli-logger` with `LogAsserts` for every `LogRecord`.
* *Inbound HTTP*: the adversarial generators of `cui-http-testing` (path, header, query attack databases) against the
  REST API and the MCP endpoint.
* *Architecture*: ArchUnit for the layering.
* *Integration*: the native container in a compose stack with Keycloak and a Gitea as Git server.
* *Web*: Vitest for the components, Playwright with axe-core for the flows.
