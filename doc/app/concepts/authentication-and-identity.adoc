Users of an ISMS or of an incident report need no account on the Git server, and the application does not require
one: a Git account per person only to fill in a form would be one more account to manage for each of them.
CISOs-Friend therefore authenticates people against the organisation's identity provider, pushes with a technical
user, and
writes the identity of the person into every commit in a form the application signs. This page is the application
side of that design: the login, the claims used, the first login, the rights, the Git credential and the step-up of
a release.

The library side (the trailer schema, the commit signature, step-up, the signature check) is described in
xref:../../concepts/identity-and-signing.adoc[Identity and Signing] and is not restated here.

== Login Through Token Sheriff

Token Sheriff provides authentication and the OAuth flows; this application takes it as given
(xref:../adr/0001-Authentication_is_delegated_to_Token_Sheriff_with_a_server-side_session_for_the_web_app.adoc[ADR-0001]).

* *Web app*: the server is a confidential client of the identity provider through `token-sheriff-client-quarkus`
  (authorization code with PKCE `S256` (https://www.rfc-editor.org/rfc/rfc7636[RFC 7636]), session-bound `state`
  and `nonce`, issuer check, optional pushed authorization requests (PAR,
  https://www.rfc-editor.org/rfc/rfc9126[RFC 9126])). The tokens stay
  in the server; the browser holds only cookies
  (xref:../specification/authentication.adoc#CIFR-AUTH-1[Authentication, CIFR-AUTH-1]). This is the
  backend-for-frontend shape Token Sheriff's client is built for; ADR-0001 explains why no API Sheriff BFF stands in
  front of the application.
* *MCP server*: AI agents present bearer access tokens. The server validates them with
  `token-sheriff-validation-quarkus` as an OAuth 2.1 resource server
  (https://www.ietf.org/archive/id/draft-ietf-oauth-v2-1-13.html[draft-ietf-oauth-v2-1-13], an Internet-Draft;
  xref:mcp-server.adoc[MCP Server]).
* *Logout* is RP-initiated
  (https://openid.net/specs/openid-connect-rpinitiated-1_0.html[OpenID Connect RP-Initiated Logout 1.0]) and revokes
  the tokens the server holds.

=== The Claims and What Becomes of Them

[cols="1,3"]
|===
|Claim |Use

|`iss`
|Which identity provider authenticated the user; written as `Actor-Issuer` trailer.

|`sub`
|Looked up in the person directory to find the user's pseudonym. *Never* written into the history: the trailer
carries the pseudonym (xref:../../concepts/data-protection.adoc[Data Protection]).

|`auth_time`, `acr`, `amr`
|Time and strength of the authentication; written as `Auth-Time` and `Auth-Context` trailers; checked before a
release (step-up).

|`name`, `email`
|Prefill the first-login form. The e-mail is not stored in the directory; it comes from the token when needed.

|`groups` (or roles)
|The source of access rights (see <<_rights>>) and a prefill for the team in the directory.

|`azp` / `client_id`
|For tokens presented to the MCP server: which agent client acts for the user; written to the audit log
(xref:mcp-server.adoc#_attribution_of_agent_actions[MCP Server, Attribution]).
|===

== First Login

The person directory is a library interface (xref:../../concepts/directory-and-catalogs.adoc[Directory and
Catalogs]); the application supplies the flow and the form. The first login below applies to the default directory
(`git`); with a directory for the organisation's own source the person already exists there, and there is no form.

The library flow (xref:../../concepts/directory-and-catalogs.adoc#_first_login[Directory and Catalogs, First Login])
applies unchanged; the application adds three things:

* *A gate.* Until the entry is saved, no other view opens and every other request is refused
  (xref:../specification/directory.adoc#CIFR-DIR-2[CIFR-DIR-2]).
* *The information duty* under GDPR Art. 13 (https://eur-lex.europa.eu/eli/reg/2016/679/oj[Regulation (EU)
  2016/679]): the form shows the operator's text on what the directory is for, what it holds, how long it is kept, and
  the legal basis agreed with the data protection officer.
* *The yearly confirmation* ("Is your team still right?") through the same form
  (xref:../specification/directory.adoc#CIFR-DIR-3[CIFR-DIR-3]).

[#_rights]
== Rights

Who may read and write a repository through the application comes from the identity provider through Token Sheriff:
a configured mapping from groups to repositories and to the actions *read*, *edit*, *approve* and *administer
catalogs*. In the first iteration no right is derived from the roles of the directory; who may approve is a matter of
access, not of the catalog of roles. A later iteration may derive rights from roles; then the assignment of such a role
needs a confirmation or comes from the identity provider.

The application enforces the rights for every request, in the web app and in the MCP server alike. The Git server sees
only the technical user.

== The Git Credential

The application reaches every Git server as one technical user, with a credential per repository (a deploy key or a
bot account token). The commit names the user's pseudonym as author and the bot as committer; the signed trailers carry
the identity. No user needs an account on the Git server, and nothing is pushed in a user's name.

The application merges releases itself, so the signed release commit names the releasing user; protecting `main` on
the Git server is an operating duty (xref:deployment.adoc#_operating_duties[Deployment, Operating Duties]).

[#_step_up]
== Step-Up

Every commit is signed by the application with the identity trailers. One rule decides where more is needed: *every
release requires step-up, and nothing else does*. Before a release the server checks `acr` or `amr` and `auth_time` of
the session against one global setting. If they do not meet it, the server re-drives authorization with `acr_values`
and `max_age` (https://www.rfc-editor.org/rfc/rfc9470[RFC 9470], provided by Token Sheriff's client) and verifies the
result before it writes the release; the
trailers record the fresh authentication. For the user that is one MFA confirmation per release; saves, the first-login
entry and changes of the own entry need none.

An AI agent can never release; it hands the release to the human (xref:mcp-server.adoc[MCP Server]). A document that
needs a qualified electronic signature is signed outside the application.
