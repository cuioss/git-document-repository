= ADR-0012: Directory roles are names only in the first iteration

// adr-metadata
// summary: Roles in the directory describe responsibility and contact; no right is derived from them, so assignments are valid at once without a pending state or confirmation.
// tags: directory, roles, authorization

// supersedes:
// end-adr-metadata

== Status

Proposed

== Decision

Users enter their own team and role on first login. A self-chosen role that grants a right is a privilege escalation.
The question is what a role means.

*The decision:* in the first iteration a role is a name. It describes who is responsible or the contact for
something. No right and no approval depends on it. Hence an assignment is valid at once, without a pending state and
without a confirmation. Roles and teams come from catalogs; free text is not allowed.

See xref:../concepts/directory-and-catalogs.adoc#_scope_of_the_first_iteration[Directory and Catalogs, Scope of the
First Iteration].

== Alternatives rejected

=== Rights derived from roles from the start

*Rejected because* a self-chosen role would grant rights. Preventing that needs a confirmation workflow, which the
first iteration does not need.

=== Roles only from the identity provider

*Rejected because* many identity providers deliver no usable groups. Where they do, the groups prefill the form.

== Consequences

=== Properties of the design

* No pending state and no confirmation workflow.
* Access stays a matter of the identity provider and the application.

=== Accepted costs

* Approvals cannot be restricted by directory role.

=== When this is revisited

When approvals are tied to roles. Assignments of such roles then need a confirmation at signature level 2, or come from
the identity provider.
