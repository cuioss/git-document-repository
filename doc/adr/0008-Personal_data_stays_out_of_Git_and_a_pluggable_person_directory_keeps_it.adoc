== Status

Accepted

== Decision

Git keeps every old version of every file, and the GDPR demands that personal data can be erased. Commits and
documents name persons: as authors, assessors, approvers or affected persons. The question is where the personal data
live so that they can be erased without rewriting the history, and how much machinery that needs.

*The decision:* what must be erasable never enters Git.

* *Git holds pseudonyms and stable ids only.* Commits name the author by pseudonym (`p-<random>`); documents refer to
  persons by pseudonym and to responsibilities by role and team (`role:…`, `team:…`). The catalogs of roles, teams,
  systems, services and external parties hold no personal data and stay in Git.
* *A person directory keeps the rest*, behind the service interface `PersonDirectory` of `git-store`: the mapping of
  an identity-provider issuer and `sub` to a pseudonym, the person's name and memberships (pairs of team and role), the
  resolution of a role in a team to persons, and the erasure. Providers are found through `ServiceLoader`; exactly one
  is active.
* *The default provider `local`* (`git-directory`) keeps one plain file per person on the application's volume,
  outside every repository, never versioned and never pushed. The pseudonym is random. Erasure deletes the file;
  where a statutory retention duty applies, the entry is restricted until the date the operator sets and deleted then.
  The erasure is recorded in the directory's repository by pseudonym and date, never by person.
* *Providers for the operator's own sources* (for example the identity provider's user directory, SCIM or LDAP) keep
  the personal data where the operator already keeps them; the operator erases them there.
* *Documents carry no personal data* beyond pseudonyms. Details of affected or involved persons stay in the system
  that handles the case, such as the ticket system, referenced by id. There is no encrypted field type.
* *Retention per repository* stays: a repository whose retention period ended is deleted as a whole.

See xref:../concepts/data-protection.adoc[Data Protection].

== Alternatives rejected

=== An encrypted keyring in Git with erasure by key rotation

The mapping and the person entries lie in Git, encrypted with a data key per person and retention class; the keyring
of data keys is encrypted with a versioned key-encryption key (KEK) held outside Git. Erasure re-encrypts the keyring
with a new KEK and destroys the old one, which makes every old version in the history unreadable (crypto-shredding).
Personal fields in documents use the same data keys.

*Rejected because* it needs a module of its own, an encryption library, a versioned KEK whose old versions must
vanish from every backup, a strict order of rotate, push and destroy, and a keyring that is a hot spot for
compare-and-swap. And it leaves the ciphertext in the history for good: whether destroying the key counts as erasure is
not settled (EDPB Guidelines 02/2025, version 2.0, para. 51). Keeping the data out of Git avoids the question.

=== Personal data in Git in plain text

Names and memberships lie in the directory's repository like the catalogs.

*Rejected because* Git forgets nothing: an erased entry stays in the history, in every clone and every backup of the
Git server. Erasure would need a rewrite of the history.

=== Rewriting the history on erasure

Erasure rewrites every commit that contains the person's data.

*Rejected because* a rewrite breaks every clone, every signature and every anchor proof.

=== A pseudonym derived from the `sub` with a secret key

The pseudonym is a keyed hash of issuer and `sub`; no mapping is stored.

*Rejected as the default because* a single person cannot be erased: whoever holds the key and the `sub` recomputes the
pseudonym. A random pseudonym whose mapping is deleted cannot be recomputed. An operator's provider may still choose a
derived pseudonym when its source is where erasure happens.

=== A database for the person directory

The directory lives in a database beside Git.

*Rejected as the default because* it brings back provisioning, backup and access control of a further store. The
local files need nothing beyond the volume the application has anyway; an operator who wants a central store plugs in
a provider for it.

== Consequences

=== Properties of the design

* No encryption, no KEK and no key rotation; erasure is a deletion, effective at once.
* References keep working after an erasure: the pseudonym stays in the history and resolves to "former member".
* An operator with an existing user directory keeps the personal data and its erasure where they already are.

=== Accepted costs

* The `local` directory is as durable as the volume: the operator backs it up and lets the backups expire within the
  erasure period. A lost volume loses the mappings; a returning user then gets a new pseudonym, and the old one resolves
  to "former member".
* The pseudonym in the history stays personal data while anything can still link it to the person: the mapping, its
  backups, and logs that pair a pseudonym with a login. Their expiry belongs in the operator's erasure concept.
* Documents cannot hold personal details; a report that needs them refers to the system that holds them.
* One instance owns the `local` directory; several instances need a provider with a shared source.

=== When this is revisited

When a document kind must hold personal details itself, or when several instances must share the directory without an
operator's source.
