== Status

Accepted

== Decision

Git's hash chain is only as trustworthy as the people who can force-push. The index and a mirror must follow every
save without a second transaction. A proof that a state existed at a time can come from the operator's own key or
from an external authority; only the external one is independent of the operator, and it is a further service the
operator has to run or buy. The question is how the store follows every save, and how it anchors the history without
making an external service a requirement.

*The decision:*

* An *outbox* walks the new commits of every branch a consumer subscribes to. It runs after a reference update the
  store performs (local mode), after a successful push (remote mode), and after a fetch that moves a subscribed branch.
  The last trigger covers a merge the Git server performs into protected `main`; a webhook or the periodic fetch
  brings it. The walk is idempotent by commit hash and keeps its progress per consumer and branch in a reference
  (`refs/meta/outbox/<consumer>/<branch>`, the branch name escaped: first every `%` as `%25`, then every `/` as
  `%2F`), so it resumes after a failure. The progress references are never pushed. The index and an optional mirror
  to a second Git server are its consumers.
* *Anchoring is pluggable.* `git-store` defines the service interface `AnchorProvider`: obtain a proof for an object
  id, and verify a stored proof. Providers are found through `ServiceLoader` and are active only when the consumer
  names them in its configuration; without one the store anchors nothing.
* *What is anchored* is decided by `git-store`, the same for every provider:
** the commit of every release tag, right after the tag exists;
** a *checkpoint* at most once per configured interval (default one day), and only when a pushed reference changed
   since the previous one. A checkpoint is a commit whose tree lists every pushed reference with its object id; its
   parent is the previous checkpoint, and it is tagged `refs/tags/checkpoints/<n>`. Anchoring a checkpoint proves
   every commit reachable from the references it lists, and every earlier checkpoint.
* *Two providers ship with the libraries:*
** `signed` (`git-signing`), an own timestamp on a best-effort basis: a statement of object id, time, sequence number
   and the hash of the provider's previous proof, signed with an anchor key of its own, never the commit-signing key.
   It refuses to sign when its clock is behind its previous proof, and it writes every proof as a log record, so the
   operator's log pipeline keeps a copy outside Git. It needs no service beyond the key source the signing already
   uses.
** `rfc3161` (`git-timestamp`), the variant with an external timestamp authority, for organisations that need a proof
   independent of their own operation.
* The proofs are stored as notes on the anchored commit under `refs/notes/anchors/<provider>`, so they travel with
  the repository. In remote mode they are pushed right after they are written; a failed push keeps the subject
  pending, and the retry pushes the stored proof instead of requesting a new one.

See xref:../concepts/evidence-and-companion-stores.adoc[Evidence and Companion Stores].

== Alternatives rejected

=== An external timestamp authority as the only anchor

Every deployment anchors its history with RFC 3161 tokens from a timestamp authority it has to name.

*Rejected because* it adds an external service, and in many networks an exception for outbound traffic, to every
deployment, also to those for which a proof by their own key is enough. It stays available as the provider `rfc3161`.

=== An anchor for every commit of `main`

Every new commit of `main` is anchored on its own.

*Rejected because* with an external authority it makes one call per commit, which a qualified timestamp service
charges for, and ties the pace of saving to that service. A checkpoint proves every commit it reaches; releases, the
states an auditor asks for, are still anchored one by one.

=== The commit signature as the own timestamp

The signed committer time of each commit serves as its timestamp; no further proof is written.

*Rejected because* the commit-signing key signs whatever time the signing host claims, and whoever holds that key can
sign a back-dated commit. A separate anchor key, a monotonic chain of proofs and a copy in the log pipeline make a
back-dated proof detectable; a commit signature alone does not.

=== RFC 3161 built into the store

`git-store` obtains RFC 3161 tokens itself.

*Rejected because* it would carry the client library into every consumer of `git-store`, and an anchor of another kind
would need a change of the store.

=== A copy of all commits in a second store

The store copies every commit into a second store as evidence beside the repository.

*Rejected because* a copy under the control of the same operator adds no independent proof: whoever can force-push can
also rewrite the copy.

=== Public transparency logs (Sigstore/Rekor)

Every new commit is recorded in a transparency log such as the public Rekor instance of Sigstore.

*Rejected as a provider shipped with the libraries because* the entries of a public log are public, and internal
compliance data must not leave the organisation. A self-hosted log keeps the entries internal, but its operator is
then no third party independent of the repository's operator.

=== WORM storage as the default

The history is written to write-once storage that refuses any later change.

*Rejected as the default because* it requires infrastructure many operators lack. It fits the service interface as a
later provider where it exists.

=== Proofs in a database

The proofs are kept in a database beside the repository.

*Rejected because* the proof would not travel with the repository.

== Consequences

=== Properties of the design

* A deployment anchors its history without an external service; one that needs an independent proof adds `rfc3161`,
  and both can be active at once.
* The proof travels with the repository and is verifiable without the application.
* A later compromise of the commit-signing key devalues only the commits not reached by a release or checkpoint
  anchored before the compromise.

=== Accepted costs

* A `signed` proof is not independent of the operator who holds the anchor key and the clock, and it is no qualified
  electronic timestamp. Its value rests on the separation of the anchor key from the Git administration and on the
  copy in the log pipeline.
* Between two checkpoints a commit that is no release is proven only by the next checkpoint: its existence is proven
  at the time of that checkpoint, not at its own commit time.
* With `rfc3161` the timestamp authority is a dependency at run time; the store retries when it is unreachable and
  never fails a save for it.
* A proof shows existence; it cannot restore a removed state. Notes and checkpoint tags in the repository can be
  removed together with the history by whoever can rewrite it; detecting that needs the log copy, a mirror or an
  archive under another responsibility.

=== When this is revisited

When a qualified timestamp service becomes mandatory, when a provider needs subjects other than releases and
checkpoints, or when the checkpoint interval proves too coarse for an audit.
