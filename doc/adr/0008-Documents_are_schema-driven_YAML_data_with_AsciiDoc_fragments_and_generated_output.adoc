== Status

Accepted

== Decision

Every kind of document the store serves has the same shape: a form, structured data, free text, review, approval,
deadlines and links, and in most kinds a readable output. The question is whether each kind is code or configuration,
and what is the
truth.

*The decision:*

* A kind of document is configuration: a JSON Schema, a template (optional for a numbered kind), a workflow and a
  repository.
* Structured data are YAML with deterministic serialisation.
* Free text is written as AsciiDoc fragments.
* Where the kind has a template, the readable AsciiDoc output is generated by it and committed as evidence; a check
  against the data runs without the application. It is never the truth.

See xref:../concepts/schema-driven-documents.adoc[Schema-Driven Documents].

== Alternatives rejected

=== AsciiDoc as the single source

The document is one AsciiDoc file that the form reads and writes.

*Rejected because* a form cannot reliably load hand-edited AsciiDoc. Mandatory fields and deadlines need structured
data.

=== Code per kind of document

Each kind of document is a module with its own classes for form, validation and output.

*Rejected because* the kinds share one shape. Code per kind multiplies effort and drifts apart.

=== JSON as the data format

Structured data are stored as JSON instead of YAML.

*Rejected because* YAML writes a mapping one key per line, without JSON's braces and commas, and multi-line text as
a block scalar in which every line break is kept, so a line-based diff in a review shows the changed field and the
changed line of text (link:https://yaml.org/spec/1.2.2/[YAML 1.2.2], 2.3 Scalars and 8.1.2 Literal Style). JSON Schema
validates any data that maps onto its data model of null, boolean, object with string keys, array, number and string
(link:https://json-schema.org/draft/2020-12/json-schema-core[JSON Schema 2020-12 Core], 4.2.1 Instance Data Model).
YAML 1.2 is a superset of JSON but goes beyond that model with aliases, non-string keys and further tags such as
`!!binary`; the data are restricted to YAML within the JSON data model, so JSON Schema validates them.

== Consequences

=== Properties of the design

* A new kind of document needs no new code.
* The schema is plain JSON Schema, usable by a validator outside the application that supports its dialect. Such a
  validator does not check link fields: it does not know the custom format `gdr-link`, which a dialect such as JSON
  Schema 2020-12 collects as an annotation unless the format-assertion vocabulary is in use
  (link:https://json-schema.org/draft/2020-12/json-schema-validation[JSON Schema 2020-12 Validation], 7.2), and only
  the application resolves link targets.

=== Accepted costs

* Content that does not fit structured fields with free text gains nothing from the layer.
* A kind of document without a template has no readable output beyond its YAML data.
* The template engine is an open question of
  xref:../concepts/schema-driven-documents.adoc#_open_questions[Schema-Driven Documents]; the JSON Schema dialect is
  decided: Draft 2020-12 (owner's decision, 2026-11-21; xref:../specification/git-forms.adoc#GDR-FORMS-2[GDR-FORMS-2]).

=== When this is revisited

When a kind of document needs behaviour the workflow configuration cannot express.
