== Status

Accepted

== Decision

The document store has several aspects: storage, forms, encryption, signing, timestamps and a directory. Some bring
third-party libraries. The question is how the code is cut into artifacts.

*The decision:* one repository, one Maven reactor, released together. Every aspect is a module of its own and is
consumed separately:

* `git-core`, `git-worktrees`, `git-testing` -- the JGit level;
* `git-store` -- drafts, saving, index, outbox;
* `git-forms` -- schema-driven documents;
* `git-signing`, `git-timestamp`, `git-directory` -- optional aspects.

Each module carries its own third-party dependencies. A consumer of `git-core` alone pulls none of the dependencies of
the modules above it. The dependency graph is in xref:../concepts/module-structure.adoc[Module Structure].

== Alternatives rejected

=== One module to start, split later

All aspects start in one module, which is split once the code grows.

*Rejected because* three forces would split it later at a higher price: the foundation shared with
other clients of Git repositories, optional dependencies that become mandatory in one module, and a layering that
one module does not enforce.

=== One repository per module

Every module lives in a repository of its own with its own release.

*Rejected because* the modules change together while the store is young. Separate repositories would need a release
per change and version alignment across them.

=== The application's kinds of documents as modules

Modules per kind of document (assessments, reports, registers).

*Rejected because* the kinds are configuration of `git-forms`, not code. No module of this repository knows a term of
a domain.

== Consequences

=== Properties of the design

* Module boundaries enforce the layering.
* Consumers take only what they need.

=== Accepted costs

* More POMs and `module-info.java` files to maintain.
* All modules share one version, even when only one changed.

=== When this is revisited

When a module needs a release cadence of its own.
