== Status

Accepted

== Decision

Some approvals need a statement stronger than "the application confirms the authenticated user". The user should
approve with a key the server does not hold, without a Git account or a GPG key. The question is how such an approval is
bound to a state of the repository.

*The decision:* the application passes a fresh, single-use challenge to WebAuthn: the SHA-256 over the commit id and a
random nonce issued for this one approval. The commit id alone would be predictable and the same for every attempt, so
a stored assertion could be replayed. The user's authenticator signs the challenge after user verification. The
application verifies the assertion with the registered public key and stores it, together with the nonce, as an entry
of `kind` `passkey` in the note on the commit under `refs/notes/approvals`, so any verifier can recompute the
challenge from the commit id. It reads the note, appends its entry and writes the note back by compare-and-swap of the
notes reference, so the entry never replaces another approval
(xref:0006-The_application_signs_every_commit_and_records_the_user_claims_as_signed_trailers.adoc[ADR-0006]). The push
refspec carries `refs/notes/*`.

See xref:../concepts/identity-and-signing.adoc#_level_3_approval_with_a_passkey[Identity and Signing, Level 3].

== Alternatives rejected

=== The passkey signs the commit itself

The passkey signature is part of the approved commit, like a Git commit signature.

*Rejected because* the commit id presupposes the finished commit. A signature inside the commit cannot cover the id
it changes.

=== An approval commit with the assertion as content

The approval is a further commit on the branch whose content is the assertion.

*Rejected because* an approval commit changes the tip of the branch. The approval would then refer to a state that is
no longer the tip, and a second approval would need a third commit.

=== A qualified electronic signature for every approval

Every approval is a qualified electronic signature (level 4).

*Rejected as the default because* the effort per approval is high. Level 4 stays available where the law demands it.

== Consequences

=== Properties of the design

* The approval binds to exactly one state: the challenge covers the commit id, and the commit id covers content and
  history.
* A captured assertion cannot be replayed: each nonce is accepted once.
* The server never holds the user's private key.

=== Accepted costs

* It is not a qualified electronic signature under eIDAS (Regulation (EU) No 910/2014).
* The list of registered public keys must itself be versioned and signed.
* Synchronised passkeys bind the key to an account, not to one device.
* The flow has to be tried in a prototype first _(unverified)_.

=== When this is revisited

When the prototype shows that browsers or authenticators refuse the challenge format.
