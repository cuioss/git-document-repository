== Status

Proposed

== Decision

Git's hash chain is only as trustworthy as the people who can force-push. Index, journal and timestamps must follow
every save without a second transaction. The question is how the store anchors the history externally and stays
consistent with what it derives.

*The decision:*

* After every successful push an *outbox* walks the new commits. It is idempotent by commit hash and keeps its
  progress in a reference, so it resumes after a failure.
* `git-timestamp` is one consumer of the outbox. It obtains an RFC 3161 timestamp for every new state of `main` and
  stores the token as a note under `refs/notes/timestamps`.
* A mirror to a second Git server is an optional further consumer.

See xref:../concepts/evidence-and-companion-stores.adoc[Evidence and Companion Stores].

== Alternatives rejected

=== A copy of all commits in a second store

*Rejected because* Git already is an append-only, hash-chained store. A copy adds no independent proof.

=== Public transparency logs (Sigstore/Rekor)

*Rejected because* the entries are public. Internal compliance data must not leave the organisation.

=== WORM storage as the default

*Rejected as the default because* it requires infrastructure many operators lack. It stays an option where it exists.

=== Timestamps in a database

*Rejected because* the proof would not travel with the repository.

== Consequences

=== Properties of the design

* The proof travels with the repository and is verifiable without the application.
* A later compromise of the signing key devalues only commits after the compromise.

=== Accepted costs

* A timestamp authority is a dependency at run time; the outbox retries when it is unreachable.
* A timestamp proves existence; it cannot restore a removed state.

=== When this is revisited

When a qualified timestamp service becomes mandatory or when the authority's availability blocks saves.
