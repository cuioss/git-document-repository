== Status

Accepted

== Decision

Commits name a pseudonym, not a person. The mapping from pseudonym to person must exist and must be erasable. Git
keeps every old version of every file. The question is where the mapping lives without a further store.

*The decision:* envelope encryption in Git.

* Each pseudonym has its own data encryption key (DEK) per retention class, so data under a retention duty and
  erasable data never share a key. The personal entries and personal fields of that person are encrypted with the DEK
  of their retention class.
* `keys/keyring.enc` holds per pseudonym the DEKs, the identity-provider issuer and the `sub`; a `sub` is unique only
  within its issuer. The keyring is encrypted with the key-encryption key (KEK).
* The KEK lies outside Git, supplied from outside and versioned.
* Erasure removes the DEKs of the retention classes whose data must be erased (the whole entry when none is left);
  a class under a statutory retention duty keeps its DEK until the retention ends (restriction, § 35(3) BDSG). It then
  re-encrypts the keyring with KEK version n+1, records version n as pending destruction, and commits the keyring; in
  remote mode it pushes it. Only then does it destroy version n, and only after that succeeds does a further commit
  record the destruction. A failed commit or push destroys nothing; a pending version is destroyed by the next run or
  the next start.
* Erasures are batched, for example daily.

See xref:../concepts/data-protection.adoc#_an_encrypted_keyring_in_git[Data Protection, An Encrypted Keyring in Git].

== Alternatives rejected

=== A separate store for the mapping

The mapping from pseudonym to person lives in a database or a vault beside Git.

*Rejected because* it brings back the operating effort Git was meant to avoid: provisioning, backup, access control.

=== One fixed key for the keyring

The keyring is encrypted with one key that never changes; erasure only removes the entry.

*Rejected because* old versions of the keyring stay in the history. Whoever holds the fixed key decrypts yesterday's
version and has the erased person back.

=== Rewriting the history on erasure

Erasure rewrites every commit that contains the person's data.

*Rejected because* a rewrite breaks every clone, every signature and every timestamp.

=== One key per person without a keyring

Each person's key lies in the external key source, and erasure destroys that key.

*Rejected because* the store would need one external secret per person. The keyring reduces the external secrets to
one versioned KEK.

== Consequences

=== Properties of the design

* No further store: outside Git lies one secret.
* Pseudonymisation and crypto-shredding run on one technique.

=== Accepted costs

* Erasure is only as good as the destruction of the old KEK, backups included.
* Until the keyring is published and the old KEK destroyed, the erasure is incomplete and reported as such.
* An instance that holds the keyring in memory forgets an erased DEK only when it reloads the keyring, at the latest at
  its next fetch.
* The keyring is a hot spot for compare-and-swap.
* Whether KEK destruction counts as erasure is not settled; operators agree it with their data protection officer.

=== When this is revisited

When the keyring's compare-and-swap conflicts dominate, or when a regulator rules on crypto-shredding.
