= Git as the Persistence of Versioned Documents
:toc: left
:toclevels: 3
:toc-title: Table of Contents
:sectnums:
:source-highlighter: highlight.js

An application in which users maintain versioned documents usually ends up with a database, a versioning scheme
bolted onto it, an approval table and a backup concept of its own. The organisations this repository serves already
run all of that once: a maintained Git server with history, rights, reviews and backups. This concept explains why
the libraries of this repository use that Git server as the persistence, what they promise, and where the approach
stops.

Statements marked _(unverified)_ come from general knowledge and were not checked against a current source; they
need verification before a decision rests on them.

== The Problem

Every additional database brings operating effort: provisioning, backup, restore tests, upgrades, access control.
For an application whose content is hundreds to a few thousand structured documents, that effort dominates the
value of the store. The documents also need what a plain database does not give for free: a complete history with
diffs, a release that freezes a state, an approval that survives as evidence, and a format a person can read
without the application.

Development organisations already operate exactly such a store. GitHub, GitLab, Gitea or Bitbucket keep history,
enforce rights, review changes and are backed up. Reusing that server avoids the extra database.

== Assumptions

* *Server-based.* One application server manages the Git repositories. No client holds a clone.
* *Git is the persistence only.* Users never see Git; they see forms, documents and approvals.
* *A maintained Git server exists*, with backups, in the organisation that runs the application.
* *Authentication is given.* User login and the OAuth flows against the Git server come from Token Sheriff, a system
  of its own in a parallel repository. The libraries consume credentials; they run no login flow.

== The Structural Response

The libraries turn the Git server into a document store with a small set of primitives. Each primitive has a concept
of its own:

[cols="1,3"]
|===
|Primitive |Concept

|*No working trees.* A branch is a reference, not a working area. Documents are written as blobs, trees and commits
in memory; references move by compare-and-swap. Drafts are references per user; saving applies a draft as a squash
merge in core and, in remote mode, pushes the result. Local and remote repositories share one API.
|xref:storage-engine.adoc[The Storage Engine on Git]

|*Identity by signature.* A technical user pushes; the application signs every commit and records the claims of the
logged-in user as trailers. Approvals can be raised to MFA or a passkey signature. Pushing in the user's name stays
optional.
|xref:identity-and-signing.adoc[Identity and Signing]

|*Data protection without a further store.* The pseudonym mapping lies in Git in an encrypted keyring; erasure
rotates the key-encryption key and destroys the old one. Repositories are cut by confidentiality and retention class.
|xref:data-protection.adoc[Data Protection]

|*Evidence.* RFC 3161 timestamps stored as `git notes` anchor the history externally. Every other store beside Git is
either derived from it (the index) or lives in a system the organisation already runs.
|xref:evidence-and-companion-stores.adoc[Evidence and Companion Stores]

|*One shape for all documents.* A schema, YAML data with AsciiDoc free text, generated AsciiDoc output, review and
approval, deadlines and links. A kind of document becomes configuration of one generic layer.
|xref:schema-driven-documents.adoc[Schema-Driven Documents]

|*Master data.* A directory of persons (encrypted) and catalogs of roles, teams and services that every document
refers to by stable ids.
|xref:directory-and-catalogs.adoc[Directory and Catalogs]
|===

How these primitives are cut into Maven modules is described in xref:module-structure.adoc[Module Structure].

== Existing Solutions

No Java library known to this concept provides this shape: drafts per user, merge on save, local or remote by
configuration, and the same API for both. None of the candidates surveyed below does. Building blocks and reference
designs exist.

[cols="1,2,1"]
|===
|Candidate |What it is |Use

|JGit
|Git in pure Java. Builds commits without a working tree (`ObjectInserter`, in-core `DirCache`), merges in core,
updates references atomically; pluggable object storage (DFS, `InMemoryRepository`). `InMemoryRepository` lies in
the internal package `org.eclipse.jgit.internal.storage.dfs`, which the JGit bundle exports only to its own friend
bundles (checked in JGit 7.8.0); it carries no API stability promise, and `git-testing` builds on it.
|Foundation

|Gerrit NoteDb
|Gerrit keeps all review metadata in Git references and writes them with atomic multi-reference `BatchRefUpdate`.
|Architectural reference, not a library

|CrafterCMS
|A Java CMS on Git with two repositories per project: _Sandbox_ for drafts, _Published_ for released content,
optionally with a remote upstream.
|Functional reference, but a whole product

|Spring Cloud Config _(unverified)_
|Reads configuration from Git through JGit.
|Read-only, unsuitable

|Dolt, Irmin, Gollum, Decap CMS
|Git-like databases or Git-based content tools outside Java.
|Comparison only
|===

Gerrit and CrafterCMS apply the pattern in their own products. A reusable persistence library for it is not known
to this concept.

== Why a Library of Its Own

The applications that use this store hold domain logic: assessment models, report formats, registers. The Git layer
underneath is generic, and every domain needs it identically. Separating it has three effects:

* the domains stay free of JGit,
* the layer is testable on its own against an in-memory or local repository,
* further domains reuse it without copying it.

=== Scope

* *Repositories*: local or remote mode by configuration; a bare clone as disposable cache; a registry of several
  repositories (confidentiality and retention classes) with stable aliases.
* *Writing*: in-core commits (blob, tree, commit) without working trees; compare-and-swap reference updates with retry;
  in-core merge; deterministic file content through a codec interface.
* *Drafts and saving*: draft references per user and document; intermediate save; save as squash merge in core,
  compare-and-swap, fetch, push and re-apply on rejection; conflict results per path; expiry and garbage collection
  of drafts.
* *Identity*: author and committer per save; a credentials strategy per push (technical user or user token); commit
  trailers for approvals.
* *Reading*: snapshots of a reference or a commit (reporting dates), change history per path, diff of two states, an
  index interface the domain fills.
* *Post-commit processing*: an outbox over the new commits, idempotent by commit hash, with its progress kept in a
  reference; the hook for timestamps, mirror and index.
* *Notes*: reading and writing `git notes` for timestamps, approvals and other annotations.
* *Results instead of exceptions* for the expected outcomes (saved, conflict, rejected, credentials expired).

=== Not in Scope

* the user interface,
* the domain schemas (assessment models, threat model formats, report formats, register entities),
* the OAuth flows and the identity provider (Token Sheriff; the libraries only consume credentials),
* integrations with issue trackers and ticket systems.

The client of the timestamp authority lives in the optional module `git-timestamp`, not in `git-store`.

== Risks and Limits

* *Many concurrent writers on one branch cause retries.* For documents maintained by few people over days this is
  uncritical; a high-frequency write load is not a case for this store.
* *Several application instances* stay safe through compare-and-swap on push, but each in-memory index is only as
  fresh as its last fetch. Webhooks of the Git server shorten the gap.
* *A conflict in the same file* is detected per path. `git-forms` resolves it per field of the YAML structure where
  the changed fields differ; a real conflict goes to the user.
* *Removing data from the history stays expensive.* The rules of xref:data-protection.adoc[Data Protection] keep
  personal data out of the history instead.
* *The content API of the Git server* would be simpler than a clone, but binds to one vendor and runs into rate
  limits. A JGit clone works with any Git server.
* *JGit's LFS support is limited* _(unverified)_. Evidence files therefore stay links, not blobs.

[CAUTION]
====
Git replaces no document management system an auditor already knows. A process description of the control of
documented information has to be written once by the organisation that runs the application. The libraries provide
the mechanisms; they do not certify them.
====
