= Git as the Persistence of Versioned Documents
:toc: left
:toclevels: 3
:toc-title: Table of Contents
:sectnums:
:source-highlighter: highlight.js

An application in which users maintain versioned documents usually ends up with a database, a versioning scheme
bolted onto it, an approval table and a backup concept of its own. The organisations this repository serves already
run all of that once: a maintained Git server with history, rights, reviews and backups. This concept explains why
the libraries of this repository use that Git server as the persistence, what they promise, and where the approach
stops.

== The Problem

Every additional database brings operating effort: provisioning, backup, restore tests, upgrades, access control.
For an application whose content is hundreds to a few thousand structured documents, that effort is the same as for
a large store, while the data stay small. The documents also need what a plain database does not give for free: a
complete history with diffs, a release that freezes a state, an approval that survives as evidence, and a format a
person can read without the application.

Development organisations already operate a store that gives these. A Git server such as GitHub, GitLab, Gitea or
Forgejo keeps the history of every change and grants rights per repository (see
xref:data-protection.adoc#_repositories_per_confidentiality_and_retention_class[Data Protection, Repositories per
Confidentiality and Retention Class]). The organisation already has such a server, with backups (see the assumptions
below); reusing it avoids the extra database.

== Assumptions

* *Server-based.* One application server manages the Git repositories. No client holds a clone.
* *Git is the persistence only.* Users never see Git; they see forms, documents and approvals.
* *A maintained Git server exists*, with backups, in the organisation that runs the application.
* *Authentication is given.* User login runs in the application against the identity provider, with the token
  libraries of https://github.com/cuioss/TokenSheriff[Token Sheriff], which live in a repository of their own. The
  libraries of this repository consume the user's claims and the technical user's credential; they run no login flow.

== The Structural Response

The libraries turn the Git server into a document store with a small set of primitives. Each primitive has a concept
of its own:

[cols="1,3"]
|===
|Primitive |Concept

|*No working trees.* A branch is a reference, not a working area. Documents are written as blobs, trees and commits
in memory; references move by compare-and-swap. Drafts are references per user; saving applies a draft as a squash
merge in core and pushes the result to the repository's remote.
|xref:storage-engine.adoc[The Storage Engine on Git]

|*Identity by signature.* Only a technical user talks to Git; the application signs every commit and records the
claims of the logged-in user as trailers. Every approval requires an MFA authentication no older than a configured
maximum age (step-up).
|xref:identity-and-signing.adoc[Identity and Signing]

|*Data protection by pseudonyms.* Commits and documents name persons only by pseudonym; names lie in one place, the
pluggable person directory, by default as entries in a repository, or in the operator's own source. Repositories are
cut by confidentiality and retention class.
|xref:data-protection.adoc[Data Protection]

|*Evidence.* Releases and periodic checkpoints are anchored through a pluggable provider (an own signed timestamp or
RFC 3161 timestamps), the proofs stored as `git notes`. Every other store beside Git is either derived from it (the
index) or lives in a system the organisation already runs.
|xref:evidence-and-companion-stores.adoc[Evidence and Companion Stores]

|*One shape for all documents.* A schema, YAML data with AsciiDoc free text, generated AsciiDoc output, review and
approval, deadlines and links. A kind of document becomes configuration of one generic layer.
|xref:schema-driven-documents.adoc[Schema-Driven Documents]

|*Master data.* A directory of persons under pseudonyms, catalogs of roles and teams, and the catalogs an application
declares (for example of its services), which every document refers to by stable ids.
|xref:directory-and-catalogs.adoc[Directory and Catalogs]
|===

How these primitives are cut into Maven modules is described in xref:module-structure.adoc[Module Structure].

== Existing Solutions

No Java library known to this concept provides this shape: drafts per user and merge on save, in memory, against any
Git server. Building blocks and reference designs exist:

[cols="1,2,1"]
|===
|Candidate |What it is |Use

|JGit
|Git in pure Java. Builds commits without a working tree (`ObjectInserter`, in-core `DirCache`), merges in core,
updates references atomically; pluggable object storage (DFS, `InMemoryRepository`). `InMemoryRepository` lies in
the internal package `org.eclipse.jgit.internal.storage.dfs`, which the JGit bundle exports only to its own friend
bundles
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/META-INF/MANIFEST.MF[`MANIFEST.MF`,
`x-friends`], JGit 7.8.0); it carries no API stability promise, and `git-testing` builds on it.
|Foundation

|Gerrit NoteDb
|Gerrit keeps all review metadata in Git references and writes them with atomic multi-reference `BatchRefUpdate`.
|Architectural reference, not a library

|CrafterCMS
|A Java CMS on Git with two repositories per project: _Sandbox_ for drafts, _Published_ for released content,
optionally with a remote upstream.
|Functional reference, but a whole product

|Spring Cloud Config
|Reads configuration from Git through JGit: the Config Server clones the repository and "never makes changes to the
'remote' repository"
(https://docs.spring.io/spring-cloud-config/reference/server/environment-repository/git-backend.html[Git Backend]).
|Read-only, unsuitable

|Dolt, Irmin, Gollum, Decap CMS
|Outside Java: Dolt (Go) and Irmin (OCaml) are databases that follow the design of Git; Gollum (Ruby) is a wiki and
Decap CMS (JavaScript) a content management system, both on Git
(https://github.com/dolthub/dolt[Dolt], https://github.com/mirage/irmin[Irmin],
https://github.com/gollum/gollum[Gollum],
https://github.com/decaporg/decap-cms[Decap CMS]).
|Comparison only
|===

Gerrit and CrafterCMS apply the pattern inside their own products, not as a reusable library.

== Why a Library of Its Own

The applications that use this store hold domain logic: assessment models, report formats, registers. The Git layer
underneath is generic, and every domain needs it identically. Separating it has three effects:

* the domains stay free of JGit,
* the layer is testable on its own against an in-memory or local repository,
* further domains reuse it without copying it.

=== Scope

* *Repositories*: a remote per repository and a bare clone as disposable cache; a registry of several repositories
  (confidentiality and retention classes) with stable aliases.
* *Writing*: in-core commits (blob, tree, commit) without working trees; compare-and-swap reference updates with retry;
  in-core merge; deterministic file content through a codec interface.
* *Drafts and saving*: draft references per user and document; intermediate save; save as squash merge in core,
  fetch, push with lease and re-apply on rejection; conflict results per path; expiry and garbage collection of
  drafts.
* *Identity*: author and committer per save; the technical user's credential for every push; the application's
  signature and the identity trailers on every commit.
* *Reading*: snapshots of a reference or a commit (reporting dates), change history per path, diff of two states, an
  index interface the domain fills.
* *Post-commit listeners*: in-process callbacks for the new commits, the hook for the index.
* *Anchoring*: releases and periodic checkpoints anchored through a provider interface, the proofs as notes. The own
  timestamp is part of `git-store`; the client of an RFC 3161 timestamp authority lives in the optional module
  `git-timestamp`.
* *Results instead of exceptions* for the expected outcomes (saved, conflict, rejected, unreachable, credentials
  expired).

=== Not in Scope

* the user interface,
* the domain schemas (assessment models, threat model formats, report formats, register entities),
* the OAuth flows (Token Sheriff, in the application) and the identity provider; the libraries only consume
  credentials,
* integrations with issue trackers and ticket systems.

== Risks and Limits

* *Many concurrent writers on one branch cause retries.* For documents maintained by few people over days this is
  uncritical; a high-frequency write load is not a case for this store.
* *One application instance* serves a repository: the drafts live in its clone. Changes made on the Git server
  itself reach the index with the next periodic fetch.
* *A conflict in the same file* is detected per path and goes to the user; one file per independently edited part
  keeps such conflicts rare.
* *Removing data from the history stays expensive.* The rules of xref:data-protection.adoc[Data Protection] keep
  personal data out of the history instead.
* *The content API of the Git server* would be simpler than a clone, but binds to one vendor and counts against its
  rate limits; a JGit clone works with any Git server
  (xref:../adr/0002-Every_repository_has_a_remote_and_the_local_bare_clone_is_a_disposable_cache.adoc[ADR-0002]).
* *JGit's LFS support works through a working tree.* It is the separate bundle `org.eclipse.jgit.lfs`, which uses
  Gson: a clean filter that turns content into a pointer file when it is added, a smudge filter that restores it on
  checkout, and a pre-push hook that uploads the media files
  (link:https://github.com/eclipse-jgit/jgit/tree/v7.8.0.202609011348-r/org.eclipse.jgit.lfs/src/org/eclipse/jgit/lfs[`org.eclipse.jgit.lfs`, JGit 7.8.0]).
  The in-core write path passes through none of them, so the store would have to write the pointer files and upload
  the objects itself. Evidence files therefore stay links, not blobs.

[CAUTION]
====
Git replaces no document management system an auditor already knows. A process description of the control of
documented information has to be written once by the organisation that runs the application. The libraries provide
the mechanisms; they do not certify them.
====
