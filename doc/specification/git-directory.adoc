= git-document-repository: `git-directory`
:toc: left
:toclevels: 2
:toc-title: Table of Contents
:source-highlighter: highlight.js

`git-directory` (module `de.cuioss.git.document.directory`, not yet created, optional) keeps the catalogs in Git and
provides the default person directory `git` of `git-store` (xref:git-store.adoc#GDR-STORE-19[GDR-STORE-19]). It
depends on `git-forms`: catalog entries and person entries are schema-driven documents; person entries are saved
directly on `main`, without a release workflow. Rationale: xref:../concepts/directory-and-catalogs.adoc[Directory and
Catalogs].

[#GDR-DIR-1]
== GDR-DIR-1: Catalogs

* The module must keep the catalogs of roles (`role:`) and teams (`team:`) with stable ids; an application must be
  able to add catalogs of its own by configuration (file, id prefix, schema).
* An entry must be retired (`retired: true`), never deleted.

[cols="1,2"]
|===
|Catalog |File

|roles |`catalog/roles.yaml` (list)
|teams |`catalog/teams.yaml` (list; optional `parent`)
|declared by the application |as configured, a list file or one file per entry
|===

Common fields: `id` (required, immutable, without the prefix: `payments` is referenced as `team:payments`), `name`
(required), `description`, `retired` (default `false`). On which branch a catalog change is saved, and whether it
passes a release, is an open question of
xref:../concepts/directory-and-catalogs.adoc#_open_questions[Directory and Catalogs].

[#GDR-DIR-2]
== GDR-DIR-2: Person Directory in Git

* The module must provide the person directory `git`, the default provider.
* A person entry must be the file `persons/<pseudonym>.yaml` in `directory.persons.repository` (a repository alias,
  default the directory's repository).
* A bound entry must hold the subject hash, the name, the memberships (pairs of team and role), the date `since` and
  the date of the last confirmation `confirmed`, and no further field unless the operator extends the schema; an
  unbound entry (<<GDR-DIR-7>>) holds the same without subject hash and `confirmed`.
* The subject hash must be the SHA-256 over the UTF-8 bytes of the issuer, a line feed and the `sub`, in lowercase
  hex; the entry must hold neither issuer nor `sub`, and `sub` must never be written to a repository. The issuer is
  not personal and appears in the `Actor-Issuer` trailer of every save
  (xref:git-store.adoc#GDR-STORE-13[GDR-STORE-13]).
* A new pseudonym must be `p-` followed by 26 characters of Crockford base32 (5 bits per character, digits and
  letters without `I`, `L`, `O` and `U`; link:https://www.crockford.com/base32.html[Douglas Crockford, Base 32]) over
  128 random bits from `SecureRandom`, never derived from issuer or `sub`.

At start and after every fetch that moves `main` of the persons' repository the provider reads the entries into
memory, indexed by subject hash and by pseudonym.

[#GDR-DIR-3]
== GDR-DIR-3: First Login

* For an issuer and `sub` without a bound entry the module must create a pseudonym, hold it in memory only, and
  report entry required with a prefill (`name` from the token, memberships from identity-provider groups where
  mapped).
* For entered memberships the module must list the binding candidates: the unbound entries (<<GDR-DIR-7>>) that hold
  at least one of them.
* Saving the first entry must take the caller's choice: *create*, a new entry under the pseudonym held in memory, or
  *bind*, naming a binding candidate. Binding must write the subject hash, the entered name and memberships and
  `confirmed` into that entry in one commit and keep its pseudonym; the pseudonym held in memory is dropped. A bind to
  an entry that is bound or holds none of the entered memberships must be refused with the outcome not bindable.
* Saving must be a save on `main` of the persons' repository, without review or release; the entry must take effect
  with that save, so that the next resolution of the pseudonym returns it.

A first login interrupted before the entry is saved leaves nothing in Git; the next login creates a new pseudonym,
and nothing refers to the old one, because no save happened under it. The binding rests on the user's statement; see
xref:../concepts/directory-and-catalogs.adoc#_first_login[Directory and Catalogs, First Login].

[#GDR-DIR-4]
== GDR-DIR-4: Reference Resolution

* The module must resolve `<catalog>:<id>` references of every configured catalog to their entries, retired ones
  included, and a role in a team to the pseudonyms holding it.
* A pseudonym must resolve to its entry from the active person directory, or to a former-member marker with the
  memberships recorded at the erasure (<<GDR-DIR-6>>) when it was erased.

[#GDR-DIR-5]
== GDR-DIR-5: Periodic Confirmation

* A confirmation interval (`directory.confirmation-interval`, ISO 8601 period; absent disables it) must be
  configurable.
* The module must list the bound person entries whose `confirmed` (or `since`) date is older than the interval;
  confirming sets `confirmed` to today.

[#GDR-DIR-6]
== GDR-DIR-6: Erasure

* Erasure must delete the person's entry in one commit on `main` that also appends an item with the fields
  `pseudonym`, `date` (ISO 8601 calendar date) and `memberships` (the pairs of team and role the entry held, empty
  when it held none) to the list in `erasures.yaml` of the same repository, and names the erased person only by
  pseudonym; the pseudonym must then resolve to a former member with those memberships.
* Erasure must never rewrite the history.

[source,yaml]
----
# erasures.yaml: one item per erased pseudonym, no further field
- pseudonym: p-3ZQ4M1V9K2D8R3T6X0B5N7HJCA
  date: 2026-11-17
  memberships:
    - team: team:payments
      role: role:security-champion
----

The erasure commit is a save of the administrator who erases, with that administrator's trailers
(xref:git-store.adoc#GDR-STORE-13[GDR-STORE-13]). The history of the repository keeps
the earlier versions of the entry; see xref:../concepts/data-protection.adoc#_erasing_a_person[Data Protection,
Erasing a Person].

[#GDR-DIR-7]
== GDR-DIR-7: Prefilled Entries

* The module must save an unbound entry: a person entry without subject hash and without `confirmed`, under a new
  pseudonym (<<GDR-DIR-2>>), as a save on `main` of the persons' repository by an administrator.
* An unbound entry must resolve like a bound one (<<GDR-DIR-4>>) and may be referenced by documents; its pseudonym
  must never be the author of a save.
* An unbound entry must become bound only by a first login that binds it (<<GDR-DIR-3>>).

[source,yaml]
----
# persons/<pseudonym>.yaml, prefilled: no subject-hash, no confirmed
name: Erika Example
memberships:
  - team: team:payments
    role: role:security-champion
since: 2026-11-17
----
