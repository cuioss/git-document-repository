== Overview

_See Requirement link:../Requirements.adoc#GDR-GEN-1[GDR-GEN-1: Module Layering and Dependency Isolation]_

*Status:* PLANNED

`git-directory` (module `de.cuioss.git.document.directory`, not yet created, optional) keeps the catalogs in Git and
provides the default person directory `local` of `git-store` (see xref:git-store.adoc#_person_directory[git-store,
Person Directory]). It depends on `git-forms`. Catalog entries are schema-driven documents in the directory's
repository; person entries are validated against a person schema like them but kept outside every repository (Local
Person Directory). Rationale: xref:../concepts/directory-and-catalogs.adoc[Directory and Catalogs].

== Catalogs

_See Requirement link:../Requirements.adoc#GDR-DIR-1[GDR-DIR-1: Catalogs]_

*Status:* PLANNED

[cols="1,2,1"]
|===
|Catalog |File |Id prefix

|roles |`catalog/roles.yaml` (list) |`role:`
|teams |`catalog/teams.yaml` (list; optional `parent`) |`team:`
|services |`catalog/services/<id>.yaml` (one file per entry) |`service:`
|systems |`catalog/systems.yaml` (list) |`system:`
|external parties |`catalog/external.yaml` (list) |`external:`
|===

Common fields: `id` (required, immutable; without the prefix, for example `payments`, referenced as `team:payments`),
`name` (required), `description`, `retired` (boolean, default `false`). A service carries `lifecycle` as well;
`lifecycle: retired` and `retired: true` are set together. Further catalogs are declared in configuration with file,
id prefix and schema.

== Service Catalog

_See Requirement link:../Requirements.adoc#GDR-DIR-2[GDR-DIR-2: Service Catalog]_

*Status:* PLANNED

[cols="1,1,2"]
|===
|Field |Required |Semantics

|`system` |no |`system:<id>`, the product above (an entry of the system catalog)
|`lifecycle` |yes |`planned`, `active`, `deprecated`, `retired`
|`owner.team`, `owner.role` |yes |references into the team and role catalogs
|`repositories` |no |list of repository URLs
|`dependsOn` |no |`service:` or `external:` references
|`protection-needs` |yes |`confidentiality`, `integrity`, `availability`: `normal`, `high`, `very-high`
|`data-classes` |no |list of names
|===

`dependsOn` keeps the spelling of Backstage, from which it is taken; the other fields are written in kebab-case.

`effectiveProtectionNeeds(service)` = per dimension the maximum over the service and every service reachable through
`dependsOn`, transitively; a cycle is reported as the cycle outcome naming the services on it.

== Local Person Directory

_See Requirements link:../Requirements.adoc#GDR-DIR-3[GDR-DIR-3: Local Person Directory],
link:../Requirements.adoc#GDR-DIR-4[GDR-DIR-4: First Login],
link:../Requirements.adoc#GDR-DIR-8[GDR-DIR-8: Erasure and Restriction]_

*Status:* PLANNED

The provider `local` of `PersonDirectory`, active when `directory.persons.provider` is `local` (the default).

* Storage: `directory.persons.path` (required for `local`), a directory on the application's persistent volume outside
  every repository. One file per person, `<pseudonym>.yaml`, written atomically (write to a temporary file, then
  rename); file mode `0600`. Fields, validated against the person schema: `pseudonym`, `issuer`, `sub`, `name`
  (required), `memberships` (list of `{team, role}`), `since` (date), `confirmed` (date of the last confirmation),
  `restricted-until` (date, set only by a restriction). Additional fields need an explicit schema extension by the
  operator.
* At start the provider reads every file into memory: an index by (issuer, `sub`) and by pseudonym, and the
  memberships for `holders`. Only one instance may use a path.
* Pseudonym: `p-` followed by 26 characters of Crockford base32 over 128 random bits from `SecureRandom`; never
  derived from issuer or `sub`.

`login(claims)`:

* known (issuer, `sub`) with a saved entry → the pseudonym and the entry;
* known (issuer, `sub`) without a saved entry (an interrupted first login) → the pseudonym and the outcome
  entry-required with a prefill, as below;
* unknown (issuer, `sub`) → a new pseudonym, a file holding only pseudonym, issuer and `sub`, and the outcome
  entry-required with a prefill (`name` from the token, memberships from IdP groups where mapped).

`saveEntry(pseudonym, entry)` validates against the person schema and writes the file; the entry is valid at once.

`erase(pseudonym, restrictUntil)`:

* without `restrictUntil`: deletes the file, then writes the erasure record;
* with `restrictUntil`: sets `restricted-until`; until that date the entry resolves as a former member and serves only
  `restricted(pseudonym)`, the call through which the operator answers a statutory request. A daily task deletes the
  entries whose date has passed and writes their erasure records.
* Erasure record: a system commit on `main` of the directory's repository (pushed with the technical user's
  credentials, see xref:git-store.adoc#_identity_per_save[git-store, Identity per Save]) that changes
  `erasures.yaml`, one line per erasure: pseudonym and date. It names no person.

Backups of `directory.persons.path` belong to the operator, whose erasure concept sets their expiry.

== Import from Backstage

_See Requirement link:../Requirements.adoc#GDR-DIR-6[GDR-DIR-6: Import from Backstage]_

*Status:* PLANNED

Backstage kinds and fields as described in its descriptor format
(https://backstage.io/docs/features/software-catalog/descriptor-format):

[cols="1,2"]
|===
|Backstage kind |Catalog

|`Component` |service (`spec.system` → `system`, `spec.lifecycle` → `lifecycle`, `spec.owner` → `owner.team`,
`spec.dependsOn` → `dependsOn`)
|`System` |system
|`Group` |team (`spec.parent` → `parent`)
|===

* References: Backstage entity references are translated by kind: a `Group` → `team:<name>`, a `System` →
  `system:<name>`, a `Component` → `service:<name>`. Only the namespace `default` is imported; a reference to
  another namespace or to another kind (a `User` as owner, a `Resource` in `spec.dependsOn`) is reported and left
  out.
* Lifecycle: Backstage accepts any value; its well-known values are `experimental`, `production` and `deprecated`.
  The mapping is configuration (`directory.backstage.lifecycle`); the default maps `production` → `active` and
  `deprecated` → `deprecated`. An unmapped value is reported and leaves the field unchanged.
* Matching: the import matches by `metadata.name`; it updates changed fields and never deletes (a vanished entry is
  reported). Fields Backstage does not know (`owner.role`, `protection-needs`, `data-classes`) are kept.
* New entries: a new service needs `owner.role`, `protection-needs` and a mapped `lifecycle`, which Backstage does not
  supply. The import takes `owner.role` and `protection-needs` from the configured defaults
  (`directory.backstage.defaults`); without them, or with an unmapped lifecycle, the new component is reported and
  not created.

== Periodic Confirmation

_See Requirement link:../Requirements.adoc#GDR-DIR-7[GDR-DIR-7: Periodic Confirmation]_

*Status:* PLANNED

`directory.confirmation-interval` (ISO 8601 period, optional; absent disables). `dueForConfirmation(instant)` lists
pseudonyms whose `confirmed` (or `since`) is older than the interval. Confirming sets `confirmed` to today.
