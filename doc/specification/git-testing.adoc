= git-document-repository: `git-testing`
:toc: left
:toclevels: 2
:toc-title: Table of Contents
:source-highlighter: highlight.js

`git-testing` (module `de.cuioss.git.document.testing`) provides test support for consumers of the reactor. It is a
regular artifact consumed in test scope and depends on no other module of the reactor. It declares JGit,
`cui-test-generator` and JUnit Jupiter in compile scope, so that a consumer that adds `git-testing` in test scope
receives them with it; the third-party dependencies are listed in xref:general.adoc#GDR-GEN-1[GDR-GEN-1]. Rationale:
xref:../concepts/module-structure.adoc#_the_foundation_modules[Module Structure, The Foundation Modules].

[#GDR-TEST-1]
== GDR-TEST-1: Repository Fixtures

* The module must provide JUnit 5 fixtures for a local repository, an in-memory repository and a local remote for
  fetch and push tests.
* The fixtures must work without network access and must clean up every directory they create.

Each fixture is a JUnit Jupiter `ParameterResolver` registered by a qualifier annotation. A fixture is selected by
its annotation on the test parameter, never by the parameter type alone, so the fixtures combine in one test: a test
method can take a `@LocalRepository Repository`, an `@InMemory Repository` and a `@Remote LocalRemote` side by side,
and each annotated parameter receives a fixture of its own. The annotation registers its extension, so no
`@ExtendWith` is needed.

[cols="1,1,1,3"]
|===
|Fixture |Annotation |Extension |Contract

|local repository |`@LocalRepository` |`LocalRepositoryExtension` |A bare repository in a temporary directory, created
per annotated parameter, closed and deleted when the test ends, also when it fails
|in-memory repository |`@InMemory` |`InMemoryRepositoryExtension` |A JGit in-memory repository of JGit's DFS
(distributed file system) storage
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/internal/storage/dfs/package-info.java[JGit 7.8.0, package `dfs`]: "Distributed file system based repository storage").
JGit's `org.eclipse.jgit.internal.storage.dfs.InMemoryRepository` lives in that internal package: the fixture wraps
it and exposes only `org.eclipse.jgit.lib.Repository`, so no consumer depends on the internal type. The fixture
initialises the repository with `create(true)`, so it starts like the bare fixtures, with `HEAD` linked to the unborn
branch `refs/heads/master`
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/internal/storage/dfs/DfsRepository.java[JGit 7.8.0, `DfsRepository#create`]).
No directory is created; the repository is closed when the test ends
|local remote |`@Remote` |`LocalRemoteExtension` |A `LocalRemote` record holding a second bare repository and the
`file:` URL (`URIish`) it is reached by, which the remote policy local only admits; closed and deleted when the test
ends, also when it fails
|===

A constructor parameter of a test class with the default per-method lifecycle receives a fixture per test method; a
test class with `Lifecycle.PER_CLASS` has one instance, so its constructor fixture lives for the whole class and is
cleaned up when the class has run (see <<_tests_of_the_module>>). The directory of a local repository or remote is
deleted also when closing its repository fails; when both fail, the closing failure is the one thrown and the deletion
failure is added to it as a suppressed exception, so the first failure is never replaced by the second.

[#GDR-TEST-2]
== GDR-TEST-2: Credential Generator

* The module must provide a `cui-test-generator` generator for transport credentials.

* The generated values must be random and never real secrets.

`GitCredentialGenerator` produces `GitCredential` values for tests. `GitCredential` is a record holding a user name
and a token as plain values; the token is a `char[]`, so a caller can clear it after use. Equality compares the user
name and the content of the token, and `toString()` masks the token and never renders it. `GitGenerators` registers
the generators of the module in one place: the factory method `GitGenerators.credentials()` returns a fresh
`GitCredentialGenerator` and is the method that
`@TypeGeneratorFactorySource(factoryClass = GitGenerators.class, factoryMethod = "credentials")` names.

[#GDR-TEST-3]
== GDR-TEST-3: Distinct Text Generator

* The module must provide a `cui-test-generator` generator whose values are distinct by construction and occur in no
  text a test did not put them in.

A test that asserts a generated value absent from a text the code under test produced, or that relies on two generated
values differing, must not draw the value from a letters-only generator (`Generators.letterStrings`,
`Generators.nonEmptyStrings`): a short value of letters occurs by chance in free text, and two such values can be equal.
Three plans met a flake of that kind, a letters-only value found in an unrelated message and two generated fixture
contents that were equal. Such a test draws its values from `DistinctTextGenerator` instead, through
`GitGenerators.distinctTexts()` (`factoryMethod = "distinctTexts"`).

Every value is the fixed marker `gdrdistinct` (`DistinctTextGenerator.MARKER`), the number of the value within its
generator instance, the separator `-` and three to eight generated lower-case letters, for example
`gdrdistinct7-kqp`. The marker makes a value found in a text one the test put there; the number makes two values of one
instance differ; the separator keeps one value from being the start of another (value 1 is no prefix of value 12). A
value consists of lower-case letters, digits and `-`, so it is a valid reference name component and file name and
never reads as a commit id. The numbering belongs to the instance, so a test draws the values it compares from one
instance; the generator is safe for use by several threads.

[#GDR-TEST-4]
== GDR-TEST-4: Hermetic Git Configuration

* The module must provide a fixture that isolates a test from the git configuration of the host.

JGit reads the user, system and JGit configuration through the JVM-wide `SystemReader`, so a setting of the machine
that runs the build, such as `http.followRedirects` in `~/.gitconfig`, reaches every repository a test opens. The
annotation `@HermeticGitConfiguration`, on a test class or method, registers `HermeticGitConfigurationExtension`, which
installs before each test method a `SystemReader.Delegate` that delegates to the reader installed before but opens an
empty user, system and JGit configuration, backed by no file, and restores the previous reader after the test method
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/util/SystemReader.java[JGit
7.8.0 `SystemReader`]). The configuration of a repository itself is read as before. `@BeforeEach` and `@AfterEach`
methods run inside the isolation, `@BeforeAll` and `@AfterAll` methods outside it. The previous reader is restored only
when the extension stored one: Jupiter calls its `afterEach` also when an earlier `BeforeEachCallback` failed and its
own `beforeEach` never ran, and `SystemReader.setInstance(null)` would then install JGit's default reader in place of
one an enclosing fixture installed, so without a stored reader the installed one is left as it is.

Usage limit: the `SystemReader` is one per JVM, so the fixture must not be used by tests that run concurrently in one
JVM; a concurrent test would read the empty configuration as well, and the reader one test restores could end the
isolation of another. The reactor configures no concurrent run: neither a `junit.jupiter.execution.parallel` setting
nor a Surefire `parallel` or `forkCount` setting is declared in this repository.

== Module Descriptor and Module Path

The module descriptor `git-testing/src/main/java/module-info.java` requires the third-party modules transitively, so
that a consumer module that reads `de.cuioss.git.document.testing` also reads the types of its signatures:

[source,java]
----
requires transitive org.eclipse.jgit;
requires transitive de.cuioss.test.generator;
requires transitive org.junit.jupiter.api;
requires static org.jspecify;
----

JGit and `cui-test-generator` ship no module descriptor; both are automatic modules, named by the
`Automatic-Module-Name` entry of their manifests. Checked with `jar --describe-module` of JDK 25.0.3:
`org.eclipse.jgit-7.8.0.202609011348-r.jar` describes as `org.eclipse.jgit@7.8.0.202609011348-r automatic`, and
`cui-test-generator-3.0.2.jar` as `de.cuioss.test.generator@3.0.2 automatic`. A JAR becomes an automatic module only
on the module path; on the class path its types belong to the unnamed module, and a named module cannot declare a
dependence on the unnamed module
(link:https://openjdk.org/jeps/261[JEP 261: Module System], sections _Automatic modules_ and _The unnamed module_).
`requires transitive org.eclipse.jgit` therefore resolves only where the JGit JAR is on the module path.

The module's own tests run on the class path: `git-testing/pom.xml` sets the Surefire parameter `useModulePath` to
`false`. Surefire's default is `true`, which runs the tests on the module path when the project has a module
descriptor and the JVM is module-aware
(link:https://maven.apache.org/surefire/maven-surefire-plugin/test-mojo.html#useModulePath[Surefire, `test` goal,
parameter `useModulePath`]). The reason is recorded in the pom: `junit-jupiter-api` is a compile dependency of this
module, so on the module path Surefire places `org.junit.platform.commons` in a named module while its launcher stays
in the unnamed module, and the launcher fails with `IllegalAccessError` on `org.junit.platform.commons.util`. On the
class path every class of the module belongs to the unnamed module (JEP 261, section _The unnamed module_), so *no test
of this module exercises the descriptor*: neither the `requires` directives above nor the `exports` directive are
resolved by any test run of `git-testing`.

A consumer module such as `git-core` that tests on the module path has to do two things, because `git-testing` is a
test-scope dependency and so appears in no `requires` directive of the consumer's descriptor:

* Make its tests read `de.cuioss.git.document.testing` in its test configuration, with the option
  `--add-reads <consumer-module>=de.cuioss.git.document.testing`, together with
  `--add-modules de.cuioss.git.document.testing` where nothing else resolves the module (the options: JEP 261,
  sections _Breaking encapsulation_ and _Root modules_), for example in Surefire's `argLine`.
* Keep the automatic modules JGit (`org.eclipse.jgit`) and `cui-test-generator` (`de.cuioss.test.generator`) on the
  module path. On the class path they are no modules at all, and the `requires transitive` directives of
  `de.cuioss.git.document.testing` fail to resolve (JEP 261, section _Automatic modules_).

The class-path workaround of `git-testing/pom.xml` applies to the consumer as well: the consumer receives
`junit-jupiter-api` through `git-testing` in the same way, so its tests on the module path are expected to fail with
the same `IllegalAccessError` and to need `useModulePath` set to `false`, unless the consumer's own run on the module
path shows otherwise. No consumer of the reactor tests against `git-testing` yet, so this expectation is not observed
in a consumer run.

== Tests of the Module

Two cleanup cases are covered by tests of their own. `PerClassLifecycleTest` takes all three fixtures under
`@TestInstance(PER_CLASS)`, as constructor and as method parameters, in one repeated test whose two invocations run
in method contexts of their own. It asserts that the constructor fixtures are shared by both invocations and cleaned
up when the class ends: the directories of the local repository and the remote are deleted then, and the in-memory
repository is closed exactly once then and not before. No directory shows that closing, so the test counts it on the
closing the resolver stored for the repository. The method-parameter fixtures stay per invocation: the second invocation asserts that the local repository
and the remote of the first are already deleted. The resolvers ask for the extension context of the test method when they resolve a constructor parameter
(`ExtensionContextScope.TEST_METHOD`); under the per-class lifecycle Jupiter hands them the context of the test class
instead, observed with junit-jupiter-api 6.1.3. For a per-class test class, "when the test ends" in
<<GDR-TEST-1>> therefore reads "when the test class ends" for a constructor fixture; no resolver change is needed,
because one instance serves every test of such a class.

`TemporaryDirectoriesTest` asserts that a tree holding a dangling symbolic link is deleted as a whole: JGit's
`FileUtils#delete` with `SKIP_MISSING` returns early only for a path its existence check reports missing, and that
check does not follow symbolic links
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/util/FileUtils.java[JGit
7.8.0, `FileUtils#delete` and `#exists`, which tests with `LinkOption.NOFOLLOW_LINKS`]); the test confirms it on
Linux. It is skipped only where the platform refuses to create a symbolic link.

=== Accepted Exceptions to EasyMock

The test approach names EasyMock for test doubles (xref:general.adoc#test-approach[Test Approach]), and the tests of
`git-testing` use it, in test scope, for the doubles of a repository: a class mock of JGit's `InMemoryRepository` that
expects exactly one `close()` (and throws a given failure from it), and, where the real repository must stay in use, a
partial mock whose `close()` is mocked and expected never to be called. The failure of
`InMemoryRepositoryExtension.initialise` is a mock whose `create(true)` throws. The following doubles remain
hand-written; each is an accepted exception, for the reason given:

[cols="1,3"]
|===
|Double |Reason

|`FailingListingFileSystem`
|A stateful NIO file system: one directory whose listing fails with a given exception, which records its own
deletion. `TemporaryDirectoriesTest` walks it through `TemporaryDirectories.delete`. With EasyMock the same behaviour
needs separate mocks for the `FileSystemProvider`, the `Path`, the `DirectoryStream` and its iterator, which is more
code and less clear.

|`UnreadableUserConfiguration`, `FailingPlatformQuery` (in `LocalRepositoryExtensionTest`)
|Both replace JGit's global `SystemReader` through `SystemReader.Delegate`. `FailingPlatformQuery` must stay silent
while `SystemReader.setInstance` queries the platform itself and fail only afterwards; a strict EasyMock mock could
express that only by pinning the number of platform queries JGit makes internally
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/util/SystemReader.java[JGit
7.8.0, `SystemReader#setInstance`, which initialises the new reader, and `#setPlatformChecker`, which asks
`isWindows()` and `isMacOS()`]), which would tie the test to JGit 7.8.0.

|`InMemoryClosingObserver`, `CountingClosing` (in `PerClassLifecycleTest`)
|A JUnit extension that, once the per-class instance exists, replaces the closing the in-memory resolver stored in the
class context with a record that counts its closings and delegates to the stored one. The resolver creates the
repository itself, so no mock can be handed to it, and the stored closing, `ClosingRepository`, is a record and so
cannot be subclassed. The observed object is the stored closing that Jupiter closes.

|`ReflectedParameter` (in `LocalRepositoryExtensionTest`)
|A record implementing JUnit's `ParameterContext` over a reflected method parameter, for calling an extension
directly. `ParameterContext` is an interface, so EasyMock could mock it; the record is kept because about ten call
sites build one from a reflected parameter and an index, and a record of three methods is shorter than the same
expectations repeated or hidden in a helper.
|===

`GitCredentialGeneratorTest` holds no test double.

EasyMock is declared in `git-testing` in test scope; the owner approved it on 2026-11-17 (xref:general.adoc#GDR-GEN-1[GDR-GEN-1]),
and its version is managed by `cui-java-parent`.
