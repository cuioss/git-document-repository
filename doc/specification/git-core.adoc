= git-document-repository: `git-core`
:toc: left
:toclevels: 2
:toc-title: Table of Contents
:source-highlighter: highlight.js

`git-core` is the JGit level of the reactor: module and package `de.cuioss.git.document.core`. It depends on no other
module of the reactor. Its third-party dependencies are JGit (`requires transitive org.eclipse.jgit`, because JGit
types such as `Repository`, `URIish`, `FS` and `CredentialsProvider` are part of its API), `cui-java-tools` for
`CuiLogger`, Lombok (scope `provided`, `requires static`) and `org.jspecify:jspecify` (`requires static`); see
xref:general.adoc#GDR-GEN-1[GDR-GEN-1]. The code is a plain copy of the repository part of `pm-provider-git`
(xref:../clients/pm-mcp-core.adoc#_what_moves_where[Client: `pm-mcp-core`, What Moves Where]).
<<GDR-CORE-1>>, <<GDR-CORE-2>>, <<GDR-CORE-3>>, <<GDR-CORE-7>>, <<GDR-CORE-8>> and <<GDR-CORE-11>> are implemented;
<<GDR-CORE-4>>, <<GDR-CORE-5>>, <<GDR-CORE-6>>, <<GDR-CORE-9>> and <<GDR-CORE-10>> are planned. The JGit APIs named
here are checked against JGit 7.8.0 (tag `v7.8.0.202609011348-r` of https://github.com/eclipse-jgit/jgit). Rationale:
xref:../concepts/module-structure.adoc#_the_foundation_modules[Module Structure, The Foundation Modules] and
xref:../concepts/storage-engine.adoc[Storage Engine].

[#GDR-CORE-1]
== GDR-CORE-1: Hardened Repository Access

* Every repository opened or created by the library must refuse the execution of Git hooks and the start of external
  processes.
* All operations must run in process; no `git` installation may be required.
* A refused capability must be reported as an outcome, not executed.

Every repository the operations open or create (also `init`, the bare clone and the cache repository) is built with
`RefusingFS`. It extends JGit's `org.eclipse.jgit.util.FS_POSIX` and overrides the hook and process methods of
`org.eclipse.jgit.util.FS` (among them `runHookIfPresent`, `runProcess`, `runInShell` and `execute`;
link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/util/FS.java[JGit 7.8.0 `FS`])
so that they throw `CapabilityRefusedException`. A hook that is not present is reported as not present, as JGit does,
so a repository without hooks works unchanged; the discovery of the `git` executable reports none, so JGit never runs
`git` to locate the system configuration.

`CapabilityRefusedException` is a public class of `git-core` that extends JGit's unchecked
`org.eclipse.jgit.api.errors.JGitInternalException`, so JGit propagates it unchanged through its callers of `FS`. Its
reason names the refused capability (`repository_hook` or `process_execution`); its message carries no secret.
`RepositoryOperations` maps it to the outcome `REFUSED_BY_POLICY` with the capability as detail.

[#GDR-CORE-2]
== GDR-CORE-2: Remote Policy

* The policy must have one of two values: an HTTPS origin, which admits only `https` URLs of that host and port, or
  local only, which admits only remotes without a host (a local path or a `file:` URL) and refuses every network
  remote.
* The policy must be checked before every fetch and every push; a remote that violates it must be refused without any
  network contact.

[#GDR-CORE-3]
== GDR-CORE-3: Bare Clone of a Remote

* Every repository must have a remote: an HTTPS URL or, on a single server, a local bare repository, as the remote
  policy admits.
* The library must work on a bare clone of that remote and clone it when it is missing.
* A new clone must restore every pushed state.

The operation is `cloneIfMissing`. An existing bare repository at the git directory is opened without contacting the
remote; a directory that holds anything else is `NOT_A_REPOSITORY`. Otherwise the URL is checked against the remote
policy (`REFUSED_BY_POLICY` without contact), a bare repository is initialised, and its remote `origin` is configured
and fetched. The fetch refspecs mirror the remote's branches, tags and notes into the clone:
`+refs/heads/*:refs/heads/*`, `+refs/tags/*:refs/tags/*` and `+refs/notes/*:refs/notes/*`. The push refspecs are
configuration supplied by the caller (for `git-store`: `refs/heads/*`, `refs/tags/*`, `refs/notes/*`). A clone that
could not be completed is removed; a transport failure is reported as in <<GDR-CORE-7>>.

[#GDR-CORE-4]
== GDR-CORE-4: In-Core Writing

* The library must create blobs, trees and commits from in-memory content without a working tree.
* Writing a commit must not create or change any file outside the object database and the references.
* Author, committer, message and parents of a commit must be set by the caller.

The new tree is built from the parent's tree in an in-core `DirCache` (`DirCache.read(ObjectReader, AnyObjectId)`,
`DirCache.writeTree(ObjectInserter)`), and blob, tree and commit are inserted through one `ObjectInserter`. An edit
sets a path to content or deletes it. The caller may pass a JGit `org.eclipse.jgit.lib.Signer` (since JGit 7.0), which
signs the commit before it is inserted; `git-core` signs nothing itself.

[#GDR-CORE-5]
== GDR-CORE-5: Compare-and-Swap Reference Update

* A reference update must succeed only when the reference still points to the expected old commit.
* When the reference moved, the library must re-apply the caller's operation on the new state and retry, up to a
  number of attempts the caller passes.
* After the last failed attempt the result must report a conflict outcome; the reference must be unchanged.
* A delete must never adopt a moved reference: when the reference no longer points to the expected old commit, the
  delete must report a conflict at once and leave the reference unchanged.

The caller supplies an *operation* (a function from the current tree to a list of edits), not a finished commit. Every
reference change sets the expected old id (`RefUpdate.setExpectedOldObjectId`; `ObjectId.zeroId()` for a reference
that must not exist yet). An update never sets the force flag: `NEW` and `FAST_FORWARD` are success. A delete
(compare-and-delete, used by the store for a draft reference) sets the expected old id and the force flag, because a
delete has no new value and `RefUpdate` returns `REJECTED` for it without the flag and `FORCED` with it; `FORCED` is
success for a delete. In both cases the expected-old check runs first, so a reference that moved yields `LOCK_FAILURE`
and is unchanged (`RefUpdate.updateImpl`,
link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/lib/RefUpdate.java[JGit 7.8.0 `RefUpdate`]).
For an update, `LOCK_FAILURE` (locked, or no longer the expected old id) re-applies the operation and retries. For a
delete, the library reads the reference after `LOCK_FAILURE`: if it still points to the expected old id, the reference
was only locked and the delete is retried with the same expected old id; if it moved, the delete ends with conflict, so
a newer draft is kept (xref:git-store.adoc#GDR-STORE-3[GDR-STORE-3], xref:git-store.adoc#GDR-STORE-7[GDR-STORE-7]).
`IO_FAILURE` is an exception; every other result is returned at once as rejected, the detail naming it.

[#GDR-CORE-6]
== GDR-CORE-6: In-Core Merge

* The library must merge two commits without a working tree, at path level only: a path changed by one side takes
  that side's entry; a path changed differently by both sides is a conflict; file contents are never merged.
* A merge with conflicts must report the conflicting paths and must not create a commit.

The merger is `MergeStrategy.SIMPLE_TWO_WAY_IN_CORE.newMerger(repo)` (class `StrategySimpleTwoWayInCore`, always in
core): a three-way merge over the merge base and both tips at the path level only, which reports a path modified by
both sides (content or file mode) as a conflict and never merges file contents
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/merge/StrategySimpleTwoWayInCore.java[JGit 7.8.0 `StrategySimpleTwoWayInCore`]).
`MergeStrategy.RECURSIVE` is not used: it merges file contents textually, which
xref:../adr/0001-Documents_are_written_in_core_without_working_trees_and_references_move_by_compare-and-swap.adoc[ADR-0001]
rejects. Success yields a tree id, from which the caller builds the merge commit. The merger reports no conflicting
paths, so on failure the library computes them itself with a tree walk over the merge base and both tips: every path
whose entry (object id or file mode) differs from the base on both sides and differs between the sides.

[#GDR-CORE-7]
== GDR-CORE-7: Fetch and Push with Credentials and Lease

* Credentials must be supplied per fetch or push by the caller; the library must not store them.
* A push must support a lease: it must be refused when the remote reference differs from the expected value.
* A rejected push, a refused lease, an unreachable remote and expired or invalid credentials must each be reported as
  a distinct outcome.

Credentials are a `@Nullable org.eclipse.jgit.transport.CredentialsProvider` per call, in `FetchInput`, `PushInput`
and `CloneInput`. The outcomes:

* `REJECTED`: the remote refuses the update (non-fast-forward, a protected branch or another refusal; JGit's
  `RemoteRefUpdate.Status` `REJECTED_NONFASTFORWARD`, `REJECTED_OTHER_REASON` or `REJECTED_NODELETE`);
* `LEASE_REFUSED`: the remote reference differs from the expected value (`REJECTED_REMOTE_CHANGED`);
* `CREDENTIALS_INVALID`: the remote refuses the authentication, HTTP 401 or 403, recognised by the wordings of JGit's
  `JGitText` and `TransportHttp` for it (`notAuthorized`, `noCredentialsProvider`, `authenticationNotSupported`,
  `serviceNotPermitted`;
  link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/resources/org/eclipse/jgit/internal/JGitText.properties[JGit
  7.8.0 `JGitText.properties`]);
* `UNREACHABLE`: every other transport failure;
* `REFUSED_BY_POLICY`: the remote's effective URL, after `insteadOf` rewriting, is outside the remote policy; nothing
  is sent.

A detail names the remote with a URL without user information and never carries a credential or a JGit message that
may carry one (xref:general.adoc#GDR-NFR-3[GDR-NFR-3]).

[#GDR-CORE-8]
== GDR-CORE-8: Cache Repository

* The library must fetch exactly one commit into a bare cache repository under the remote policy.
* It must read the content of one file at a given commit of the cache.
* A commit the remote does not serve must be reported as an outcome.

The operations are `initCache` (create or open a bare cache repository), `fetchCommit` and `readFile`. `fetchCommit`
fetches one commit by its full id from a URL the remote policy of the call admits, within a transport timeout, and
keeps it reachable under `refs/pinned/<id>`; a commit already in the cache is not fetched again. A commit the remote
does not serve is `UNSERVED`; a URL outside the policy or a process start is `REFUSED_BY_POLICY`; a remote that does
not answer is `UNREACHABLE`. `readFile` reads the raw blob of a path at a commit of the cache, without any filter;
a commit not in the cache or a path that is no regular file is `NOT_FOUND`.

[#GDR-CORE-9]
== GDR-CORE-9: Reading

* The library must read a snapshot of the tree of a reference, a tag or a commit.
* It must list the commits that changed a given path, newest first, with author, committer, time and message.
* It must compute the added, modified and deleted paths between two commits.

[#GDR-CORE-10]
== GDR-CORE-10: Git Notes

* The library must read and write notes on a commit under a caller-named notes reference (for example
  `refs/notes/anchors/rfc3161`).
* Writing a note must use the compare-and-swap of <<GDR-CORE-5>> on the notes reference.

Notes are read and written through JGit's `NoteMap` (`NoteMap.read`, `NoteMap.set`, `NoteMap.writeTree`). `git-core`
reserves no notes reference itself.

[#GDR-CORE-11]
== GDR-CORE-11: Identity of Commits and References

* The library must provide full and abbreviated commit ids and resolve branch, tag and remote-branch names.
* A name that resolves to more than one object must be reported as ambiguous, with the candidates in the detail.

`GitIdentity` holds the rules. A commit is passed and compared as its full 40-digit id. "Provide" means producing:
`abbreviate(Repository, AnyObjectId)` returns the shortest unique abbreviation through JGit's
`ObjectReader.abbreviate(AnyObjectId)`, for display only; an abbreviated id is never resolved as an identity, and an
operation given one reports `NOT_FOUND` with the detail `abbreviated commit id`. `branchRef`, `tagRef` and
`remoteBranchRef` return the full references `refs/heads/<name>`, `refs/tags/<name>` and
`refs/remotes/<remote>/<name>`; `resolution(Repository, String)` classifies a name. A name that matches two
references, or a reference and a full commit id, is `AMBIGUOUS`; `candidates(Repository, String)` lists the full
reference names, and the id when the name is a full commit id, and `log` puts them into the detail. A full commit id
that reaches another commit is `IDENTITY_MISMATCH`.
