= git-document-repository: `git-core`
:toc: left
:toclevels: 2
:toc-title: Table of Contents
:source-highlighter: highlight.js

`git-core` is the JGit level of the reactor: module and package `de.cuioss.git.document.core`, with the package
`de.cuioss.git.document.core.worktrees` for the linked working trees (<<working-trees>>). It depends on no other
module of the reactor. Its third-party dependencies are JGit (`requires transitive org.eclipse.jgit`, because JGit
types such as `Repository`, `URIish`, `FS` and `CredentialsProvider` are part of its API), `cui-java-tools` for
`CuiLogger`, Lombok (scope `provided`, `requires static`) and `org.jspecify:jspecify` (`requires static`); see
xref:general.adoc#GDR-GEN-1[GDR-GEN-1]. The code is a plain copy of the repository part of `pm-provider-git`
(xref:../clients/pm-mcp-core.adoc#_what_moves_where[Client: `pm-mcp-core`, What Moves Where]).
<<GDR-CORE-2>> to <<GDR-CORE-15>> are implemented. <<GDR-CORE-1>> is met except the one JVM-wide process start of
JGit's `SystemReader`, which `git-core` does not prevent by itself; installing `RefusingFS.systemReader` closes it and
is the recommended setup of an embedding application. The JGit APIs named here are checked against JGit 7.8.0 (tag `v7.8.0.202609011348-r` of https://github.com/eclipse-jgit/jgit). Rationale:
xref:../concepts/module-structure.adoc#_the_foundation_modules[Module Structure, The Foundation Modules] and
xref:../concepts/storage-engine.adoc[Storage Engine].

[#GDR-CORE-1]
== GDR-CORE-1: Hardened Repository Access

* Every repository opened or created by the library must refuse the execution of Git hooks and the start of external
  processes.
* All operations must run in process; no `git` installation may be required.
* A refused capability must be reported as an outcome, not executed.

Every repository the operations open or create (also `init`, the bare clone and the cache repository) is built with
`RefusingFS`. It extends JGit's `org.eclipse.jgit.util.FS_POSIX` and overrides the hook and process methods of
`org.eclipse.jgit.util.FS` (among them `runHookIfPresent`, `runProcess`, `runInShell` and `execute`;
link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/util/FS.java[JGit 7.8.0 `FS`])
so that they throw `CapabilityRefusedException`. A hook that is not present is reported as not present, as JGit does,
so a repository without hooks works unchanged; the discovery of the `git` executable reports none, so JGit never runs
`git` to locate the system configuration. Setting the execute permission of a file is done in process: JGit's
`FS_POSIX.setExecute(file, true)` reads the umask by running `sh -c umask` through `Runtime.exec`, outside every process
entry point of `FS`
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/util/FS_POSIX.java[JGit 7.8.0 `FS_POSIX`]),
so `RefusingFS` grants the owner the execute permission and the group and others exactly when they may read. A refusal
names the capability, never the refused command or its arguments.

One process start lies outside the repository's `FS`. JGit reads the user configuration, and with it the system
configuration, through the process-wide `SystemReader.getInstance()` whenever it constructs a `FileRepository` or runs
`InitCommand`; the default `SystemReader` locates the system configuration with `FS.DETECTED`, which runs
`git --version` and `git config --system` once per JVM
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/internal/storage/file/FileRepository.java[JGit 7.8.0 `FileRepository`],
link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/util/SystemReader.java[`SystemReader`],
link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/util/FS.java[`FS.discoverGitSystemConfig`]).
JGit 7.8.0 offers no configuration source per repository, and `SystemReader.setInstance` changes every JGit user of the
JVM, so the operations leave the process-wide `SystemReader` untouched and this process start is not prevented by
`git-core` itself. `RefusingFS.systemReader(SystemReader)` returns a reader that opens the configuration files through
a `RefusingFS`; an application that needs the guarantee for its whole JVM installs it before any JGit use. With it the
system configuration is skipped by design, because it cannot be located without running `git`, and the user and JGit
configuration are read as before, in process.

GDR-CORE-1 is therefore met with one limit: no operation starts a process through the repository's `FS`, and the
JVM-wide `SystemReader` process start is closed only when the embedding application installs the reader of
`RefusingFS.systemReader(SystemReader)` with `SystemReader.setInstance` at its start, before it constructs a
repository. That installation is the recommended setup of every embedding application; `git-core` does not perform it,
because it would change every other JGit user of the JVM.

`CapabilityRefusedException` is a public class of `git-core` that extends JGit's unchecked
`org.eclipse.jgit.api.errors.JGitInternalException`, so JGit propagates it unchanged through its callers of `FS`. Its
reason names the refused capability (`repository_hook` or `process_execution`); its message carries no secret.
`RepositoryOperations` maps it to the outcome `REFUSED_BY_POLICY` with the capability as detail.

The hooks and programs of a remote reached over the local transport are covered as well. JGit runs a native hook only
through `GitHook`, which calls `FS.runHookIfPresent`; its hooks are the client-side `pre-commit`, `commit-msg`,
`post-commit` and `pre-push`. `ReceivePack` runs Java hooks only, so a native `pre-receive` hook of a local remote is
never run by a push
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/hooks/GitHook.java[JGit
7.8.0 `GitHook`],
link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/transport/ReceivePack.java[`ReceivePack`]).
A configured `remote.<name>.receivepack` is never run either: `PushCommand` keeps its own receive-pack program, the
default `git-receive-pack`, and sets it on every transport it opens, which replaces the configured one
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/api/PushCommand.java#L71[JGit
7.8.0 `PushCommand`, line 71] and
link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/api/PushCommand.java#L145-L146[lines 145-146]),
so `TransportLocal` pushes through its in-process `ReceivePack`. A configured `remote.<name>.uploadpack` is used by a
fetch (`Transport.applyConfig`), and `TransportLocal.openFetch` would start any program other than `git-upload-pack`
through `FS.runInShell`
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/transport/Transport.java[JGit
7.8.0 `Transport`],
link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/transport/TransportLocal.java[`TransportLocal`]);
`RefusingFS` refuses that start, so the fetch ends `REFUSED_BY_POLICY` and nothing is fetched. The tests
`remotePreReceiveHookNeverRun`, `receivePackProgramNeverRun` and `uploadPackProgramRefused` of
`JGitRepositoryOperationsTest` cover the three cases.

[#GDR-CORE-2]
== GDR-CORE-2: Remote Policy

* The policy must have one of two values: an HTTPS origin, which admits only `https` URLs of that host and port, or
  local only, which admits only remotes without a host (a local path or a `file:` URL) and refuses every network
  remote.
* The policy must be checked before every fetch and every push; a remote that violates it must be refused without any
  network contact.

`RemotePolicy` validates its origin in the canonical constructor, so every construction path refuses an origin that
is no absolute `https` URI with a host. A port is either omitted, which means 443, or explicit within 1 to 65535; an
explicit port outside that range is refused on the origin and on the remote, because JGit's `URIish` keeps a parsed
port 0 but omits it when it formats the transport URL, so the request would go to 443
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/transport/URIish.java[JGit 7.8.0 `URIish`]).

The configured URLs are checked first, and then every transport a fetch, a push or the clone's fetch opens is checked
again before it connects, through its `TransportConfigCallback`: `FetchCommand` and `PushCommand` resolve the remote
name once more, and `FileRepository.getConfig()` reloads a configuration saved after the first check
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/internal/storage/file/FileRepository.java[JGit 7.8.0 `FileRepository`]),
so only the transport's own URL is the destination the command uses. The same check binds the transport of
`fetchCommit` to the policy of its call.

The policy also covers redirect targets. JGit's `TransportHttp` follows a redirect of the first request
(`http.followRedirects`, default `initial`) and its `isValidRedirect` accepts any host of the same scheme
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/transport/TransportHttp.java[JGit 7.8.0 `TransportHttp`],
link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/transport/HttpConfig.java[`HttpConfig`]),
so an admitted remote could send a request on to a host the policy refuses. Every HTTP transport the operations open
therefore creates each connection through a policy-checking `HttpConnectionFactory`, installed on that transport with
`TransportHttp.setHttpConnectionFactory`, so a redirect target is checked before any request reaches it. The
mechanism is scoped to these transports: the process-wide `HttpTransport.setConnectionFactory` is not touched, and
`http.followRedirects` in a repository or user configuration cannot re-enable a refused redirect, because the check
does not depend on it. A refused redirect is `REFUSED_BY_POLICY` with a detail that names the host only, and it is
logged with the `REMOTE_REFUSED` warning. A fetch does not recurse into submodules, which
`FetchCommand` would fetch on demand from their own remotes
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/api/FetchCommand.java[JGit 7.8.0 `FetchCommand`]).

`RedirectEndToEndTest` checks the refusal end to end against the CUI MockWebServer
(`de.cuioss.test:cui-test-mockwebserver-junit5`, test scope, approved by the owner; see
xref:general.adoc#GDR-GEN-1[GDR-GEN-1]) over HTTPS on the loopback interface. The server answers the first request
(`GET .../info/refs?service=git-upload-pack`) with a `302` to the same server under the host `127.0.0.1`, while the
policy admits `https://localhost:<port>` only. Both `fetchCommit` on a cache and `fetch` of a named remote end
`REFUSED_BY_POLICY` with the detail `redirect to 127.0.0.1 is outside the remote policy`, the server receives exactly
one request, and `REMOTE_REFUSED` is logged. The JGit transport accepts the certificate the extension generates
because the configuration of the test's own repository sets `http.sslVerify=false`; no process-wide TLS state is
changed. `refusedRedirectLogged` of `JGitRepositoryOperationsTest` checks that the log message names the host only,
without user information.

[#GDR-CORE-3]
== GDR-CORE-3: Bare Clone of a Remote

* Every repository must have a remote: an HTTPS URL or, on a single server, a local bare repository, as the remote
  policy admits.
* The library must work on a bare clone of that remote and clone it when it is missing.
* A new clone must restore every pushed state.

The operation is `cloneIfMissing`. An existing bare repository at the git directory is opened without contacting the
remote; a directory that holds anything else is `NOT_A_REPOSITORY`. Otherwise the URL is checked against the remote
policy (`REFUSED_BY_POLICY` without contact), a bare repository is initialised, and its remote `origin` is configured
and fetched. The fetch refspecs mirror the remote's branches, tags and notes into the clone:
`+refs/heads/*:refs/heads/*`, `+refs/tags/*:refs/tags/*` and `+refs/notes/*:refs/notes/*`. They are public as the
unmodifiable list `JGitRepositoryOperations.MIRROR_FETCH_REF_SPECS`, the one source of that set: a caller that prunes a
clone passes it to `fetch` explicitly, so the prune of <<GDR-CORE-7>> deletes only references below the mirrored
namespaces, whatever fetch refspecs the clone's configuration holds (JGit 7.8.0 `Transport.fetch` falls back to the
configured fetch refspecs only for an empty list, and `FetchProcess.deleteStaleTrackingRefs` deletes only references
matching the destination of a fetched refspec).

The stored origin carries no secret the caller passed in the URL: it is built from an allowlist of the URL's components,
scheme, host, port and path, as a URL is rendered for a detail (<<GDR-CORE-7>>), so neither user information nor query
data nor a fragment reaches the persistent configuration of the clone, and the clone fetches from that origin. JGit's
`URIish` keeps query data and a fragment in its path, so removing user name and password alone would store a token
passed in the query. The raw path is kept, so its escaping is unchanged. The credentials of a call come from its
`CredentialsProvider` only (<<GDR-CORE-7>>).

A local path without a scheme and without a host is stored as `URIish` parsed it. Its local-file pattern keeps the
whole value literally as the path, so `#`, `?` and `%` are part of a file name there: cutting the path at the first
`#` or `?`, or percent-decoding it as `URIish.setRawPath` does, would store and clone `/srv/source` for
`/srv/source#archive.git` and `/srv/my repo` for `/srv/my%20repo`. Such a path carries no user information, query data
or fragment that could hold a secret.

An explicit port 0 is `REFUSED_BY_POLICY` with the detail `not a URL` before anything is created: `URIish.setPort`
maps every value that is not positive to the default port, so the stored origin would name a port the caller did not
give, and the remote policy of <<GDR-CORE-2>>, which requires an explicit port within 1 to 65535, would admit it.

A URL that JGit parses as a local path although it starts like an authority, a scheme and `//` or `//` alone, is
`REFUSED_BY_POLICY` with the detail `not a URL` before anything is created: JGit's `URIish` matches its scheme pattern
`[a-z][a-z0-9+-]+://` in lower case only, so `HTTPS://user:secret@host/repo.git` falls through to its local-file
pattern and the whole string, user information included, becomes the path
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/transport/URIish.java[JGit
7.8.0 `URIish`]), where it cannot be told apart from the rest of the path. A remote policy that admits local
repositories would otherwise admit it and store it.

Accepted exception: an existing bare repository at the git directory is opened without comparing its `origin` with the
URL of the call. The clone is a disposable cache owned by its caller
(xref:../adr/0002-Every_repository_has_a_remote_and_the_local_bare_clone_is_a_disposable_cache.adoc[ADR-0002]), and the
caller that chose the git directory is the one that knows which remote it belongs to.

The push refspecs are configuration supplied by the caller (for `git-store`: `refs/heads/*`, `refs/tags/*`,
`refs/notes/*`). A source-only refspec, a wildcard included, pushes to the reference of the same name and is configured
as `<source>:<source>`; JGit's `new RefSpec("refs/heads/*")` rejects a source-only wildcard
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/transport/RefSpec.java[JGit 7.8.0 `RefSpec`]).
A clone restores exactly what it mirrors, so a push destination must lie below `refs/heads/`, `refs/tags/` or
`refs/notes/`, and it must be a valid reference name (a wildcard standing for a valid name part, so `refs/heads/x.lock`
is refused); a refspec with another destination (for example `refs/releases/*`), a deleting or a matching refspec
and one that is no refspec are `REFUSED_BY_POLICY` before anything is created. The mirrored namespaces are derived from
the fetch refspecs above, so the two cannot differ.

That rule covers the push refspecs the clone is configured with. An explicit `push` writes the reference its caller
names in `remoteRef`, on any repository, and is not checked against the mirrored namespaces: a push to another
namespace (for example `refs/releases/v1`) succeeds on a remote that accepts it, and a new clone does not restore that
reference. A caller that needs the guarantee for a reference pushes below the mirrored namespaces.

The clone is built in a private staging directory beside the git directory and published by one atomic move after
the fetch succeeded and every mirrored reference was written, so the git directory holds nothing, the empty directory
the caller prepared, or a complete clone, never a partial one. The move itself replaces the prepared empty directory
(POSIX `rename`) and never a non-empty one, so a failed move leaves the prepared directory as it was. Each attempt
removes only its own staging directory; an attempt that finds a clone published concurrently opens it, also when its
own move failed because of it. A clone that could not be completed leaves the git directory as it was; a transport
failure is reported as in <<GDR-CORE-7>>. The fetch of the clone runs with the transport timeout of <<GDR-CORE-7>>.
The tests `publishLosesRace` (a clone published concurrently is opened and the own staging directory removed) and
`mirroredRefsNotWritten` (a fetch that could not write a mirrored reference ends `FAILED`, nothing is published and the
staging directory is removed) of `JGitRepositoryOperationsTest` cover both branches.

Accepted exception: the staging directory is created by `Files.createTempDirectory`, which on a POSIX file system
creates it with the mode `rwx------`
(link:https://github.com/openjdk/jdk21u/blob/master/src/java.base/share/classes/java/nio/file/TempFileHelper.java[JDK 21
`TempFileHelper`]), and the atomic move publishes that directory as the git directory, so the clone is readable by its
owner only. A caller that serves the clone to another operating-system user adjusts its permissions itself.

[#GDR-CORE-4]
== GDR-CORE-4: In-Core Writing

* The library must create blobs, trees and commits from in-memory content without a working tree.
* Writing a commit must not create or change any file outside the object database and the references.
* Author, committer, message and parents of a commit must be set by the caller.

The writer is `InCoreWriter.write(Repository, List<String> parents, CommitMetadata, List<TreeEdit>)`. The new tree is
built from the first parent's tree in an in-core `DirCache` (`DirCache.read(ObjectReader, AnyObjectId)`, an empty
`DirCache.newInCore()` for a root commit, and `DirCache.writeTree(ObjectInserter)`;
link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/dircache/DirCache.java[JGit
7.8.0 `DirCache`]), and blobs, tree and commit are inserted through one `ObjectInserter`, flushed once after the
commit. A `TreeEdit` is either `TreeEdit.Put`, which sets a path to content with a `TreeEdit.Mode` (a regular file,
mode `100644`, unless the caller names an executable file, `100755`, or a symbolic link, `120000`), or
`TreeEdit.Delete`, which removes it. `CommitMetadata` carries author, committer, message and an optional
`CommitSigning`; the caller sets them all, and the parents are full commit ids of the repository.

Every path of the edits is checked before anything is written, with one strictness on every host: a JGit
`ObjectChecker` with `setSafeForWindows(true)` and `setSafeForMacOS(true)`, whatever the platform the library runs on
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/lib/ObjectChecker.java[JGit
7.8.0 `ObjectChecker`]). Besides what JGit refuses everywhere (an empty component, `.`, `..`, `.git` in any case and
`git~1`), it refuses a component ending in a dot or a space, a character Windows forbids, a Windows device name such as
`CON` or `aux.txt`, and a name HFS+ folds to `.git`. Owner decision: JGit's own check, `SystemReader.checkPath`, applies
the checks of the running platform only
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/util/SystemReader.java[JGit
7.8.0 `SystemReader`]), so a tree written on a Linux server could hold a path a client on Windows or macOS cannot check
out; one strictness for every host keeps every tree the library writes portable, at the cost of refusing on Linux a
name Linux would store. The edits are also checked against each other, compared after Unicode normalization to form
NFC and without case: two edits of the same path are refused (`edits: duplicate path`), and so are two edits of which
one names a directory of the other's path, such as `a` and `a/b` (`edits: overlapping path`), because JGit 7.8.0
`DirCacheEditor` keeps only one of them (`deleteOverlappingSubtree`) and the caller's other edit would be lost without
a word. The normalization makes the composed and the decomposed spelling of one name, such as `é.txt` as one code point
and as `e` with a combining accent, one path: both are distinct names to Git, but HFS+ stores names decomposed, so a
tree holding both cannot be checked out on it. The edit itself keeps the path as the caller spelled it.

With a `CommitSigning` (a JGit `org.eclipse.jgit.lib.Signer`, the signing key and a `CredentialsProvider`), the commit
is signed before it is inserted through
`Signer.signObject(Repository, GpgConfig, ObjectBuilder, PersonIdent, String, CredentialsProvider)`, with
`new GpgConfig(repository.getConfig())` and the committer of the metadata
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/lib/Signer.java[JGit
7.8.0 `Signer`], since JGit 7.0); `git-core` brings no signer of its own.

The writer creates objects only: it reads and writes no reference, so nothing outside the object database changes.
Moving a reference to the commit is <<GDR-CORE-5>>, which writes no reflog. The outcomes: `OK` with the full id of the
commit; `NOT_FOUND` when a parent is no full commit id or no commit of the repository, or an edit names an invalid, a
repeated or an overlapping path, the detail naming the field (`parents` or `edits`) and nothing being written; `FAILED`
for an I/O or a signing failure, the detail naming the exception class. `FAILED` also covers three failures JGit
raises unchecked, each named by its class only:

* a tree of the first parent that holds a path JGit refuses, such as `.GIT` or `git~1` written by another tool:
  `DirCache.read` builds a `DirCacheEntry` per path, whose check throws the `InvalidPathException` of
  `org.eclipse.jgit.dircache`
  (link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/dircache/DirCacheEntry.java[JGit
  7.8.0 `DirCacheEntry`]);
* a tree too large to be read in one piece: `CanonicalTreeParser.reset` reads a tree through
  `ObjectLoader.getCachedBytes()`, which throws a `LargeObjectException` (the notes tree of <<GDR-CORE-10>> as well,
  through `NoteMap.readTree` and `NoteParser`);
* an invalid `gpg.format` of the repository's configuration when the commit is signed: `new GpgConfig(Config)` reads
  it through `Config.getEnum`, which throws an `IllegalArgumentException` for an unknown value
  (link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/lib/GpgConfig.java[JGit
  7.8.0 `GpgConfig`]); the signer is not called.

The caller's code runs on the caller's contract and is mapped to no outcome: an unchecked exception of the `Signer`
propagates unchanged, except the `JGitInternalException` that JGit 7.8.0 `Signer.signObject` itself wraps an encoding
failure in, which is `FAILED`; a checked exception of the `Signer` (`IOException`, a `GitAPIException`) is a signing
failure, `FAILED`. Nothing is inserted in either case.

[#GDR-CORE-5]
== GDR-CORE-5: Compare-and-Swap Reference Update

* A reference update must succeed only when the reference still points to the expected old commit.
* When the reference moved, the library must re-apply the caller's operation on the new state and retry, up to a
  number of attempts the caller passes.
* After the last failed attempt the result must report a conflict outcome; the reference must be unchanged.
* A delete must never adopt a moved reference: when the reference no longer points to the expected old commit, the
  delete must report a conflict at once and leave the reference unchanged.

The caller supplies an *operation* (a function from the current tree to a list of edits), not a finished commit. Every
reference change sets the expected old id (`RefUpdate.setExpectedOldObjectId`; `ObjectId.zeroId()` for a reference
that must not exist yet). An update never sets the force flag: `NEW` and `FAST_FORWARD` are success. A delete
(compare-and-delete, used by the store for a draft reference) sets the expected old id and the force flag, because a
delete has no new value and `RefUpdate` returns `REJECTED` for it without the flag and `FORCED` with it; `FORCED` is
success for a delete. In both cases the expected-old check runs first, so a reference that moved yields `LOCK_FAILURE`
and is unchanged (`RefUpdate.updateImpl`,
link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/lib/RefUpdate.java[JGit 7.8.0 `RefUpdate`]).
For an update, `LOCK_FAILURE` (locked, or no longer the expected old id) re-applies the operation and retries. For a
delete, the library reads the reference after `LOCK_FAILURE`: if it still points to the expected old id, the reference
was only locked and the delete is retried with the same expected old id; if it moved, the delete ends with conflict, so
a newer draft is kept (xref:git-store.adoc#GDR-STORE-3[GDR-STORE-3], xref:git-store.adoc#GDR-STORE-7[GDR-STORE-7]).
`IO_FAILURE` is an unexpected I/O failure and is returned as `FAILED`, as
xref:general.adoc#GDR-GEN-3[GDR-GEN-3] requires; it is neither retried nor a conflict. Every other result is returned
at once as rejected, the detail naming it.

The class is `ReferenceUpdater`, built on an `InCoreWriter`. `compareAndSwap(Repository, String refName,
CommitMetadata, TreeOperation, int attempts)` reads the reference exactly (`Repository.exactRef`), hands the tree of
its commit to the `TreeOperation` (`null` for a reference that does not exist yet), writes the next commit with the
reference's commit as the only parent (<<GDR-CORE-4>>) and moves the reference. `compareAndDelete(Repository,
String refName, String expectedOldId, int attempts)` deletes it. `attempts` is the total number of tries, at least one;
fewer is an `IllegalArgumentException`. The loops count from zero to below `attempts`, so `Integer.MAX_VALUE` is a
bound like any other and the counter never overflows. Neither writes a reflog (`RefUpdate.disableRefLog()`).

Every entry point, `compareAndSwapTree` below included, checks the reference name before it reads anything. A name
that `Repository.isValidRefName` rejects (a `..` component such as `refs/heads/../../../outside/x`, a name of one
component such as `HEAD`, a name ending `.lock`, a character git forbids;
link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/lib/Repository.java[JGit
7.8.0 `Repository`]) is `REFUSED_BY_POLICY` with the detail `refName: not a valid reference name` before any file is
read or written, because the file backend maps a reference name to a path below the git directory. A name read as
absent that overlaps an existing reference (`RefDatabase.isNameConflicting`: `refs/heads/a/b` while `refs/heads/a`
exists, or the reverse) is `REJECTED` with the detail `refName: name conflict`: a compare-and-swap decides it after it
read the reference and before the operation runs, a compare-and-delete in the re-read that follows its `LOCK_FAILURE`.
Without that decision JGit 7.8.0 `RefUpdate.updateImpl` answers the name with `LOCK_FAILURE` (lines 714-718), and the
loop would re-run the operation for every attempt and end in `CONFLICT`, a lost race that no retry can win.

An attempt parses the commit the reference points at as it is (`RevWalk.parseAny`). A reference that points at an
annotated tag, or at any other object that is no commit, ends the call `REJECTED` with the detail
`<refName>: points at no commit`: `RevWalk.parseCommit` would peel the tag and move the reference from the tag to a
commit on the tagged commit.

The outcomes as built:

* `compareAndSwap`: `OK` with the full id of the new commit for `NEW` or `FAST_FORWARD`; `REFUSED_BY_POLICY` for an
  invalid reference name; `CONFLICT` when every attempt ended in `LOCK_FAILURE`, the reference left as the concurrent
  writers left it; the result of the `InCoreWriter` when it wrote no commit, the reference untouched; `FAILED` for
  `IO_FAILURE` or an I/O failure; `REJECTED` for a name conflict, a reference at no commit and every other result. The
  commit of a lost attempt stays unreferenced in the object database.
* `compareAndDelete`: `OK` with the deleted id for `FORCED`; `REFUSED_BY_POLICY` for an invalid reference name and
  `NOT_FOUND` when `expectedOldId` is no full commit id, nothing being read or written in either case; `CONFLICT` when
  the reference moved away or is gone, or every attempt met a held lock; `FAILED` for `IO_FAILURE` or an I/O failure;
  `REJECTED` for a name conflict and every other result.

The `TreeOperation` is the caller's code and runs on the caller's contract: an exception it throws, and the
`NullPointerException` of a `null` list or element it returns, propagates out of `compareAndSwap` unchanged, with the
reference untouched.

A package-private tree-level variant, `compareAndSwapTree`, runs the same retry loop with a finished tree instead of
edits, for a caller that builds the whole tree itself (the notes of <<GDR-CORE-10>>): each attempt hands the tree of
the reference's current commit to a tree source, and `InCoreWriter.writeTree` commits the tree it returns as it is,
with the same parent, signing and single flush as `write`. Its update is created with
`Repository.updateRef(refName, true)`, so a symbolic reference is replaced by one that points at the new commit and its
former target is left as it is (`RefDirectory.newUpdate` and `DfsRefDatabase.newUpdate` with `detach`,
link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/internal/storage/file/RefDirectory.java[JGit
7.8.0 `RefDirectory`]); `compareAndSwap` follows a symbolic reference and moves its target instead. Its outcomes are
those of `compareAndSwap`.

For a symbolic reference replaced by `compareAndSwapTree` or deleted by `compareAndDelete`, the two backends check the
expected id differently. The file backend compares it with the id the symbolic reference resolves to while it holds
the lock (`RefDirectoryUpdate.tryLock` re-reads the reference under the lock). The in-memory DFS backend does not:
`DfsRefUpdate.tryLock(false)` sets the old id of a symbolic reference to none, so `RefUpdate.updateImpl` compares the
expected id with the zero id and reports `LOCK_FAILURE` for every expected id, and its compare-and-put checks only that
the reference is still symbolic with the same target
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/internal/storage/dfs/DfsRefUpdate.java[JGit
7.8.0 `DfsRefUpdate`],
link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/lib/RefUpdate.java[JGit
7.8.0 `RefUpdate`]). When a detaching update or a delete of a symbolic reference ends in `LOCK_FAILURE` with no old id,
the updater therefore decides through one atomic `BatchRefUpdate`. On the file backend that state is reached as well,
when another writer holds the reference's lock: `RefDirectoryUpdate.tryLock` returns before it calls
`setOldObjectId`
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/internal/storage/file/RefDirectoryUpdate.java[JGit
7.8.0 `RefDirectoryUpdate`]), so the old id is unset there too; the file backend refuses the batch, and the attempt is
reported as the same `LOCK_FAILURE`, a lost race. The batch is: the unlink of the symbolic reference
(`ReceiveCommand.unlink`, expecting its target), a no-op `ReceiveCommand.link` on every further link of a symbolic chain
that holds only while the link still points at the same target, and a command on the base reference from the expected
id to the same id, which changes nothing and holds only while the base reference still points at the expected id.
`ReftableBatchRefUpdate.matchOld` compares a symbolic command with the immediate target name only
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/internal/storage/reftable/ReftableBatchRefUpdate.java[JGit
7.8.0 `ReftableBatchRefUpdate`]), so without the commands on the links a writer that retargeted a middle link while the
base reference stayed at the expected id would go unseen. A batch that lost a race is the `LOCK_FAILURE` it replaces: a
retry, then `CONFLICT`, and for a delete the re-read above. A batch that failed on a storage error is not a lost race:
`ReftableBatchRefUpdate.execute` reports an `IOException` as `LOCK_FAILURE` with the message `io error`, which the
updater maps to `IO_FAILURE`, so the call ends in `FAILED` without a retry. The expected id is never replaced by the
zero id and the check is never dropped; a backend that cannot run the batch atomically, such as the file backend's
`PackedBatchRefUpdate`, which refuses a symbolic command in an atomic batch, writes nothing.

A dangling symbolic reference has no resolved id, so the attempt expects none. `DfsRefUpdate.tryLock(false)` sets no
old id for a symbolic reference whether or not its target has been written since, so there the zero expected id always
matches and a `RefUpdate` would replace the alias with a root commit, dropping a commit another writer wrote to the
target between the read and the update. For a dangling symbolic reference the updater therefore runs the batch before
any `RefUpdate`, with the command on the base reference holding only while the base reference is still absent: a target
written in between makes the batch fail, which is a lost race, and the next attempt reads the alias again and builds
on the written commit. A backend that refuses the batch (the file backend) falls through to its `RefUpdate`, which
re-reads the reference under its lock. That fall-through is recorded, not closed: the file backend compares the zero
expected id with the id it reads under its own lock, so no comparison is dropped, and a guard of the updater around it
would only repeat that comparison outside the lock.

A detail names the reference and the `RefUpdate.Result`, never content or an identity
(xref:general.adoc#GDR-NFR-3[GDR-NFR-3]). On a file-based repository a held `.lock` file of the reference ends an
attempt in `LOCK_FAILURE` (`RefDirectoryUpdate.tryLock` and `LockFile.lock()`,
link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/internal/storage/file/LockFile.java[JGit
7.8.0 `LockFile`]); the in-memory DFS reference database compares and stores atomically, so there an attempt is lost
only to another writer.

[#GDR-CORE-6]
== GDR-CORE-6: In-Core Merge

* The library must merge two commits without a working tree, at path level only: a path changed by one side takes
  that side's entry; a path changed differently by both sides is a conflict; file contents are never merged.
* A merge with conflicts must report the conflicting paths and must not create a commit.

The class is `InCoreMerger`. `merge(Repository, String ours, String theirs)` takes the full ids of two commits and runs
`MergeStrategy.SIMPLE_TWO_WAY_IN_CORE.newMerger(repository)` (class `StrategySimpleTwoWayInCore`, always in core): a
three-way merge over the merge base and both tips at the path level only, which never merges file contents
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/merge/StrategySimpleTwoWayInCore.java[JGit 7.8.0 `StrategySimpleTwoWayInCore`]).
Its `NameConflictTreeWalk` takes an entry equal on both sides, or unchanged on one side, as it is, a whole subtree
included, enters a subtree changed on both sides, and reports every other entry that is no tree on one of the three
sides as a conflict, a file on one side and a directory of the same name on the other included.
`MergeStrategy.RECURSIVE` is not used: it merges file contents textually, which
xref:../adr/0001-Documents_are_written_in_core_without_working_trees_and_references_move_by_compare-and-swap.adoc[ADR-0001]
rejects. The merge base is the one merge base of the two commits (`Merger.getBaseCommit` with `RevFilter.MERGE_BASE`;
link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/merge/Merger.java[JGit
7.8.0 `Merger`]); two commits without a common ancestor merge against the empty tree, and JGit refuses more than one
merge base with a `NoMergeBaseException` of reason `MULTIPLE_MERGE_BASES_NOT_SUPPORTED`. A clean merge inserts the
merged tree through the merger's own inserter; the merge writes no commit and moves no reference, and the caller builds
the merge commit from the tree id.

The merger reports no conflicting paths, so on failure the library computes them itself with a tree walk over the
merge base and both tips: a `NameConflictTreeWalk` that applies the merger's own rule, so a path is conflicting when its
entry (object id or file mode) differs from the base on both sides and differs between the sides.

`merge` returns the sealed `MergeResult`, which carries its content as data:

* `MergeResult.Merged`: outcome `OK`, no detail; `treeId()` is the full id of the merged tree, written to the object
  database.
* `MergeResult.Conflicting`: outcome `CONFLICT`; `paths()` is every conflicting path, repository-relative, sorted and
  distinct, never empty. The detail names only their number (`N conflicting paths`), never a path, so a caller reads the
  paths from `paths()` and never parses a detail.
* `MergeResult.NotMerged`: every other non-success, with its outcome and its detail (the component `reason`, returned
  by `detail()`): `NOT_FOUND` when a commit id is no full commit id or no commit of the repository (an annotated tag or
  a tree included), the detail naming the field `ours` or `theirs`; `CONFLICT` with the detail
  `merge base: more than one` and no paths, because none were computed; `FAILED` for an I/O failure, and for a tree of
  the merge base or a tip that holds a path JGit refuses, such as `.GIT` or `git~1` (`StrategySimpleTwoWayInCore`
  builds a `DirCacheEntry` per entry it takes, whose check throws an `InvalidPathException`), and for a tree too large
  to be read in one piece (`CanonicalTreeParser.reset` reads a tree through `ObjectLoader.getCachedBytes()`, which
  throws a `LargeObjectException` above the streaming threshold, as for <<GDR-CORE-4>> and <<GDR-CORE-10>>), the
  detail naming the exception class. When the merger fails and the walk finds no conflicting path, the result is `CONFLICT` with the
  detail `merge: no conflicting path`, because a `Conflicting` without a path would contradict its own contract.

`MergeResult` composes the shape of xref:general.adoc#GDR-GEN-3[GDR-GEN-3] (an outcome of the closed `GitOutcome` list
and a detail for every non-success that carries nothing xref:general.adoc#GDR-NFR-3[GDR-NFR-3] forbids) instead of
extending `GitResult`: a `GitResult` that is no success carries no value, and a conflict that names its paths would
break that invariant. A caller branches with a pattern-matching `switch` over the three variants; `toResult()` gives the
plain `GitResult<String>` to a caller that needs no more: `OK` with the tree id for `Merged`, otherwise the outcome and
the detail without value, so the conflicting paths are not carried over.

[#GDR-CORE-7]
== GDR-CORE-7: Fetch and Push with Credentials and Lease

* Credentials must be supplied per fetch or push by the caller; the library must not store them.
* A push must support a lease: it must be refused when the remote reference differs from the expected value.
* A rejected push, a refused lease, an unreachable remote and expired or invalid credentials must each be reported as
  a distinct outcome.

Credentials are a `@Nullable org.eclipse.jgit.transport.CredentialsProvider` per call, in `FetchInput`, `PushInput`
and `CloneInput`. A secret in the URL of a clone is not stored: the origin of a clone carries no user information,
query data or fragment, and a URL whose user information cannot be separated is refused (<<GDR-CORE-3>>). The
outcomes:

* `REJECTED`: the remote refuses the update permanently (non-fast-forward, a protected branch, a refusing hook or
  another refusal; JGit's `RemoteRefUpdate.Status` `REJECTED_NONFASTFORWARD`, `REJECTED_OTHER_REASON` or
  `REJECTED_NODELETE`), and a plain push without a lease that lost a race;
* `LEASE_REFUSED`: a leased push lost a race on the remote reference, so a fetch and a new attempt may succeed: the
  advertised reference differs from the expected value (`REJECTED_REMOTE_CHANGED`), or the lease held in the
  advertisement and the remote could not lock the reference for the update because it moved or another writer held it
  after the advertisement. JGit's `ReceivePack` updates the reference against the advertised id and answers its
  `LOCK_FAILURE` with `ng <ref> failed to lock`
  (link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/transport/ReceivePack.java[JGit
  7.8.0 `ReceivePack.sendStatusReport`],
  link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/transport/ReceiveCommand.java[`ReceiveCommand.execute`]);
  the client turns every `ng` into `REJECTED_OTHER_REASON` with that text as the message
  (link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/transport/BasePackPushConnection.java[`BasePackPushConnection.readStatusReport`]),
  (checked in the JGit 7.8.0 sources: an `ng <ref> <message>` line becomes `REJECTED_OTHER_REASON`, and the rest of
  the line after the reference name is `RemoteRefUpdate.getMessage()`). A native Git remote answers the same lost race,
  a reference that no longer holds the old id the push sent, with `ng <ref> incorrect old value provided`, while the
  reason that names both ids (`cannot lock ref '<ref>': is at <id> but expected <id>`) reaches the client only as a
  sideband error line and never as the message. This was observed with native Git 2.56.1 as the remote (files
  backend), the client being JGit 7.8.0; the reftable backend and the source of `builtin/receive-pack.c` were not
  checked. A leased update whose message is exactly `failed to lock` or exactly `incorrect old value provided`, each
  compared whole, is `LEASE_REFUSED`; either message on a plain push without a lease, and every other message of a
  leased push, stays `REJECTED`. Another remote that words a lost race differently again is reported as `REJECTED`.
  Accepted as a documented limit (owner decision of 2026-11-24): a remote that answers a lost race with a wording
  not named above, for example `failed to update ref` (a wording reported in review, not checked against any Git
  release), makes the leased push `REJECTED`, so a save of `git-store` is not retried; its draft remains and the
  caller saves again (xref:git-store.adoc#GDR-STORE-3[GDR-STORE-3]);
* `CREDENTIALS_INVALID`: the remote refuses the authentication, HTTP 401 or 403, recognised by the wordings of JGit's
  `JGitText` and `TransportHttp` for it (`notAuthorized`, `noCredentialsProvider`, `authenticationNotSupported`,
  `serviceNotPermitted`;
  link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/resources/org/eclipse/jgit/internal/JGitText.properties[JGit
  7.8.0 `JGitText.properties`]);
* `UNREACHABLE`: every other transport failure;
* `REFUSED_BY_POLICY`: the remote's effective URL, after `insteadOf` rewriting, is outside the remote policy, or a
  push names a remote with more than one push URL; nothing is sent. A refused pre-push hook is `REFUSED_BY_POLICY` as
  well, but later: JGit's `PushProcess` runs the hook after it read the remote's reference advertisement and before it
  sends any update
  (link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/transport/PushProcess.java[JGit
  7.8.0 `PushProcess.execute`]), so the remote was contacted, but no update and no object was sent.

A fetch checks every reference update it reports, because JGit's `FetchProcess` returns the `FetchResult` also when
an update was not written
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/transport/FetchProcess.java[JGit
7.8.0 `FetchProcess`]). The `RefUpdate.Result` values `NEW`, `FORCED`, `FAST_FORWARD` and `NO_CHANGE` are written;
`REJECTED`, `REJECTED_CURRENT_BRANCH`, `REJECTED_MISSING_OBJECT` and `REJECTED_OTHER_REASON` end the fetch `REJECTED`;
`LOCK_FAILURE`, `IO_FAILURE` and every other result end it `FAILED`, and so does an update without a result, which
JGit's `TrackingRefUpdate` holds until its command was applied
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/transport/TrackingRefUpdate.java[JGit
7.8.0 `TrackingRefUpdate`]; detail `<reference>: no result`). The detail names the local reference and the result. The
fetch of a clone checks its mirrored references by the same rule (<<GDR-CORE-3>>).

A fetch with `FetchInput.prune` set (`false` by default) also deletes every local reference that lies in the
destination of one of its reference specifications and whose source the remote no longer advertises, through
`FetchCommand.setRemoveDeletedRefs`; JGit 7.8.0 `FetchProcess.deleteStaleTrackingRefs` considers only the local
references that match a destination of the fetch's reference specifications, so a reference outside every
destination, such as a draft below `refs/drafts/` of `git-store`, is never deleted
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/transport/FetchProcess.java[JGit
7.8.0 `FetchProcess`]).

Every transport of a clone, a fetch and a push runs with a compiled timeout of 60 seconds
(`JGitRepositoryOperations.TRANSPORT_TIMEOUT_SECONDS`, set through `TransportCommand.setTimeout`;
link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/api/TransportCommand.java[JGit
7.8.0 `TransportCommand`]), as `fetchCommit` does (<<GDR-CORE-8>>): a remote that stops answering must not block a
caller thread forever. The value bounds the connect and every single read, not the total duration of the operation.

A call uses exactly the caller's `CredentialsProvider`, and none when the caller passes `null`: JGit's
`TransportCommand` and `Transport` start with the process-wide `CredentialsProvider.getDefault()` and keep it when given
`null`
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/api/TransportCommand.java[JGit 7.8.0 `TransportCommand`]),
so the operations set the provider on every transport they open.

Accepted exception: `http.extraHeader` and the cookies of `http.cookieFile` in the repository or user configuration
reach the remote. JGit's `TransportHttp` reads the cookie file when it is constructed and adds the configured extra
headers and the cookies that match the URL to every request
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/transport/TransportHttp.java#L294[JGit
7.8.0 `TransportHttp`, line 294] and
link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/transport/TransportHttp.java#L1093-L1097[lines
1093-1097]); the library neither strips nor refuses them. They are configuration the owner of the repository wrote, the library
writes neither of them, and every connection that carries them goes to a URL the remote policy admits, because the
policy-checking connection factory checks each connection, a redirect target included, before it is opened. The test
`extraHeaderAndCookieFileReachRemote` of `JGitRepositoryOperationsTest` records that both reach the remote.

A push has exactly one destination. JGit's `PushCommand` pushes to every push URL of a remote and reports one
`PushResult` each
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/api/PushCommand.java[JGit 7.8.0 `PushCommand`]),
so destinations could disagree; a remote with more than one push URL is refused before any contact instead. A lease
holds only when the remote reference is at the expected head, also when it is already at the pushed commit: JGit's
`PushProcess` reports `UP_TO_DATE` before it compares the lease and before it sets the expected old id
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/transport/PushProcess.java[JGit 7.8.0 `PushProcess.prepareRemoteUpdates`]),
so an up-to-date update is checked against the advertised reference of the same push, and its old id is the advertised
id; an old id of `null` means only that the push created the reference. A lease that is no full object id is
`NOT_FOUND`, named by its field `expectedRemoteHead`: JGit's `Transport.findRemoteRefUpdatesFor` resolves a lease that
names nothing to no lease
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/transport/Transport.java[JGit 7.8.0 `Transport`]),
which would push without one.

A detail and a log message never carry anything xref:general.adoc#GDR-NFR-3[GDR-NFR-3] forbids. A URL is rendered from
its scheme, host, port and path only, without user information, query data or fragment, which JGit's `URIish` keeps
in its path and would render. An invalid or unknown input value (a revision, a local reference, a commit, a path) is
named by its field and the reason, never by the caller's value, and a failure detail names the exception class without
its message. A detail is never blank, so no operation fails with the `IllegalArgumentException` of `GitResult` for a
blank detail: the class of an anonymous exception, whose simple name is empty, is named by its binary name, a path that
renders blank (`Path.of("")`) is rendered as `(blank path)`, and a blank remote reference name as
`(blank reference name)`. The `toString` of `RemotePolicy` renders the origin as scheme, host and port only
(`RemotePolicy[localOnly]` without origin), and the one of `FetchCommitInput` renders its URL as above.

[#GDR-CORE-8]
== GDR-CORE-8: Cache Repository

* The library must fetch exactly one commit into a bare cache repository under the remote policy.
* It must read the content of one file at a given commit of the cache.
* A commit the remote does not serve must be reported as an outcome.

The operations are `initCache` (create or open a bare cache repository), `fetchCommit` and `readFile`. `fetchCommit`
fetches one commit by its full id from a URL the remote policy of the call admits, within a transport timeout, and
keeps it reachable under `refs/pinned/<id>`; a commit already in the cache is not fetched again, and its pin is
written again when an earlier fetch stored the object but could not write the pin. The fetch is anonymous: user
information in the URL is removed before the transport sees it, and no credentials provider is set. A commit the
remote does not serve is `UNSERVED`; a URL outside the policy or a process start is `REFUSED_BY_POLICY`; a remote that
does not answer is `UNREACHABLE`. `readFile` reads the raw blob of a path at a commit of the cache, without any filter;
a commit not in the cache or a path that is no regular file is `NOT_FOUND`. Both operations open the cache as its
configuration describes it and refuse anything but a bare repository as `NOT_A_REPOSITORY`, so the git directory of a
working tree is never used as a cache; JGit's `BaseRepositoryBuilder.setBare()` would override `core.bare`
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/lib/BaseRepositoryBuilder.java[JGit 7.8.0 `BaseRepositoryBuilder`]).

`readFile` reads a blob of at most 16 MiB (`JGitRepositoryOperations.READ_FILE_LIMIT_BYTES`, 16 × 1024 × 1024 bytes), a
blob of exactly that size included. The size is asked through `ObjectReader.getObjectSize` before the blob is opened,
which reads it from the header of a loose object or from the pack entry without inflating the content
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/internal/storage/file/WindowCursor.java[JGit
7.8.0 `WindowCursor`]), and a larger blob is `REFUSED_BY_POLICY` with the detail
`path: larger than the limit of 16 MiB`, so it is never loaded into memory. Opening the blob first would not do: JGit's
`Repository.open` reads a blob below the streaming threshold completely into memory before it returns the loader
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/internal/storage/file/UnpackedObject.java[JGit
7.8.0 `UnpackedObject`]). The reason is the caller's memory: the
operation returns the whole blob as one byte array, and the cache holds commits of a source the remote policy admits but
whose content the library does not control, so without a bound one large file of a pinned commit would load into the
heap of the process in full. The value lies far above the configuration files and documents the cache serves and below
the JGit default `core.streamFileThreshold` of 50 MiB, above which JGit no longer keeps a blob in one array itself.

[#GDR-CORE-9]
== GDR-CORE-9: Reading

* The library must read a snapshot of the tree of a reference, a tag or a commit.
* It must list the commits that changed a given path, newest first, with author, committer, time and message.
* It must compute the added, modified and deleted paths between two commits.

The class is `RepositoryReader`. It takes a JGit `Repository`, so it reads an in-memory repository as well as one on
disk, and it writes no object and no reference. A revision of `snapshot` and `history` is a reference, by its short or
full name, or a full commit id, resolved through the one resolution `log` uses (<<GDR-CORE-11>>): an ambiguous
revision is `AMBIGUOUS`, an abbreviated commit id or a revision expression `NOT_FOUND`, a full commit id that reaches
another commit `IDENTITY_MISMATCH`, and an annotated tag is peeled to its commit. The commits of `changes` are full
commit ids, parsed as they are (`RevWalk.parseAny`) and required to be commits, so an annotated tag or a tree is
`NOT_FOUND`. A detail names the input field (`revision`, `path`, `from` or `to`) and the reason, never a path or
content; a failure detail names the exception class. The JGit APIs are checked against JGit 7.8.0
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/revwalk/RevWalk.java[`RevWalk`],
link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/treewalk/TreeWalk.java[`TreeWalk`]):

* `snapshot(Repository, String revision)` returns a `Snapshot` with the commit id, the tree id and every regular and
  executable file of the tree, recursively and in the tree's order, each as a `SnapshotFile` with its path, its
  `FileKind` (`REGULAR`, mode `100644`, or `EXECUTABLE`, mode `100755`) and its blob id. A symbolic link or a submodule
  entry is no file of the snapshot.
* `history(Repository, String revision, String path, int maxCount)` returns the commits that changed the path, at most
  `maxCount` (a value below 1 counts as 1, as for `log`), newest first, as the `CommitInfo` of `log` with id, parents,
  author, committer, times and message. The walk visits the whole ancestry of the revision's commit, with no tree filter
  on the `RevWalk`, and keeps a commit whose tree differs at the path from the tree of at least one of its parents,
  compared per parent by a `TreeWalk` with `PathFilter` and `TreeFilter.ANY_DIFF`; a root commit that holds the path
  counts as a change, a merge that equals every parent at the path does not, a directory changes when a path below it
  changes, and no rename is followed. A merge that equals one parent at the path and differs from another is kept: a
  `RevWalk` tree filter would drop it, because for such a merge JGit 7.8.0 `TreeRevFilter` reports no change and
  follows only the parent the merge equals
  (link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/revwalk/TreeRevFilter.java[JGit
  7.8.0 `TreeRevFilter`]). Without a tree filter the walk rewrites no parent, so the parents of a returned commit are
  its real parents. The walk advances with `RevWalk.next()` and stops once `maxCount` commits are found, reading no
  commit beyond them; an I/O failure of the walk, a missing tree included, is `FAILED`. A path that is blank, starts or
  ends with `/` or holds an empty segment is `NOT_FOUND` with the detail `path: not a valid path`; a path no commit
  changed yields an empty list.
* `changes(Repository, String from, String to)` returns every changed path between the two trees as a `PathChange` with
  its `ChangeType`, recursively, in the trees' order and without rename detection (`TreeWalk` with
  `TreeFilter.ANY_DIFF`): `ADDED` for a path in the newer commit only, `DELETED` in the older one only, `MODIFIED` in
  both with another content or file mode. A file replaced by a directory of the same name is the file deleted and the
  files below the directory added. Equal trees yield an empty list.

[#GDR-CORE-10]
== GDR-CORE-10: Git Notes

* The library must read and write notes on a commit under a caller-named notes reference (for example
  `refs/notes/anchors/rfc3161`).
* Writing a note must use the compare-and-swap of <<GDR-CORE-5>> on the notes reference.

The class is `GitNotes`, built on a `ReferenceUpdater`. A note is attached to a commit under a notes reference the
caller names, below `refs/notes/`; `git-core` reserves no notes reference itself. The notes reference points at a
commit whose tree is the note map, which JGit's `NoteMap` reads (`NoteMap.read`, `NoteMap.readTree`), looks up
(`NoteMap.get`, the id of the note's blob), sets (`NoteMap.set`) and writes back as a tree (`NoteMap.writeTree`)
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/notes/NoteMap.java[JGit
7.8.0 `NoteMap`]). A commit is addressed by its full id and must be a commit itself: it is parsed as it is
(`RevWalk.parseAny`), so neither a tree, a blob nor an annotated tag, not even one that points at a commit, receives a
note.

* `read(Repository, String notesRef, String commitId)` reads the notes reference exactly, a symbolic one resolved to
  the commit it points at, and returns the note's content as a copy owned by the caller. `NOT_FOUND` names the commit
  (`commit: not a full commit id`, `commit: not found`), an absent notes reference (`notesRef: not found`) or an absent
  note (`note: not found`); a notes reference that points at no commit is `FAILED`.
* `write(Repository, String notesRef, String commitId, byte[] note, CommitMetadata, int attempts)` sets the note,
  replacing a note the commit already has, and returns the full id of the new notes commit. The note is copied on
  entry. `NOT_FOUND` names the commit as for `read`, nothing being written; `CONFLICT` means every attempt lost its race
  to another writer of the notes reference; `FAILED` is an I/O or a signing failure, an invalid `gpg.format`, or a
  notes tree too large to be read in one piece (the `LargeObjectException` of `NoteMap.readTree`, which parses each
  tree with `NoteParser` through `CanonicalTreeParser.reset` and `ObjectLoader.getCachedBytes()`;
  link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/notes/NoteParser.java[JGit
  7.8.0 `NoteParser`]); `REJECTED` is a notes reference that does not exist and whose name conflicts with an existing
  reference, such as `refs/notes/a/b` while `refs/notes/a` exists (detail `refName: name conflict`, decided by the
  updater before the note is set, never a lost race, see <<GDR-CORE-5>>), a notes reference at no commit, and every
  other result of the reference update.

For both, a notes reference that is not below `refs/notes/` or no valid reference name
(`Repository.isValidRefName`) is `REFUSED_BY_POLICY` with a detail naming the field only, as for an invalid branch
name (xref:general.adoc#GDR-GEN-3[GDR-GEN-3]), and nothing is read or written. A detail never carries a note's content
(xref:general.adoc#GDR-NFR-3[GDR-NFR-3]).

A write is the compare-and-swap of <<GDR-CORE-5>> on the notes reference, through the tree-level variant
`compareAndSwapTree`: each attempt reads the notes tree the reference currently points at (an empty map,
`NoteMap.newEmptyMap()`, for a reference that does not exist yet), inserts the note as a blob, sets it for the commit
and commits the map's tree, with the reference's commit as the only parent. A lost race re-reads the notes tree the
concurrent writer left and sets the note on that tree again, so the other writer's notes are kept. Notes bypass
`TreeEdit`, because the map decides its own fan-out: JGit's `LeafBucket.set` splits a bucket that already holds 256
notes into a fan-out subtree before it adds another
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/notes/LeafBucket.java[JGit
7.8.0 `LeafBucket`]), so a note expressed as a path edit could exist at two fan-out levels, while the map's own tree
holds it at exactly one path. The update of the notes reference is detaching (`Repository.updateRef(refName, true)`):
a symbolic notes reference is replaced by one that points at the new notes commit, and its former target is left as it
is.

[#GDR-CORE-11]
== GDR-CORE-11: Identity of Commits and References

* The library must provide full and abbreviated commit ids and resolve branch, tag and remote-branch names.
* A name that resolves to more than one object must be reported as ambiguous, with the candidates in the detail.

`GitIdentity` holds the rules. A commit is passed and compared as its full 40-digit id. "Provide" means producing:
`abbreviate(Repository, AnyObjectId)` returns the shortest prefix of at least seven hexadecimal digits that is unique
in the repository, through JGit's one-argument `ObjectReader.abbreviate(AnyObjectId)`, which starts at seven digits
and lengthens the prefix only while it is ambiguous, so it returns seven digits even when six would identify the
object
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/lib/ObjectReader.java[JGit 7.8.0 `ObjectReader`]).
The abbreviation is for display only; an identity input is always a full id or a reference name.

`branchRef`, `tagRef` and `remoteBranchRef` return the full references `refs/heads/<name>`, `refs/tags/<name>` and
`refs/remotes/<remote>/<name>`. `lookup(Repository, String)` classifies a name and lists its candidates from one read
of the reference database, so the candidates always belong to the classification; `resolution` and `candidates`
return one half of it. A name names a reference when it is the reference's full or short name, `HEAD` included. A name
that matches two references, or a reference and a full commit id, is `AMBIGUOUS`, and the detail lists the full
reference names, and the id when the name is a full commit id.

`log` (its start revision) and `push` (its local reference) resolve only a supported identity: exactly one reference
or a full commit id, resolved by the full reference name or by the id itself. Everything else is not resolved and is
`NOT_FOUND`: an abbreviated id (detail `revision: abbreviated commit id` or `localRef: abbreviated commit id`), a
shorter prefix, and a revision expression such as `main~1` or `<prefix>~0`. JGit's `Repository.resolve` would accept
an abbreviation from two digits on and an expression on an abbreviated base
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/lib/Repository.java[JGit 7.8.0 `Repository.resolveSimple`],
link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/lib/AbbreviatedObjectId.java[`AbbreviatedObjectId.isId`]),
so none of them reaches it. A full commit id absent from the repository is `NOT_FOUND`, not `FAILED`; a full commit id
that reaches another commit is `IDENTITY_MISMATCH`.

`log` lists at most `maxCount` commits (a value below 1 counts as 1), newest first. The walk advances with
`RevWalk.next()` and stops once `maxCount` commits are listed, so it reads no commit past the limit beyond the parents of
the listed ones, which the walk parses to order the history. JGit's `RevWalk.iterator()` would read one commit ahead of
the one it returns and rethrow a read failure as the unchecked `RevWalkException`
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/revwalk/RevWalk.java[JGit
7.8.0 `RevWalk`]), so a missing commit past the limit would escape the operation. A commit missing further back than
the parents of the listed commits does not affect the result; a missing parent of a listed commit ends `FAILED`
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/revwalk/PendingGenerator.java[JGit
7.8.0 `PendingGenerator`]).

== Working Trees

The package `de.cuioss.git.document.core.worktrees` of `git-core` holds the linked working trees. It builds on the
package `de.cuioss.git.document.core` and adds no third-party dependency to those of `git-core`, see
xref:general.adoc#GDR-GEN-1[GDR-GEN-1]. The document store does not use it; clients that work on files on disk do.
<<GDR-CORE-12>>, <<GDR-CORE-13>>, <<GDR-CORE-14>> and <<GDR-CORE-15>> are implemented. The JGit APIs named here are
checked against JGit 7.8.0 (tag `v7.8.0.202609011348-r` of https://github.com/eclipse-jgit/jgit). JGit 7.8.0 has no
command that creates a linked working tree: its `api` package holds no worktree command
(link:https://github.com/eclipse-jgit/jgit/tree/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/api[JGit 7.8.0 `api` package]),
so the package reads and writes Git's administration files of linked working trees itself. `LinkedWorktrees` is taken
from `pm-provider-git` and changed where <<GDR-CORE-12>> demands it
(xref:../clients/pm-mcp-core.adoc#_what_the_worktrees_package_took_and_changed[Client: `pm-mcp-core`, What the
Worktrees Package Took and Changed]). Rationale:
xref:../concepts/module-structure.adoc#_the_foundation_modules[Module Structure, The Foundation Modules].

|===
|Type |Role

|`WorktreeOperations` |The working-tree operations below (`worktreeAdd`, `worktreeList`, `worktreeRemove`, `commit`,
`worktreeStatus` and `releaseBranchReservation`) and their input and value records (`Worktree`, `WorktreeAddInput`,
`CommitInput`, `WorktreeStatus`)
|`JGitWorktreeOperations` |The implementation of `WorktreeOperations` on JGit, in process and without a `git`

The log messages of the working-tree operations are records of `GitCoreLogMessages`, catalogued in
`git-core/doc/LogMessages.adoc` (xref:general.adoc#GDR-GEN-4[GDR-GEN-4]).

Every operation returns a `GitResult` with one constant of `GitOutcome`
(xref:general.adoc#GDR-GEN-3[GDR-GEN-3]). A refused capability (a present hook, a filter driver that would start a
process) is `REFUSED_BY_POLICY` with the capability as detail; every other unexpected failure is `FAILED` with the
failure class only. No operation starts a process through the repository's `RefusingFS`; that the library starts no
process at all holds under the condition of <<GDR-CORE-1>>: JGit reads the configuration through its process-wide
`SystemReader`, which the operations do not replace, and the default reader runs `git` once per JVM, so no process
starts only where the application installed `RefusingFS.systemReader(SystemReader)` before any JGit use. No detail and
no log message carries an author or committer name, an e-mail address or a commit message, and no log message carries
a path or an administrative name derived from it (xref:general.adoc#GDR-NFR-3[GDR-NFR-3]).

[#GDR-CORE-12]
=== GDR-CORE-12: Linked Working Trees

* The library must add, list and remove linked working trees.
* The administration files must follow Git's own layout, so that `git worktree list` of a Git installation lists the
  working trees the library created.

`worktreeAdd` creates a linked working tree for a branch, or detached at a commit, at a path inside the main working
tree and writes the administration directory `$GIT_DIR/worktrees/<id>/` with `gitdir` (the absolute path back to the
working tree's `.git` file), `commondir` (the path of the main repository's `$GIT_DIR`) and `HEAD`, and in the working
tree the `.git` file holding `gitdir: <path>` that points to the administration directory
(link:https://git-scm.com/docs/gitrepository-layout[gitrepository-layout(5)], entries `worktrees`,
`worktrees/<id>/gitdir` and `commondir`; link:https://git-scm.com/docs/git-worktree[git-worktree(1)], DETAILS). The
start point and the branch are classified by `GitIdentity` (<<GDR-CORE-11>>): only `HEAD`, exactly one reference or a
full commit id is resolved, an abbreviated or unknown start point never, also not for an existing branch.

Before an addition claims anything it is guarded in this order: the root must be the main working tree, not a linked
one (`PATH_REFUSED`); the branch, new or existing, must form a valid reference name `refs/heads/<branch>` by JGit 7.8.0
`Repository.isValidRefName` and be a branch name git accepts (`REFUSED_BY_POLICY`, the detail naming the field, never
the string); the target must lie inside the root, outside the common directory with its administration area
`worktrees/` and outside every registered linked working tree, compared by real paths (`PATH_REFUSED`). Only then is
the start point classified and the target claimed.

* *Branch name.* JGit 7.8.0 `Repository.isValidRefName` checks the full reference: it refuses `.lock` only at the end
  of the whole name and accepts `refs/heads/HEAD`, `refs/heads/@`, `refs/heads/-<name>` and `refs/heads/refs/<name>`.
  The guard refuses these short names as well: `HEAD`, a leading `-` and a component ending `.lock`, which git refuses
  as a branch name (`git check-ref-format --branch` of git 2.56.1 ends with "not a valid branch name"; a component
  ending `.lock` is rule 1 of link:https://git-scm.com/docs/git-check-ref-format[git-check-ref-format(1)]); the name
  `@`, which git accepts as a branch but reads as `HEAD`
  (link:https://git-scm.com/docs/gitrevisions[gitrevisions(7)], "`@` alone is a shortcut for `HEAD`"); and a name
  starting `refs/`, which git accepts but which reads as a full reference name, a rule of the library beyond git. So
  no name reaches the repository that git would refuse or read as something other than the branch.
  `GitWorktreeListCompatibilityTest` checks the guard against an installed git.
* *Bare root.* A bare repository has no main working tree: its root is its git directory, so every target inside the
  root lies inside the git directory and is refused `PATH_REFUSED` before anything is claimed, rather than registering
  a working tree whose administration area would hold it.
* *Real paths.* A path is resolved with `Path.toRealPath`, or, where it is missing, through its nearest existing
  ancestor, without a prior existence test: a working tree removed concurrently moves the resolution to its ancestor
  instead of failing the operation, and a prunable working tree registered or named through a symbolic link is found
  by its real path.

Concurrent additions on one repository do not interfere:

* The target is claimed exclusively: a missing target directory is created with `Files.createDirectory`, and in it, or
  in a caller-supplied empty directory, the `.git` file is created with `Files.createFile`; a lost claim ends
  `ALREADY_EXISTS`.
* Every branch, a new one like an existing one, is reserved before it is checked, by the reservation file
  `worktree-branch-<SHA-1 of the full branch name>.lock` in the common directory, created with `Files.createFile`, until
  the new working tree is checked out and unlocked, or, for a refused or failed addition, until its rollback has
  deleted the branch it created; a branch another addition reserved ends `BRANCH_CHECKED_OUT`. A new branch is
  created by a compare-and-swap from the zero id. A reservation left by a process that ended during an addition stays
  until <<GDR-CORE-15>> releases it. So does the reservation of a complete addition whose release fails: the working
  tree is registered and checked out, so the addition ends `OK` with the working tree kept, and the failed release is
  logged as `GIT_CORE-105` without an argument, never rolled back.
* The administration directory is claimed atomically under the next free numeric suffix; its files are written
  completely before they appear under their names, `HEAD` last, and it stays locked while the start commit is checked
  out.
* A refused or failed addition removes what it created and nothing else: the target directory it created or what it
  wrote into a caller-supplied one, its administration directory, its reservation, and the branch it created, the
  latter only while it still points at the start commit, so a retry succeeds. JGit 7.8.0 `RefUpdate.delete` returns
  `LOCK_FAILURE` both for a held reference lock and for a branch no longer at the expected commit, so after a lock
  failure or a rejection the branch is read again: an absent branch was deleted, a branch at another commit was
  advanced by another writer and is kept, and a branch still at the start commit is left behind and reported as an
  incomplete rollback, logged as `GIT_CORE-104`, never silently. Every step of the rollback runs, also after an
  earlier step failed with an unchecked exception; the first failure is reported with the later ones suppressed, and the
  branch is deleted before the reservation is released. An unchecked exception during an addition is rolled back in the
  same way and ends as a result, `FAILED` with the failure class.

An invalid configuration value a working-tree operation reads ends `FAILED` with the failure class only. JGit 7.8.0
reads `core.autocrlf` and the other keys of `WorkingTreeOptions` with `Config.getEnum`, which throws
`IllegalArgumentException` for a value that names no constant
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/treewalk/WorkingTreeOptions.java[JGit 7.8.0 `WorkingTreeOptions`]),
wherever a `FileTreeIterator` or a checkout is built: in `commit`, in `worktreeStatus`, in the status check of
`worktreeRemove` and in the checkout of `worktreeAdd`, which is rolled back first.

`worktreeList` skips an administration directory whose `gitdir` or `HEAD` is not present, one being initialized or
removed, so it does not fail the list or the removal of another working tree; a locked working tree with complete files
is listed. A relative `gitdir` is resolved against the administration directory.

[cols="1,3"]
|===
|Operation |Outcomes

|`worktreeAdd` |`OK` with the new working tree; `ALREADY_EXISTS` for a non-empty path, a target claimed by another
addition or an existing branch to create; `BRANCH_CHECKED_OUT` for a branch checked out in the main or another linked
working tree, also for a branch another addition reserved; `NOT_FOUND` for an unknown branch or an unknown, absent or
abbreviated start point; `AMBIGUOUS` with the candidates; `IDENTITY_MISMATCH` for a full commit id the existing branch
is not at, or one that reaches another commit; `PATH_REFUSED` for a path outside the main working tree or the main
working tree itself, for a root that is a linked working tree, for a bare root, and for a target inside the common
directory, its administration area or another linked working tree; `REFUSED_BY_POLICY` for a branch name that is no
valid branch name, also `HEAD`, `@`, a leading `-`, a component ending `.lock` and a name starting `refs/`, and for a
refused capability; `NOT_A_REPOSITORY`; `FAILED`, also for an invalid configuration value the checkout
reads. A refused or failed checkout leaves neither the working tree nor its administration directory behind. A failed
release of the reservation after a complete addition ends `OK` with the working tree kept.
|`worktreeList` |`OK` with the main working tree first, then the linked working trees by administrative name, each with

|`worktreeRemove` |`OK` with the removed root, deleting the clean working tree and its administration directory, a

`WORKTREE_LOCKED`; `PATH_REFUSED` for the main working tree; `REFUSED_BY_POLICY`; `NOT_A_REPOSITORY`; `FAILED`, also
for a repository without a working tree and for an invalid configuration value the status check reads. The registered

registered through a symbolic link is deleted at its real root. The removal is never forced.
|===

The caller of `worktreeRemove` guarantees exclusive use of the working tree until the call returns: the check that the
working tree is clean and its deletion cannot be made one atomic step, so a change written in between is deleted with
it.

`JGitWorktreeOperationsTest` covers every outcome of the three operations, the guards (`invalidBranchNameRefused`,
`linkedRootRefused`, `targetInsideAdministrationRefused`), the reservation of new and existing branches
(`reservedBranchCheckedOut`, `concurrentAdditions`), the comparison by real paths (`removeThroughSymlink`,
`replacedRepositoryAndReusedPath`) and the result contract (`bareRepositoryFails`, `uncheckedFailureRolledBack`,
`branchDeletionResultRead`, `reservationOutlivesRollback`, `heldRefLockReported`, `uncheckedRollbackStepContinues`,
`failedReservationReleaseKeepsWorktree`, `invalidAutoCrlfFails`). `GitWorktreeListCompatibilityTest`
asserts that `git worktree list --porcelain` of an installed Git lists the added working trees with path, branch and
`HEAD`, a locked one `locked` and one whose directory is gone `prunable`, and that `git worktree remove` removes a
working tree the library added. It is skipped through a JUnit assumption when no `git` binary is found; only this test
starts a process, never the library.

[#GDR-CORE-13]
=== GDR-CORE-13: Commit from a Working Tree

* The library must stage every change of a working tree (changed, untracked and deleted files) and commit it in one
  operation, with caller-supplied author, committer and message.

`commit` stages every addition, modification and deletion of the main or a linked working tree and commits it on the
working tree's branch, never signed, whatever the repository configuration asks. Its outcomes are `OK` with the commit,
`NOTHING_TO_COMMIT`, `REFUSED_BY_POLICY` for a present hook, which is never run (`RefusingFS`), `NOT_A_REPOSITORY` and
`FAILED`, also for a repository without a working tree and for an invalid configuration value the staging reads, such
as `core.autocrlf` (<<GDR-CORE-12>>), before anything is committed.

* *Hooks.* JGit 7.8.0 `CommitCommand` runs the `post-commit` hook after it updated the branch and only logs its
  failure
  (link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/api/CommitCommand.java[JGit 7.8.0 `CommitCommand`]),
  so `commit` looks up the `pre-commit`, `commit-msg` and `post-commit` hooks first, with `FS.findHook` of the
  repository's `RefusingFS`, and a present one ends `REFUSED_BY_POLICY` before anything is staged; `RefusingFS` stays
  the guard against running one.
* *Linked roots.* JGit 7.8.0 `FileTreeIterator` reports a directory holding a `.git` entry as a gitlink, which
  `AddCommand` stages
  (link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/treewalk/FileTreeIterator.java[JGit 7.8.0 `FileTreeIterator`]),
  so `commit` removes the root of every registered linked working tree inside the committing one from its index
  before the commit.
* *Reflog.* JGit 7.8.0 `RefDirectory.logFor("HEAD")` resolves to the `logs/HEAD` of the common directory
  (link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/internal/storage/file/RefDirectory.java[JGit 7.8.0 `RefDirectory`]),
  the reflog of the main working tree, so a commit in a linked working tree runs without JGit's reflog and writes its
  `HEAD` entry to `logs/HEAD` of the linked working tree's own git directory and its branch entry to the branch's log
  in the common directory: `HEAD` is a ref of each working tree, the branches are shared
  (link:https://git-scm.com/docs/git-worktree[git-worktree(1)], REFS). The commit and its branch are stored before
  these entries are appended, so no failure of an entry, an unchecked one included, fails the created commit: the
  result stays `OK` with the commit, and the omission is logged as `GIT_CORE-103` with the commit id only. An invalid
  `core.logAllRefUpdates` value is such a case: JGit 7.8.0 `Config.getEnum` throws `IllegalArgumentException` for a
  value that names no constant of `CoreConfig.LogRefUpdates`.

The commit tests of `JGitWorktreeOperationsTest` cover each outcome, `reflogFailureKeepsCommit`,
`invalidLogAllRefUpdatesKeepsCommit` and `uncheckedReflogFailureKeepsCommit` the reflog choice, and its secrets test asserts with a JUL log capture and on the
result details that no author or committer name, e-mail address or message reaches a log message or a detail, and no
raw working-tree path an INFO message.

[#GDR-CORE-14]
=== GDR-CORE-14: Working-Tree Status

* The library must report the status of a working tree as three path sets: `changed` (tracked and modified),
  `untracked` (present and not tracked) and `deleted` (tracked and missing).
* The status must consist of these three path sets and nothing else.

`worktreeStatus` returns the record `WorktreeStatus(changed, untracked, deleted)`: three unmodifiable sets of
repository-relative paths with `/` separators, sorted by path; its outcomes are `OK`, `REFUSED_BY_POLICY`,
`NOT_A_REPOSITORY` and `FAILED`, also for a repository without a working tree and for an invalid configuration value
the status reads, such as `core.autocrlf` (<<GDR-CORE-12>>). `REFUSED_BY_POLICY` follows from the
`RefusingFS` guarantee: the repository is opened on `RefusingFS`, so a capability the policy refuses, such as a process
start, reaches the caller as `REFUSED_BY_POLICY` with the capability as detail (<<GDR-CORE-1>>). The sets are mapped
from JGit's `Status` by its definitions in JGit 7.8.0
(link:https://github.com/eclipse-jgit/jgit/blob/v7.8.0.202609011348-r/org.eclipse.jgit/src/org/eclipse/jgit/api/Status.java[`org.eclipse.jgit.api.Status`]):

[cols="1,3"]
|===
|Set |JGit `Status` categories

|`changed` |`getAdded` (in the index, not in `HEAD`), `getChanged` (changed from `HEAD` to the index), `getModified`
(modified on disk relative to the index), `getConflicting` (in conflict)
|`deleted` |`getRemoved` (in `HEAD`, not in the index), `getMissing` (in the index, not on disk)
|`untracked` |`getUntracked` (neither ignored nor in the index)
|===

Ignored files are in no set. The sets are not disjoint: a file removed from the index but still on disk is both removed
and untracked, so it is in `deleted` and in `untracked`. The union of the three sets is the path union of the seven
categories, the digest input a consumer such as `WorktreeShaDigest` of `pm-provider-git` builds on.

Two behaviours of JGit 7.8.0 are settled by observation, each pinned by a test of `WorktreeStatusTest`:

* *Clean filter.* `StatusCommand` runs the clean filter of a driver configured through the repository's own
  `.gitattributes` when it compares the content of a tracked file whose modification time no longer matches the
  index, so the refusal of its process is reachable through `worktreeStatus`: the status ends `REFUSED_BY_POLICY`
  with `process_execution` (`cleanFilterRefused`).
* *Nested linked root.* For a linked working tree registered inside the main working tree, `worktreeStatus` of the
  main working tree lists the linked root as untracked, since `FileTreeIterator` reports it as a gitlink, while
  `commit` of the main working tree removes every registered linked root from the index (<<GDR-CORE-13>>) and ends
  `NOTHING_TO_COMMIT` (`nestedLinkedRootStatusAgainstCommit`). The divergence is accepted: the status reports the
  working tree as JGit sees it, and leaving the linked roots out is a rule of the commit alone.

`WorktreeStatusTest` covers one scenario per category and the union; `WorktreeOperationsRecordsTest` covers the
record's null checks, its equality over the paths, its defensive copy and its immutability.

[#GDR-CORE-15]
=== GDR-CORE-15: Release of a Branch Reservation

* The library must release the reservation of a branch left by an addition that did not finish, deleting the
  reservation and nothing else.
* The release must start no process (<<GDR-CORE-1>>).

An addition reserves its branch with the reservation file `worktree-branch-<SHA-1 of the full branch name>.lock` in
the common directory (<<GDR-CORE-12>>); the name is the hash of `refs/heads/<branch>`, so no caller string forms a file
name. The reservation is held until the new working tree is complete. A process that ends between the reservation and
its release leaves the file behind, as does a complete addition whose release fails (`GIT_CORE-105`), and every later
addition of that branch ends `BRANCH_CHECKED_OUT` although no working tree has it checked out.

`releaseBranchReservation(root, branch)` takes any working-tree root of the repository and the short branch name as
given to `worktreeAdd`; both are required. It opens the repository on `RefusingFS`, guards the branch name before any
path is derived from it, and deletes the reservation file in the real common directory with one atomic `Files.delete`,
so of two concurrent releases exactly one reports it.

[cols="1,3"]
|===
|Outcome |When

|`OK` |The reservation was deleted; the value is the full branch name `refs/heads/<branch>`
|`NOT_FOUND` |The branch has no reservation; the detail is `branch: no reservation`
|`REFUSED_BY_POLICY` |The branch name is no valid branch name, by JGit 7.8.0 `Repository.isValidRefName` or by the
branch-name rule of an addition (`HEAD`, `@`, a leading `-`, a component ending `.lock`, a name starting `refs/`,
<<GDR-CORE-12>>); the detail names the field only, and no file is deleted
|`NOT_A_REPOSITORY` |The root holds no repository
|`FAILED` |An I/O failure, also a repository without a working tree, with the failure class only
|===

The caller guarantees that no addition of that branch runs, in any process, from the call until it returns. This is a
precondition rather than a check: a reservation held by a running addition cannot be told apart from one a crashed
process left without inspecting processes, which the library does not do, so releasing a live reservation would let a
second addition of the branch past its check. A release is logged as `GIT_CORE-4`, which carries no argument, neither
the branch name nor a path (xref:general.adoc#GDR-NFR-3[GDR-NFR-3]).

The nested test group `ReleaseBranchReservation` of `JGitWorktreeOperationsTest` covers the crashed-process scenario
(`crashedProcessRecovered`: the left reservation blocks the addition, the release returns `OK`, the addition succeeds
again, and the log carries `GIT_CORE-4` without branch name or path), `noReservation`, `invalidBranchNameRefused`,
`notARepository`, `bareRepositoryFails`, the release from a linked root (`fromLinkedRoot`) and the release of the
named reservation only (`onlyNamedReservation`).

[#tests]
== Tests

The tests of `git-core` run on the class path against the fixtures of xref:git-testing.adoc[`git-testing`]; each names
the requirement it checks. Three tests guard contracts that span the module:

* `GitOutcomeSpecificationTest` reads the `GitOutcome` table of xref:general.adoc#GDR-GEN-3[GDR-GEN-3] and asserts that
  its first column lists exactly the constants of `GitOutcome`, in their order, so a constant added without a row, a
  row without a constant, a renamed or a reordered one fails the build.
* `AbsenceContractsTest` of the package `de.cuioss.git.document.core` asserts the `@Nullable` values of the results on
  absences that real operations produce: opening a bare repository yields no working-tree root, `init` an unborn
  branch without head, a detached `HEAD` no branch, a push that creates the remote reference no old id, a failed
  operation no value, and a local-only remote policy no origin.
* `AbsenceContractsTest` of the package `de.cuioss.git.document.core.worktrees` asserts the same for the working-tree
  components: a failed working-tree result carries no value but a detail, the listed main working tree has no name
  while a linked one has its name, a detached addition has no branch but a head, and the main working tree of an
  unborn repository has no head but its branch.

Test doubles are EasyMock doubles (scope `test`, xref:general.adoc#GDR-GEN-1[GDR-GEN-1]): the HTTP connection of the
recording connection factory and the failing signer of `InCoreWriterTest`, the reference update and the partially
mocked repository through which `ReferenceUpdaterTest` observes that compare-and-swap never sets the force flag and
that both operations disable the reflog, and the tracking reference update without a result of
`JGitRepositoryOperationsTest`. Three hand-written doubles stay, each for a reason EasyMock cannot meet:

* `InterceptingTransportProtocol` and `RecordingTransportProtocol` are JGit `TransportProtocol` subclasses registered
  through `Transport.register`, ahead of the built-in protocols. JGit selects them from its registry and opens a real
  `Transport` whose state, the URL, the credentials provider and the timeout the operations set, the test reads back
  through that transport's own getters; a mocked abstract `Transport` would replace exactly the setters and getters
  under observation. `InterceptingTransportProtocol` never handles its own delegate URL, so a marker that also occurs
  in the delegate's path cannot make it select itself again: that recursion was the `StackOverflowError` of
  `publishLosesRace`, which the test now reproduces with such a marker.
* `TestSigner` is a working fake: it computes a signature over the payload JGit hands it, which the written commit
  carries and `TestSigner.verify` checks against the commit's own bytes. An expectation-based double records calls but
  produces no signature a commit could carry.
