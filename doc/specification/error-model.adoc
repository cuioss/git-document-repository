== Results and Outcomes

_See Requirement link:../Requirements.adoc#GDR-GEN-3[GDR-GEN-3: Results Instead of Exceptions]_

*Status:* PLANNED

`GitResult` (taken over from `pm-provider-git`) carries:

[cols="1,3"]
|===
|Component |Semantics

|`outcome` |one value of `GitOutcome`, never null
|`value` |`@Nullable`; present only for a success outcome that yields a value
|`detail` |`@Nullable`; present for every non-success outcome; never contains material that
link:../Requirements.adoc#GDR-NFR-3[GDR-NFR-3] forbids
|===

`GitOutcome` is one closed list in `git-core` for all modules, worktree outcomes included. The list taken over from
`pm-provider-git` is authoritative; the outcomes these requirements name are added where missing:

[cols="1,2"]
|===
|Outcome (category) |Raised by

|success |every operation; reported by the store as saved
|saved locally |save in remote mode when the remote cannot be reached; the commit waits on the local working branch
|conflict |compare-and-swap after the last attempt, merge, save, concurrent change detection
|rejected |push refused by the remote; reference update refused locally (`git-core`, Compare-and-Swap); save after
the last attempt
|lease refused |push with lease (`git-core`); the store retries it and reports rejected after the last attempt
|credentials expired or invalid |fetch, push, save
|refused by policy |remote policy, refused capability (hook or process start)
|not found |reading, cache repository, in-core writing on a missing reference, pseudonym lookup
|unserved |cache repository
|ambiguous |identity resolution
|invalid |schema validation, typed links, personal field without an encryption provider (`git-forms`)
|mismatch |check of the generated output (`git-forms`)
|transition refused, level not met |workflow (`git-forms`, signature level evidence)
|cycle |effective protection needs over `dependsOn` (`git-directory`)
|undecryptable |`git-crypto`; also an erased person entry (`git-directory`)
|key version missing |keyring at start: the key source has no key for the keyring's version (`git-crypto`)
|entry required |first login and interrupted first login (`git-directory`)
|incomplete |erasure whose commit, push or key destruction is still outstanding (`git-crypto`); release whose tag is
still missing after `main` moved (`git-store`)
|no token, imprint mismatch, signature invalid |timestamp verification (`git-timestamp`); a valid token is success
with the time
|===

Exceptions remain for programming errors (violated preconditions) and unexpected I/O failures (for example the
`IO_FAILURE` result of a JGit reference update); they are never used for the outcomes above.

== Null Safety and Platform Modules

_See Requirement link:../Requirements.adoc#GDR-GEN-2[GDR-GEN-2: Java Platform Modules and Null Safety]_

*Status:* PLANNED (`module-info.java` and `@NullMarked` packages exist in the three scaffolds)

* Module names: `de.cuioss.git.document.<suffix>` with suffix `core`, `worktrees`, `testing`, `store`, `forms`,

* An `exports` directive is added together with the first public class of a package.
* `org.jspecify` is `requires static`.

== Logging

_See Requirement link:../Requirements.adoc#GDR-GEN-4[GDR-GEN-4: Logging]_

*Status:* PLANNED

* Each module has one `LogRecord` holder class with its messages; a module prefix makes identifiers unique across the
  reactor.
* Identifiers follow the CUI `LogRecord` ranges per level; each module documents its messages in a log-message
  catalogue beside its code.
* Debug and trace messages use `CuiLogger` directly, without identifiers.

== Secrets

_See Requirement link:../Requirements.adoc#GDR-NFR-3[GDR-NFR-3: Secrets]_

*Status:* PLANNED

The single list of material that must never appear in a result detail, an exception message, a log message or a
commit is link:../Requirements.adoc#GDR-NFR-3[GDR-NFR-3]. The table states where each secret may live. Public keys
(WebAuthn credentials, `allowed_signers`) are no secrets.

[cols="1,2"]
|===
|Material |Rule

|access tokens, passwords |accepted as call parameters only; never stored, logged or put into a detail
|technical push secret (`CredentialsStrategy` `technical`), `timestamp.credentials` |read from the application's
configuration for the call; never logged, put into a detail or committed
|KEK, DEKs, signing keys |held by the key source or in memory; never written in clear text
|HMAC key of the `Session` trailer |configured secret, held in memory; never logged, put into a detail or committed
|`sid` |only as HMAC in the `Session` trailer
|`sub`, e-mail address, person name |only inside the encrypted keyring or the encrypted person entries
|===

Tests assert the rules with a JUL log capture (`cui-test-juli-logger`) and with checks of result details.
