= git-document-repository: `git-timestamp`
:toc: left
:toclevels: 2
:toc-title: Table of Contents
:source-highlighter: highlight.js

`git-timestamp` (module `de.cuioss.git.document.timestamp`, optional) provides the anchor provider `rfc3161` of
`git-store` (xref:git-store.adoc#GDR-STORE-15[GDR-STORE-15]): proofs from an external RFC 3161 timestamp authority,
for organisations that need a proof independent of their own operation. It implements <<GDR-TSA-1>> and
<<GDR-TSA-2>>. It is the alternative to the own
timestamp `signed` of `git-store`. It depends on `git-store` and adds no third-party dependency (see the decision
below). Rationale: xref:../concepts/evidence-and-companion-stores.adoc#_the_anchor[Evidence and Companion Stores, The
Anchor].

*Decision (2026-11-24):* RFC 3161 is implemented by an own dependency-free DER/CMS reader and writer in
`git-timestamp`, on the JDK alone: the signature check, the certificates and the certification path come from
`java.security` (link:https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/security/Signature.html[Java SE
21, `Signature`];
link:https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/security/cert/CertPathValidator.html[Java SE 21,
`CertPathValidator`]), the transport from `java.net.http`
(link:https://docs.oracle.com/en/java/javase/21/docs/api/java.net.http/java/net/http/HttpClient.html[Java SE 21,
`HttpClient`]). This is the choice `git-store` made for SSHSIG
(xref:git-store.adoc#GDR-STORE-12[GDR-STORE-12]). The module adds no dependency, and Bouncy Castle is not used
(xref:general.adoc#GDR-GEN-1[GDR-GEN-1]).

The alternative considered and rejected was Bouncy Castle, whose time-stamp protocol API ships in `bcpkix`
(`org.bouncycastle:bcpkix-jdk18on`, named "Bouncy Castle PKIX, CMS, EAC, TSP, PKCS, OCSP, CMP, and CRMF APIs" in its
POM). Reason: it brings three artifacts instead of none. `bcpkix-jdk18on` 1.87 declares a compile dependency on
`bcutil-jdk18on` 1.87, and that one declares a compile dependency on `bcprov-jdk18on` 1.87
(link:https://repo1.maven.org/maven2/org/bouncycastle/bcpkix-jdk18on/1.87/bcpkix-jdk18on-1.87.pom[`bcpkix-jdk18on`
1.87 POM]; link:https://repo1.maven.org/maven2/org/bouncycastle/bcutil-jdk18on/1.87/bcutil-jdk18on-1.87.pom[`bcutil-jdk18on`
1.87 POM]; both checked on 2026-11-24). The module needs one request and the verification of one token, which the JDK
classes above cover with a small own DER/CMS reader and writer.

[#GDR-TSA-1]
== GDR-TSA-1: RFC 3161 Anchor Provider

* For an object id the provider must obtain an RFC 3161 timestamp token from the configured timestamp authority.
* The module must contain no decision about which commits are anchored and no handling of notes or pushes.

The request is a `TimeStampReq` with `messageImprint` = SHA-256 over the object id as lowercase ASCII hex,
`certReq = true` and a random nonce; the previous proof is not used. The proof is the DER-encoded `TimeStampToken`
(`TimeStampReq`, `messageImprint`, `certReq`, `nonce` and `TimeStampToken` as defined in
link:https://www.rfc-editor.org/rfc/rfc3161[RFC 3161], 2.4). The outcomes are those of the `git-store` list of
xref:general.adoc#GDR-GEN-3[GDR-GEN-3]: an unreachable authority returns unavailable, an error response refused;
`git-store` keeps the subject pending.

[cols="1,2"]
|===
|Configuration |Semantics

|`timestamp.url` |required; HTTPS URL of the timestamp authority
|`timestamp.trust` |required; a non-empty list of paths to PEM files, each holding one or more X.509 certificates of
the authority for verification; each file is read without following a symbolic link and refused above a size limit
|`timestamp.credentials` |optional; a single bearer token for authorities that require authentication, sent as the
header `Authorization: Bearer <token>`
|===

The forms of `timestamp.trust` and `timestamp.credentials` were decided by the owner on 2026-11-24. The bearer token of
`timestamp.credentials` is held in memory only and never appears in a result detail, a log message of the module, an
exception message or a `toString` (xref:general.adoc#GDR-NFR-3[GDR-NFR-3]), and no request that carries it is sent
while the JDK HTTP client would write it to its own log (see the design below); without `timestamp.credentials` no
`Authorization` header is sent.

An authority run inside the organisation counts as independent only when it lies under a responsibility other than
the Git administration and the application's operation; otherwise it proves no more than `signed`.

=== Design of GDR-TSA-1

The module exports the package `de.cuioss.git.document.timestamp` with two public top-level types, `Rfc3161AnchorProvider` and
the `LogRecord` holder `GitTimestampLogMessages`; everything else is package-private: `TimestampConfiguration` (the
section `timestamp`), `TimestampTransport` (the HTTP exchange), `TimeStampRequests` (the request and the reading of the
reply), `TimeStampTokens` (the verification of <<GDR-TSA-2>>) and `Der`, the bounded DER reader and writer.

* *Building the provider.* An application builds the configured provider with the public factory
  `Rfc3161AnchorProvider.from(Map)` from the same already-parsed nested configuration map it hands to
  `StoreConfiguration.from` of `git-store`, which ignores the section `timestamp`. `from` returns a `StoreResult`:
  `OK` with the provider, or `MALFORMED` with a detail naming the missing or malformed key, never its value. The
  application passes the provider to `StoreProviders.select` as a candidate anchor provider, and
  `anchor.provider = rfc3161` selects it.
* *The unconfigured instance.* `module-info.java` provides `Rfc3161AnchorProvider` to `ServiceLoader`. The instance
  `ServiceLoader` creates through the public no-argument constructor has no configuration and never reaches the
  network: its `obtain` answers `REFUSED` and its `verify` `SIGNATURE_INVALID`, each with the detail
  `rfc3161: the section timestamp is not configured`. An application that also hands the loaded providers to
  `select` passes the configured instance in place of the loaded one, since two candidates with one id are refused.
* *The configuration.* `timestamp.url` must be an absolute `https` URL with a host, without user information and, when
  it names a port, with a port of at most 65535. Each file of `timestamp.trust` is read without following a symbolic
  link (`LinkOption.NOFOLLOW_LINKS`), only when it is a regular file of at most 1 MiB, and must be PEM: it must carry at
  least one `-----BEGIN CERTIFICATE-----` block (link:https://www.rfc-editor.org/rfc/rfc7468#section-5.1[RFC 7468,
  5.1]) and every certificate it holds must be an X.509 certificate. A binary DER or PKCS #7 file, which
  `CertificateFactory` would otherwise read as well, is refused. A refusal names the entry by its index
  (`timestamp.trust[<n>] is malformed`). `timestamp.credentials` must be a `token68` of
  link:https://www.rfc-editor.org/rfc/rfc6750#section-2.1[RFC 6750, 2.1], so it cannot break the header.
* *The request.* A `TimeStampReq` of version 1 with the `messageImprint` SHA-256 over the object id as lowercase
  ASCII hex, a random 64-bit nonce from `SecureRandom` and `certReq = TRUE`, without a policy and without extensions;
  the algorithm identifier of SHA-256 carries no parameters, as
  link:https://www.rfc-editor.org/rfc/rfc5754#section-2[RFC 5754, 2] asks of an encoder.
* *The transport.* The request is posted over `java.net.http.HttpClient` with HTTP/1.1, redirects never followed, a
  connect timeout of 10 seconds and one deadline of 30 seconds from sending the request to the end of the reply body,
  as `Content-Type: application/timestamp-query`; the reply is accepted only with the HTTP status 200 and the media
  type `application/timestamp-reply`, the two media types of
  link:https://www.rfc-editor.org/rfc/rfc3161#section-3.4[RFC 3161, 3.4], and at most 1 MiB of it is read. The request
  timeout of `HttpRequest.Builder` covers only the wait for the response headers ("If the response is not received
  within the specified timeout", its Javadoc in OpenJDK 21 and 25), so the body is closed when the deadline passes and
  a stalled body is `UNAVAILABLE`. With `timestamp.credentials` the header `Authorization: Bearer <token>` is sent;
  without it no `Authorization` header is sent.
* *No credentialed request under header logging.* The JDK client writes the complete request headers, `Authorization`
  included and not redacted, to its logger `jdk.httpclient.HttpClient` when the system property
  `jdk.httpclient.HttpClient.log` names the item `headers` or `all` (checked in the sources of
  `jdk.internal.net.http.common.Log` and `Http1Request` of OpenJDK 21 (`jdk21u`) and 25.0.3). A request that carries
  the bearer token is therefore refused before the authority is contacted when the property, read on every request,
  names either item: `REFUSED` with the detail
  `rfc3161: credentialed requests are refused while HTTP client header logging is enabled`, logged as
  `GIT_TIMESTAMP-101`. A request without a token is sent as usual. The JDK reads the property once, when its logging is
  first initialised; the check reads it on every request, so a property set later refuses more than needed, and a
  property cleared after the JDK read it is not seen: an application that enables the client's header logging must
  leave the property set.
* *The reply.* The token is granted only with the `PKIStatus` `granted` (0) or `grantedWithMods` (1); the token must
  repeat the nonce and the imprint of the request (RFC 3161, 2.4.2), and it must verify against `timestamp.trust` by
  every rule of <<GDR-TSA-2>> before `obtain` returns it: the anchoring engine of `git-store` publishes a proof it is
  handed without verifying it and does not ask again for a subject that has one, so a proof that would not verify
  must never be returned. The proof is the DER encoding of the `TimeStampToken`. The commit time and the previous proof are not used: the authority keeps its own time, and
  `rfc3161` forms no chain.
* *The outcomes.* An authority that cannot be reached (connection refused, timeout or another I/O failure) is
  `UNAVAILABLE`; an error status, another HTTP status than 200, another media type, a reply larger than the limit or
  unreadable, a token with another nonce or imprint, and a token that does not verify against `timestamp.trust` are
  `REFUSED`. `git-store` keeps the subject pending on
  either. A token obtained is logged as `GIT_TIMESTAMP-1`, an unavailable authority as `GIT_TIMESTAMP-100` and a
  refusal as `GIT_TIMESTAMP-101`, with the repository alias, the object id and the fixed detail only
  (xref:../../git-timestamp/doc/LogMessages.adoc[log-message catalogue]).
* *No secret leaves the module* (xref:general.adoc#GDR-NFR-3[GDR-NFR-3]): no result detail, log message or
  `toString` of `TimestampConfiguration`, `TimestampTransport` or `Rfc3161AnchorProvider` carries the URL of the
  authority, the bearer token, the body of a reply or the content of a certificate file.

Tests: `Rfc3161ObtainTest` (the request, the fresh nonce, the bearer header and its absence, every refusal including a
reply of one octet above 1 MiB beside one of exactly 1 MiB, a token that does not verify, the defined and undefined
`PKIStatus` values and the fields of `PKIStatusInfo` and `TSTInfo`, a body stalled past the deadline, the unreachable
authority, the unconfigured instance and the `provides` directive), `TimestampConfigurationTest` (the keys
and refusals of the section `timestamp`), `DerTest` (the bounds of the DER
reader) and `TimestampSecretsTest` (GDR-NFR-3, including no credentialed request under the values `headers` and `all`
of `jdk.httpclient.HttpClient.log`, and a request sent under `errors` and without the property). They run against an in-process authority on the JDK `HttpsServer`
bound to the loopback address, with certificates generated at run time, so no test needs network access and no
private key is committed.

[#GDR-TSA-2]
== GDR-TSA-2: Timestamp Verification

* The module must verify a stored token against the object id and `timestamp.trust`, and report the time the token
  proves, or imprint mismatch or signature invalid (also for a token that cannot be read).

=== Design of GDR-TSA-2

`Rfc3161AnchorProvider.verify` hands the stored token to `TimeStampTokens`, which accepts it only when every rule below
holds, each checked with `java.security` alone
(link:https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/security/Signature.html[Java SE 21,
`Signature`];
link:https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/security/cert/CertPathValidator.html[Java SE 21,
`CertPathValidator`]):

. The token is a CMS `ContentInfo` of `id-signedData` whose `SignedData` encapsulates content of the type
  `id-ct-TSTInfo` (link:https://www.rfc-editor.org/rfc/rfc3161#section-2.4.2[RFC 3161, 2.4.2];
  link:https://www.rfc-editor.org/rfc/rfc5652#section-5.1[RFC 5652, 5.1]). Between the encapsulated content and the
  signer infos it carries at most one `certificates [0]` and then at most one `crls [1]`, in that order (RFC 5652,
  5.1); the CRLs are not used.
. The `SignedData` carries exactly one `SignerInfo`; RFC 3161, 2.4.2 requires a single signer.
. The `SignerInfo` has signed attributes (link:https://www.rfc-editor.org/rfc/rfc5652#section-5.3[RFC 5652, 5.3])
  with exactly one `contentType` of the single value `id-ct-TSTInfo` and exactly one `messageDigest` equal to the
  digest of the encapsulated `TSTInfo` under the `digestAlgorithm` of the `SignerInfo` (RFC 5652, 11.1, 11.2 and 5.4).
. The signed attributes carry an ESS `signingCertificate`
  (link:https://www.rfc-editor.org/rfc/rfc2634#section-5.4[RFC 2634, 5.4], its certificate hash SHA-1), a
  `signingCertificateV2` (link:https://www.rfc-editor.org/rfc/rfc5035#section-3[RFC 5035, 3], its hash SHA-256 by
  default) or both, each at most once, as RFC 3161, 2.4.2 and
  link:https://www.rfc-editor.org/rfc/rfc5816#section-2.2[RFC 5816, 2.2.1] require; two present attributes are
  evaluated independently (link:https://www.rfc-editor.org/rfc/rfc5035#section-2[RFC 5035, 2], the new text of RFC 2634, 5.4). The first
  certificate identifier of each names the signer certificate by hash; the certificate is looked up among the
  certificates the token carries and those of `timestamp.trust`, and must match every such hash and the `sid` of the
  `SignerInfo` (issuer and serial number, or subject key identifier). Further certificate identifiers of an attribute
  are not evaluated: trust comes only from `timestamp.trust`, so ignoring them cannot widen it.
. The signature verifies over the DER of the signed attributes under the explicit SET OF tag (RFC 5652, 5.4), with
  ECDSA or RSA PKCS #1 v1.5 and SHA-256, SHA-384 or SHA-512, the hash of the signature algorithm equal to the digest
  algorithm (link:https://www.rfc-editor.org/rfc/rfc5754#section-3[RFC 5754, 3.2 and 3.3]); any other algorithm is
  refused.
. The signer certificate carries the extended key usage extension, critical, with the single purpose
  `id-kp-timeStamping` (link:https://www.rfc-editor.org/rfc/rfc3161#section-2.3[RFC 3161, 2.3]); when it carries the
  key usage extension, that holds `digitalSignature` or `nonRepudiation`, the key usages consistent with
  `id-kp-timeStamping` (link:https://www.rfc-editor.org/rfc/rfc5280#section-4.2.1.12[RFC 5280, 4.2.1.12], which
  processes both extensions independently, and 4.2.1.3). A certificate without the key usage extension is not
  restricted by it.
. The signer certificate is one of `timestamp.trust` and valid at the time the token states, or has a certification
  path to a certificate of `timestamp.trust` at that time
  (link:https://www.rfc-editor.org/rfc/rfc5280#section-6[RFC 5280, 6]): `CertPathBuilder` of the type PKIX builds it
  to the exact signer certificate from the certificates the token carries, so two intermediates of one subject name
  are both tried, and `CertPathValidator` of the type PKIX validates it. Revocation checking is off: a verification
  reaches no network, and the token holds no revocation status of the time of stamping.

A token that cannot be read, or that breaks any of these rules, is `SIGNATURE_INVALID` with a fixed detail naming the
rule, never a value of the token. A token that passes them and whose imprint is not SHA-256 over the lowercase hex of
the object id is `IMPRINT_MISMATCH`; otherwise the result is `OK` with the `genTime` of the token, the time it proves.
`rfc3161` forms no chain: the previous proof is ignored and `CHAIN_BROKEN` is never returned. Every rejected proof is
logged as `GIT_TIMESTAMP-102` with the object id, the outcome and the detail. The same provider instance serves the
anchor verification of `git-store`, `AnchorVerification.verifyAnchors(repository, provider)`
(xref:git-store.adoc#GDR-STORE-17[GDR-STORE-17]).

Tests: `Rfc3161VerifyTest` (a token of the authority verifies with its `genTime`; a token for another object id is
`IMPRINT_MISMATCH`; a flipped signature byte, a signer outside `timestamp.trust`, a signer without
`id-kp-timeStamping`, a signer whose key usage is `keyEncipherment` only (through a path and trusted directly), a token
whose signer certificate is neither carried nor trusted, two certificates fields, CRLs before certificates, two
`signingCertificateV2` attributes or two signing certificate attributes naming different certificates, a truncated
token, random octets and no octets are `SIGNATURE_INVALID`; a token without its certificate verifies when
`timestamp.trust` holds the signer, a token with both signing certificate attributes verifies, and a path is built past
an intermediate of the same subject name) and `Rfc3161AnchoringTest`, end to end with `anchor.provider = rfc3161`: `StoreProviders.select` with the
configured provider, a release onto a `git-testing` local remote, `StoreWriter.anchor()` and
`AnchorVerification.verifyAnchors` reporting a complete anchoring with every proof verified, and an unreachable
authority that leaves the release commit pending without failing the release.

[#native-image]
== Native Image

`git-timestamp` ships no native-image metadata (xref:general.adoc#GDR-NFR-4[GDR-NFR-4]): its main code uses no
reflection, resource or resource bundle of its own, and a consumer receives the metadata of `git-core` through the
dependency, on the same grounds as `git-store`. The reasons and what stays unchecked are stated in GDR-NFR-4.
