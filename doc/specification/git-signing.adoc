== Overview

_See Requirement link:../Requirements.adoc#GDR-GEN-1[GDR-GEN-1: Module Layering and Dependency Isolation]_

*Status:* PLANNED

`git-signing` (module `de.cuioss.git.document.signing`, not yet created, optional) signs commits, writes the identity
and approval trailers, verifies passkey approvals and checks signatures. It depends on `git-store`. A WebAuthn
verification library is open and needs the owner's approval. Rationale:
xref:../concepts/identity-and-signing.adoc[Identity and Signing].

== Commit Signature

_See Requirement link:../Requirements.adoc#GDR-SIGN-1[GDR-SIGN-1: Commit Signature]_

*Status:* PLANNED

* The module implements JGit's signer interface _(unverified: `org.eclipse.jgit.lib.Signer` in recent versions)_ and
  delegates the signing operation to a `SigningKeySource`.
* `SigningKeySource` implementations: KMS, HSM (PKCS#11), key file. The application never holds the private key when
  KMS or HSM is used.
* `signing.format`: `ssh` or `gpg` (required). Whether the JGit version in use writes SSH signatures is to verify
  _(unverified)_.

== Identity Trailers

_See Requirement link:../Requirements.adoc#GDR-SIGN-2[GDR-SIGN-2: Identity Trailers]_

*Status:* PLANNED

[cols="1,2,2"]
|===
|Trailer |Value |Source

|`Actor` |pseudonym (`p-…`) |`git-crypto`
|`Actor-Issuer` |issuer URL of the identity provider |token claim `iss`
|`Auth-Time` |ISO 8601 UTC, seconds precision |token claim `auth_time`
|`Auth-Context` |`acr` value; `amr` values comma-separated |token claims `acr`, `amr`
|`Session` |`hmac:` + hex HMAC-SHA-256 of `sid` under a configured key |token claim `sid`
|`Actor-Client` |OAuth client id of a delegated client; absent when the user acted directly |token claim `azp` or
`client_id` of the delegated token
|===

The caller supplies the claims; the module never receives the access token. `sub` and `sid` are refused as trailer
values.

== Portable Approvals

_See Requirement link:../Requirements.adoc#GDR-SIGN-3[GDR-SIGN-3: Portable Approvals]_

*Status:* PLANNED

----
Release <collection>/<id>

Approved-by: p-91c2d0a7e1b3 (role:ciso)
Review: https://git.example/sec/register/pull/17
----

One `Approved-by` per approval; `Review` only when the release came through a pull or merge request. The caller
supplies the approvals collected from the Git server.

When the Git server creates the release merge (protected `main`), the merge commit is the server's and carries no
signature of the application. The library then writes the same `Approved-by` and `Review` lines as a note on that merge
commit under `refs/notes/approvals`, in a notes commit signed by the application. The note is written when a fetch
shows the new tip of `main` (outbox consumer `approvals` of `git-store`); in remote mode the notes reference is pushed
right after.

== Step-Up Evidence

_See Requirement link:../Requirements.adoc#GDR-SIGN-4[GDR-SIGN-4: Step-Up Evidence (Level 2)]_

*Status:* PLANNED

Level 2 is met when `Auth-Context` contains an `amr` value from `signing.mfa-amr` (configured list, for example `mfa`,
`otp`, `hwk`) or an `acr` value from `signing.mfa-acr`, and `now - Auth-Time <= signing.step-up-max-age` (ISO 8601
duration, required).

== Passkey Approvals

_See Requirement link:../Requirements.adoc#GDR-SIGN-5[GDR-SIGN-5: Passkey Approvals (Level 3)]_

*Status:* PLANNED

[cols="1,3"]
|===
|Element |Specification

|Registration file |`keys/webauthn.yaml`: per pseudonym a list of credential ids and COSE public keys with
`registered` and optional `retired` dates; changed only by signed commits
|Challenge |SHA-256 over the raw commit id followed by a 16-byte random nonce; the nonce is issued for one approval,
used once, and expires after `signing.challenge-ttl` (ISO 8601 duration, required)
|Acceptance |client data `type` is `webauthn.get`; client data `origin` is in `signing.allowed-origins`; client data
`challenge` equals the issued challenge; the nonce is unused and not expired; signature verifies with a registered,
non-retired key; flags UP and UV set; RP id hash matches the configured `signing.rp-id`
|Storage |note on the commit under `refs/notes/approvals`: YAML with pseudonym, credential id, nonce, authenticator data,
client data JSON and signature, base64. A verifier recomputes the challenge from the commit id and the nonce.
|===

== Signature Verification

_See Requirement link:../Requirements.adoc#GDR-SIGN-6[GDR-SIGN-6: Signature Verification]_

*Status:* PLANNED

* `allowed_signers` at the repository root, in the format of Git's SSH signature verification (principal, options
  `valid-after` / `valid-before`, public key).
* Trust root: the verifier reads the application's signing keys from its own configuration (`signing.trust-root`), not
  from the repository. A version of `allowed_signers` is trusted only when the commit that introduced it is signed by a
  key the previous trusted version lists; the first version must be signed by a key of the trust root. A Git
  administrator who replaces the file therefore cannot make own keys trusted.
* A merge commit the Git server created on `main` passes when both parents pass and an approval note signed by the
  application exists for it (Portable Approvals).
* `verify(ref)` walks the commits of the reference and returns those without a signature valid at their commit time.
* CI without the application: with `signing.format = ssh`, `git -c gpg.ssh.allowedSignersFile=allowed_signers
  verify-commit <id>` checks a commit with a stock git installation.
