== Overview

_See Requirement link:../Requirements.adoc#GDR-GEN-1[GDR-GEN-1: Module Layering and Dependency Isolation]_

*Status:* PLANNED

`git-signing` (module `de.cuioss.git.document.signing`, not yet created, optional) signs commits, writes the identity
and approval trailers, verifies passkey approvals and checks signatures. It depends on `git-store` and provides two
of its service provider interfaces: `SignatureLevelVerifier` (evidence of a signature level for a transition) and
`CommitTrailerContributor` (identity and approval trailers), and the anchor provider `signed` (Own Timestamp); see
xref:git-store.adoc#_service_provider_interfaces[git-store, Service Provider Interfaces]. A WebAuthn verification
library is open and needs the owner's approval. Rationale: xref:../concepts/identity-and-signing.adoc[Identity and
Signing].

== Commit Signature

_See Requirement link:../Requirements.adoc#GDR-SIGN-1[GDR-SIGN-1: Commit Signature]_

*Status:* PLANNED

* The module implements JGit's signer interface `org.eclipse.jgit.lib.Signer` (since JGit 7.0) and delegates the
  signing operation to a `SigningKeySource`.
* `SigningKeySource` implementations: KMS, HSM (PKCS#11), key file. The application never holds the private key when
  KMS or HSM is used.
* `signing.format`: `ssh` or `openpgp` (required), the values of Git's `gpg.format` and of JGit's
  `GpgConfig.GpgFormat`. JGit 7.8.0 ships a signer and a verifier for each format in separate artifacts:
  `org.eclipse.jgit.ssh.apache` for `ssh` and `org.eclipse.jgit.gpg.bc` (Bouncy Castle) for `openpgp`, both in internal
  packages and registered through `ServiceLoader`. Whether `git-signing` uses them, and therefore adds the artifact of
  the configured format as a dependency, is open and needs the owner's approval.
* Every selectable format is verifiable (Signature Verification).

== Identity Trailers

_See Requirement link:../Requirements.adoc#GDR-SIGN-2[GDR-SIGN-2: Identity Trailers]_

*Status:* PLANNED

[cols="1,2,2"]
|===
|Trailer |Value |Source

|`Actor` |pseudonym (`p-…`)
|the `PersonDirectory` of `git-store` (`local` of `git-directory` or an operator's provider)
|`Actor-Issuer` |issuer URL of the identity provider |token claim `iss`
|`Auth-Time` |ISO 8601 UTC, seconds precision |token claim `auth_time`
|`Auth-Context` |`acr=<acr>; amr=<amr>,<amr>…` (for example `acr=urn:example:mfa; amr=pwd,otp`); a part is left out
when its claim is absent |token claims `acr`, `amr`
|`Session` |`hmac:` + hex HMAC-SHA-256 of `sid` under a configured key |token claim `sid`
|`Actor-Client` |OAuth client id of a delegated client; absent when the user acted directly |token claim `azp` or
`client_id` of the delegated token
|===

The caller supplies the claims; the module never receives the access token. `sub` and `sid` are refused as trailer
values. The HMAC key of `Session` is a configured secret (see xref:error-model.adoc#_secrets[Error Model, Secrets]).

== Portable Approvals

_See Requirement link:../Requirements.adoc#GDR-SIGN-3[GDR-SIGN-3: Portable Approvals]_

*Status:* PLANNED

----
Release <collection>/<id>

Approved-by: p-91c2d0a7e1b3 (role:ciso)
Review: https://git.example/sec/register/pull/17
----

One `Approved-by` per approval; `Review` only when the release came through a pull or merge request. The caller
supplies the approvals collected from the Git server.

When the Git server creates the release merge (protected `main`), the merge commit is the server's and carries no
signature of the application. The library then records the same approvals as an entry of `kind` `merge` in the note
on that merge commit under `refs/notes/approvals`, in a notes commit signed by the application. The note is written
when a fetch shows the new tip of `main` (outbox consumer `approvals` of `git-store`); in remote mode the notes
reference is pushed right after, as a system commit with the technical user's credentials.

A commit has at most one note under `refs/notes/approvals`: a YAML document with a list `approvals`. Each entry
carries a `kind` (`merge` or `passkey`) and the fields of that kind; binary values are base64.

[source,yaml]
----
approvals:
  - kind: merge
    approved-by:
      - { actor: p-91c2d0a7e1b3, role: "role:ciso" }
    review: https://git.example/sec/register/pull/17
  - kind: passkey
    actor: p-91c2d0a7e1b3
    credential-id: <base64>
    nonce: <base64>
    authenticator-data: <base64>
    client-data-json: <base64>
    signature: <base64>
----

A writer reads the note, appends its entry and writes the note back in a new notes commit that moves
`refs/notes/approvals` by compare-and-swap (`git-core` Notes); on a lost race it reads the new note and appends again.
A second approval therefore never replaces the first.

In remote mode every write of `refs/notes/approvals` is pushed right after, as a system commit with the technical
user's credentials. Before the push the writer fetches the remote notes reference and merges the local notes into it,
with JGit's `NoteMapMerger` (`org.eclipse.jgit.notes`; base: the merge base of the two notes commits) and a note
merger of this module: for a commit with a note on both sides the merged note holds the union of the `approvals`
entries, an entry present on both sides once. The writer commits the merged notes (parents: the local and the fetched
notes commit), signed by the application, moves the local reference by compare-and-swap and pushes with lease, the
expected remote id being the fetched one. On a rejection it repeats from the fetch, up to the configured number of
attempts (`save.max-attempts` of `git-store`). An approval written on another instance is therefore never replaced.

== Step-Up Evidence

_See Requirement link:../Requirements.adoc#GDR-SIGN-4[GDR-SIGN-4: Step-Up Evidence (Level 2)]_

*Status:* PLANNED

Level 2 is met when `Auth-Context` contains an `amr` value from `signing.mfa-amr` (configured list, for example `mfa`,
`otp`, `hwk`) or an `acr` value from `signing.mfa-acr`, and `now - Auth-Time <= signing.step-up-max-age` (ISO 8601
duration, required).

== Passkey Approvals

_See Requirement link:../Requirements.adoc#GDR-SIGN-5[GDR-SIGN-5: Passkey Approvals (Level 3)]_

*Status:* PLANNED

[cols="1,3"]
|===
|Element |Specification

|Registration file |`keys/webauthn.yaml`: per pseudonym a list of credential ids and COSE public keys with
`registered` and optional `retired` dates; changed only by signed commits
|Challenge |SHA-256 over the commit id as lowercase ASCII hex followed by a 16-byte (128-bit) random nonce, the same
form of the commit id as the timestamp imprint of `git-timestamp`; the nonce is issued for one approval, used once,
and expires after `signing.challenge-ttl` (ISO 8601 duration, required)
|Acceptance |client data `type` is `webauthn.get`; client data `origin` is in `signing.allowed-origins`; client data
`challenge` equals the issued challenge; the nonce is unused and not expired; the RP ID hash of the authenticator data
matches the configured `signing.rp-id`; flags UP and UV set; the signature verifies with a key that is registered and
not retired at the time of the approval. A later retirement leaves earlier approvals valid.
|Storage |an entry of `kind` `passkey` in the note on the commit under `refs/notes/approvals` (Portable Approvals). A
verifier recomputes the challenge from the commit id and the nonce, and checks the key against the version of
`keys/webauthn.yaml` valid at the time of the notes commit.
|===

== Signature Verification

_See Requirement link:../Requirements.adoc#GDR-SIGN-6[GDR-SIGN-6: Signature Verification]_

*Status:* PLANNED

* Key files at the root of `main`, one per format; a signature passes when it verifies with a key of the file that
  is valid at the commit time:
** `ssh`: `allowed_signers`, in the format of Git's SSH signature verification (principal, options `valid-after` /
   `valid-before`, public key).
** `openpgp`: `allowed_keys.asc`, the ASCII-armored public keys; a key is valid between its creation time and its
   expiry or revocation as recorded in the file.
* Trust root: the verifier reads the application's signing keys from its own configuration (`signing.trust-root`), not
  from the repository. A version of a key file is trusted only when the commit that introduced it is signed by a key
  the previous trusted version lists; the first version must be signed by a key of the trust root. A Git
  administrator who replaces the file therefore cannot make own keys trusted.
* A merge commit the Git server created on `main` passes when both parents pass and an approval note signed by the
  application exists for it (Portable Approvals).
* `verify(ref)` walks the commits of the reference and returns those without a signature valid at their commit time.
* CI without the application: `verify(ref)` needs only the repository and `signing.trust-root`, so a CI job can run
  it without the application. With `signing.format = ssh`, `git -c gpg.ssh.allowedSignersFile=<file> verify-commit <id>`
  also checks a single signature with a stock Git installation, but it applies no trust-root chain: it trusts the
  given file as it is. A CI job using it must therefore take the file from a trusted source (the chain check above),
  never from the commit under test.

== Own Timestamp

_See Requirement link:../Requirements.adoc#GDR-SIGN-7[GDR-SIGN-7: Own Timestamp]_

*Status:* PLANNED

The provider `signed` of `git-store`'s `AnchorProvider` (see xref:git-store.adoc#_anchoring[git-store, Anchoring]).
It proves on a best-effort basis that an object existed at a time, without an external service. Rationale and limits:
xref:../concepts/evidence-and-companion-stores.adoc#_the_anchor[Evidence and Companion Stores, The Anchor].

* Statement: UTF-8 text, one field per line in this order, each line ended by LF:
+
----
anchor signed 1
object <object id, lowercase hex>
time <UTC, ISO 8601 with seconds, for example 2026-11-16T09:30:00Z>
sequence <n>
previous <SHA-256 of the previous proof, lowercase hex, or "none" for sequence 1>
----
* Proof: the statement followed by a detached signature over it in the configured `signing.format`: for `ssh` an
  armored SSH signature with the namespace `git-document-anchor`
  (https://github.com/openssh/openssh-portable/blob/master/PROTOCOL.sshsig[PROTOCOL.sshsig]); for `openpgp` an
  ASCII-armored detached signature.
* Key: `anchor.signed.key-source`, a `SigningKeySource` of its own (KMS, HSM, key file). The start fails when its
  public key equals that of the commit-signing key. The key should lie under a responsibility other than the Git
  administration, for example the security team's KMS policy.
* Sequence and chain: `previous` is the proof the store passes (see xref:git-store.adoc#_proofs_as_notes[git-store,
  Proofs as Notes]); `sequence` is one more than its sequence, 1 without one.
* Clock: the provider refuses (outcome refused, reason clock behind) when its time is earlier than the time of the
  previous proof, or earlier than the commit time of the subject minus `anchor.signed.max-clock-skew` (default
  `PT5M`).
* Log copy: every proof is written as a `LogRecord` at INFO with the repository alias, the object id, the time, the
  sequence number and the SHA-256 of the proof. The operator's log pipeline carries it to a store outside the Git
  administration, for example the SIEM.
* Verification: the signature against `anchor.signed.trust` (the anchor keys with their validity periods, from the
  verifier's configuration, never from the repository); the statement's object id against the subject; the chain
  against the previous proof (sequence one more, `previous` equal to its hash, time not earlier). Outcomes: the time
  of the statement, signature invalid, imprint mismatch, chain broken. With `ssh`, a single proof can also be checked
  with a stock OpenSSH installation: `ssh-keygen -Y verify -f <allowed signers> -I <identity> -n git-document-anchor
  -s <signature file> < <statement file>` (https://man.openbsd.org/ssh-keygen.1[ssh-keygen(1)]).

[cols="1,2"]
|===
|Configuration |Semantics

|`anchor.signed.key-source` |required when `signed` is active; the anchor key, never the commit-signing key
|`anchor.signed.trust` |required for verification; the public anchor keys with validity periods
|`anchor.signed.max-clock-skew` |ISO 8601 duration; default `PT5M`
|===
