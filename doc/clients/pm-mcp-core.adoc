`pm-mcp-core` is the core repository of the product PM-MCP. It is a client of the foundation modules `git-core` and
`git-testing`, not a part of these libraries. Its module `pm-provider-git` holds the hardened JGit code from which the
foundation is taken, and after the switch-over it depends on `git-core`, including its working-tree package.

This document collects everything that concerns this client: why the foundation is shared with it, the inventory of
`pm-provider-git`, what moves where, what changes in `pm-mcp-core`, and the order of the switch-over. The library
documentation does not depend on it; the foundation itself is described in
xref:../concepts/module-structure.adoc#_the_foundation_modules[Module Structure, The Foundation Modules]. The decision
is xref:../adr/0004-The_libraries_are_one_reactor_of_separately_consumed_modules_and_the_JGit_foundation_is_shared_with_its_clients.adoc[ADR-0004].

== A Shared Foundation with `pm-provider-git`

`pm-provider-git` and the document store stand on one foundation instead of each carrying its own copy.

Gains:

* the hardening and the transport exist once, so a security fix reaches both products;
* one test base runs against real local remotes;
* `pm-provider-git` shrinks to a facade, an adapter and a digest.

Constraints:

* *The foundation does not live in `pm-mcp-core`.* That repository is proprietary, publishes only to the
  organisation's registry and deploys `SNAPSHOT` versions that are never released. Another project must not hang on
  that life cycle. The foundation lives in `git-document-repository` and is released with real versions to Maven
  Central.
* *Two life cycles are coupled.* PM-MCP is pre-1.0 and changes contracts without deprecation cycles. The foundation
  therefore stays small and stable and carries no domain term of either side.
* *Licence.* The code taken over from `pm-provider-git` has to be released for the open-source licence of
  `git-document-repository` (Apache License 2.0). The other direction needs no release: a work that merely links to the
  interfaces of the libraries is no Derivative Work of them (§ 1), every licensee may reproduce and distribute the
  libraries (§ 2), and a redistribution carries a copy of the licence and keeps the notices (§ 4)
  (link:https://www.apache.org/licenses/LICENSE-2.0[Apache License 2.0], §§ 1, 2, 4). A proprietary product may
  therefore depend on the libraries under these conditions.

== Inventory of `pm-provider-git`

The inventory was taken from the sources on 2026-11-12. The module holds about 2,000 lines of production code and
3,800 lines of tests. Its only dependency on another module of the product lies in a single class,
`JGitSourceRepository`, which uses three types of `pm-core`.

[cols="2,3,2"]
|===
|Class |What it does |Dependency on `pm-core`

|`RefusingFS`
|A JGit file system that refuses hooks and process starts (`CapabilityRefusedException`)
|none

|`RemotePolicy`
|The permitted remote: an HTTPS origin, or local only; checked before every fetch and push
|none

|`GitIdentity`
|Full and abbreviated commit ids, branch, runtime and remote-branch references, resolution and ambiguity of a name
|none

|`GitResult`, `GitOutcome`
|The result type (outcome, value, detail) and the closed list of outcomes, worktree outcomes included
|none

|`GitOperations`
|The contract: open, init, log, commit, fetch, push with lease, the linked working trees, the worktree digest, the

|none

|`JGitOperations`
|The variant of the contract on JGit, in process, without a `git` installation
|none

|`LinkedWorktrees`
|The administration files of git's linked working trees, read and written natively, because JGit has no command

xref:../concepts/storage-engine.adoc#_no_working_trees[Storage Engine, No Working Trees])
|none

|`WorktreeShaDigest`
|The framing of `git.worktree-sha` version 1, fixed by the job runtime specification of PM-MCP

|The adapter of the cache repository to the corpus interface `SourceRepository` of `pm-core`
|`SourceRepository`, `SourceManifest`, `SourceFetch`

The module logs nothing and carries no native-image metadata of its own. Within `pm-mcp-core` no module depends on
it; its consumer is the assembly in `plan-marshall-mcp`. All of it is generic except the corpus adapter and the
digest format. Even the cache repository is a generic mechanism: one commit fetched into a bare cache under a remote
policy, a file read at that commit.

== What Moves Where

* *`git-core`* takes `RefusingFS`, `RemotePolicy`, `GitIdentity`, `GitResult` and `GitOutcome`, and from
  `GitOperations`/`JGitOperations` the repository part as `RepositoryOperations`/`JGitRepositoryOperations`: open and
  init, the log, fetch and push (with credentials and lease), and the cache repository. The list of `GitOutcome` is
  reconciled with the outcomes the requirements of the libraries name (see <<_what_git_core_took_and_changed>>).
* *The package `de.cuioss.git.document.core.worktrees` of `git-core`* takes `LinkedWorktrees`, adding, listing and
  removing working trees, and the commit from a working tree, and offers the working-tree status on which
  `WorktreeShaDigest` builds.
* *`git-testing`* takes the generator of the transport credential (`GitCredentialGenerator`, `GitGenerators`, which lie in
  the test artifact `pm-provider-git:tests`).
* *`pm-provider-git` keeps* `JGitSourceRepository`, `WorktreeShaDigest` with its ported tests and fixtures (its
  framing is a contract of PM-MCP; it then builds on the working-tree status of `git-core`), and `GitOperations`
  as a facade over the two new interfaces, so the assembly keeps its interface for the first step.

Every class is taken over as a plain copy without history (owner's decision, 2026-11-17): the commit that brings it
names `pm-mcp-core`, the source path and the commit it was copied from. `git-core` holds the copy of
`pm-providers/pm-provider-git/src/main/java/de/planmarshall/provider/git/` at commit `287e1a86`, package-renamed to
`de.cuioss.git.document.core`; its package `de.cuioss.git.document.core.worktrees` holds `LinkedWorktrees` from
the same path and commit, package-renamed and since changed (see
<<_what_the_worktrees_package_took_and_changed>>); `git-testing` holds the copy of the generator. The taken-over
code is released under the Apache License 2.0 of `git-document-repository`.

The tests move with the classes they test. Test classes that cover both sides (`JGitOperationsTest`,
`GitOperationsContractTest`, `GitOperationsRecordsTest`, `AbsenceContractsTest`) are split along the interfaces. The
repository part of each moves to `git-core`, rewritten onto the fixtures of `git-testing`; its commits are written
through an `ObjectInserter` (the helper `TestCommits`) instead of from a working tree. `GitOperationsContractTest`
tests only the source's `GitCredential` record, which `git-core` does not take, so no part of it moves. The worktree
part of `JGitOperationsTest`, `GitOperationsRecordsTest` and `AbsenceContractsTest` moves to the package
`de.cuioss.git.document.core.worktrees` of `git-core`, likewise rewritten onto the fixtures; the main working tree of its tests is a clone of a fixture
repository.

[[_what_git_core_took_and_changed]]
=== What `git-core` Took and Changed

`git-core` changed the copied code where the requirements of the libraries demand it
(xref:../specification/git-core.adoc[`git-core`]); the facade of `pm-provider-git` maps the differences at the
switch-over:

* *Outcomes.* The constants of `GitOutcome` carry the names of the outcomes of
  xref:../specification/general.adoc#GDR-GEN-3[GDR-GEN-3]; no alias of an old name is kept. The mapping is in the
  table below.
* *Credentials.* A JGit `CredentialsProvider` is passed per call instead of the source's `GitCredential` record.
* *Identity.* `GitIdentity` has no `runtimeRef` (`refs/pm-mcp/`, a term of PM-MCP) and gains `tagRef`, `abbreviate` and
  `candidates`; `log` puts the candidates of an ambiguous name into the detail.
* *Hardening.* `CapabilityRefusedException` is a top-level class instead of a class nested in `RefusingFS`; every
  repository the operations open or create is built on `RefusingFS`.
* *Operations.* `open` accepts the git directory of a bare repository; `init` is a method of its own; the bare clone
  of a remote (`cloneIfMissing`) is new; `fetchCommit` writes the reference `refs/pinned/<id>` itself, because JGit
  7.8.0 ignores the destination of a fetch refspec whose source is an object id (`FetchProcess.expandSingle`); the
  operations log through `CuiLogger`.
* *Write path.* In-core writing, compare-and-swap, the in-core merge and the notes
  (xref:../specification/git-core.adoc#GDR-CORE-4[GDR-CORE-4], xref:../specification/git-core.adoc#GDR-CORE-5[GDR-CORE-5],
  xref:../specification/git-core.adoc#GDR-CORE-6[GDR-CORE-6], xref:../specification/git-core.adoc#GDR-CORE-10[GDR-CORE-10])
  have no counterpart in the inventory above, so the facade maps none of their outcomes. A client that adopts them
  meets these outcomes besides the ones the table below maps: `REFUSED_BY_POLICY` for a reference name JGit's
  `Repository.isValidRefName` rejects, before any file is touched; `REJECTED` with the detail `refName: name conflict`
  for a reference that does not exist and overlaps an existing one, and for a reference at no commit, never retried as a
  lost race; `NOT_FOUND` for edits whose paths are invalid on any of Linux, Windows and macOS, repeated without regard to
  case, or of which one is a directory of the other; and `FAILED` for a stored tree JGit cannot take in (a path such as
  `.GIT`, a tree too large to be read in one piece) and for an invalid `gpg.format` of a signed commit. An exception of
  the client's own `TreeOperation` or `Signer` propagates unchanged.

[cols="2,2"]
|===
|`GitOutcome` of `pm-provider-git` |`GitOutcome` of `git-core`

|`OK`, `NOT_A_REPOSITORY`, `NOTHING_TO_COMMIT`, `ALREADY_EXISTS`, `BRANCH_CHECKED_OUT`, `WORKTREE_NOT_FOUND`,
`WORKTREE_DIRTY`, `WORKTREE_LOCKED`, `PATH_REFUSED` |unchanged
|`UNKNOWN_REVISION`, `PATH_NOT_FOUND` |`NOT_FOUND`; a commit the remote does not serve in `fetchCommit` is `UNSERVED`
|`REJECTED_NON_FAST_FORWARD` |`REJECTED`, also for the remote's other refusals
|`REJECTED_LEASE` |`LEASE_REFUSED`
|`REMOTE_ORIGIN_MISMATCH`, `CAPABILITY_MISSING` |`REFUSED_BY_POLICY`; the detail names the remote or the capability
|`GIT_IDENTITY_AMBIGUOUS` |`AMBIGUOUS`
|`GIT_IDENTITY_MISMATCH` |`IDENTITY_MISMATCH`
|`UNAVAILABLE` |dropped: the worktree digest stays in `pm-provider-git`, whose facade maps its own outcome
|none |new: `CONFLICT`, `UNREACHABLE`, `CREDENTIALS_INVALID`, `UNSERVED`, `FAILED`
|===

[[_what_the_worktrees_package_took_and_changed]]
=== What the Worktrees Package Took and Changed

The package `de.cuioss.git.document.core.worktrees` of `git-core` changed the copied code where the requirements of
the libraries demand it (xref:../specification/git-core.adoc#working-trees[`git-core`, Working Trees]); the facade of
`pm-provider-git` maps the differences at the switch-over:

* *Outcomes.* The worktree operations report the constants of `GitOutcome` of `git-core`, so the mapping of the table
  above applies to them as well; an unexpected failure is `FAILED` with the failure class as detail.
* *Administration directory.* `LinkedWorktrees` claims the administration directory `worktrees/<id>/` atomically with
  `Files.createDirectory` and moves to the next numeric suffix when the name is taken, instead of probing it with
  `Files.exists` and then creating it, so two concurrent additions on one repository never share it. It writes each
  file completely before it appears under its name, `HEAD` last, removes the directory it claimed when a write fails,
  skips an entry without `gitdir` or `HEAD` when listing, and resolves a relative `gitdir` against the administration
  directory.
* *Concurrent additions.* `worktreeAdd` claims its target exclusively and reserves every branch, a new one like an
  existing one, until the new working tree is complete; a refused or failed addition removes only what it created, a
  branch it created only while the branch still points at the start. An unknown start point is not found, also for an
  existing branch. A failed release of the reservation after a complete addition ends `OK` with the working tree kept
  and the reservation left for `releaseBranchReservation`, and is logged as `GIT_CORE-105` without an argument.
  `releaseBranchReservation` is new: it releases a reservation an ended process or a failed release left behind
  (xref:../specification/git-core.adoc#GDR-CORE-15[GDR-CORE-15]).
* *Guards.* `worktreeAdd` refuses a bare root `PATH_REFUSED`, since its root is the git directory, and guards the
  branch name more strictly than the source: besides the reference names JGit refuses, `HEAD`, `@`, a leading `-`, a
  component ending `.lock` and a name starting `refs/` end `REFUSED_BY_POLICY`, for an addition as for
  `releaseBranchReservation`.
* *Removal.* `worktreeRemove` ends `WORKTREE_NOT_FOUND`, no longer `IDENTITY_MISMATCH`, for a repository at the root
  that is not the registered working tree, compares the registered paths as real paths and removes a prunable working
  tree by its administration directory only.
* *Commit.* `commit` refuses a present `pre-commit`, `commit-msg` or `post-commit` hook before anything is staged, does
  not stage the root of a linked working tree inside the committing one, and writes the `HEAD` reflog entry of a
  commit in a linked working tree to that working tree's own log; a reflog entry that cannot be written keeps the
  created commit `OK`, whatever the failure, so the reflog step no longer reports a stored commit as thrown. An
  invalid `core.autocrlf` ends `FAILED` with the failure class for `commit`, `worktreeStatus` and `worktreeRemove`.
* *Log messages.* The INFO messages carry no path and no administrative name; the add message names the start commit,
  and the release of a branch reservation is logged without an argument. The WARN message `GIT_CORE-103` names
  the commit id of a commit whose reflog entry was not written.
* *Status.* The working-tree status `worktreeStatus` is new: the three path sets `changed`, `untracked` and `deleted`
  mapped from JGit's `Status`, whose union is the path union the source's `worktreeSha` reads; the digest itself stays
  in `pm-provider-git`.

== What Changes in `pm-mcp-core`

Each item is part of the work package that switches `pm-provider-git` over:

. *The dependency decision* for the new artifacts, by the owner of `pm-mcp-core`; their version comes from its root
  POM's `dependencyManagement`.
. *The Module Structure Specification* of PM-MCP: `pm-provider-git` may depend on `git-core`.
. *The enforcer rules of the root POM* name the new artifacts, and `BuildGuardsIT` proves the changed rule. JGit stays
  a dependency of `pm-provider-git` through `git-core`; `pm-core` and `pm-workflow` stay without JGit.
. *The registry.* Artifacts under `de.cuioss` from Maven Central need no change of the group filter in `.mvn/rrf`.
. *The documentation*: `pm-provider-git/README.adoc`, its developer documentation, ADR 012 of PM-MCP for the generator
  that moves out of `pm-provider-git:tests`, and an ADR for the extraction itself.
. *The assembly* `plan-marshall-mcp` keeps its interface through the facade; the native build of `pm-mcpd` against the
  new `SNAPSHOT` verifies that JGit still works in the native image.

The effect on the size of `pm-mcp-core` is small: about 1,700 lines of production code and most of 3,800 lines of
tests leave, against more than 150,000 lines of production Java. The value lies in the shared foundation, not in
the size.

== Order of the Switch-Over

. Fill `git-core` and `git-testing`: copy the classes and their tests into `git-core` (the worktree part into its
  package `de.cuioss.git.document.core.worktrees`), and the generator into `git-testing`, each as a plain copy without
  history whose commit names the source (owner's decision, 2026-11-17); build and release a first version. `git-core`
  and `git-testing` are filled; the first release follows.
. Work package in `pm-mcp-core`: switch `pm-provider-git` onto `git-core` and reduce it to facade, adapter and
  digest, with the changes listed above.

The aspect modules of the document store (`git-store` and the modules above it) change nothing in `pm-mcp-core`.

[CAUTION]
====
Coupling two life cycles is the price of the shared foundation. A contract change wanted by PM-MCP is a release of
`git-document-repository` first. The foundation stays small precisely so that this price stays rare.
====
